# Input monitoring, multi-track recording, and takes

**Contracts.** `MonitorMode { Off, On, Auto }` is a node field `NodeKind::Audio::monitor` (in the project, undoable; default `Off`: with speakers and a microphone close together, monitoring causes feedback), edited via `TrackControl::set_monitor`. `InputChannels { Stereo, Left, Right }` and arming are session state in `AudioRecordControl` (`set_armed`, `set_input`; not written to the project). `InputMonitor` (implements `EngineLink`): the recorder hands the engine a table of `TrackInput { track, armed, channels }`, and the engine answers with `MonitorStatus { listening, input_rate, output_rate }` (`problem()` — a human-readable text). `LiveInput` is the input-reading side for the output audio thread; it is provided by `AudioCapture::take_live_input` (once), and `daw-bootstrap` (`wiring/audio.rs`) passes it to the engine with the command `DspCommand::SetLiveInput`. `TakeControl` (`ProjectTakes`) — clip takes.

**Monitoring signal path.** Besides peaks and the recording queue, the input callback (`daw-audio-cpal/src/capture.rs: InputFeed::feed`) writes channels 1–2 as stereo frames into a second `rtrb` queue (`live.rs`, 16,384 frames, mono goes to both channels) while the engine needs the input. There is one queue for the host's whole lifetime: the writing side moves into each new input stream via `Arc<Mutex<..>>` and is taken in the callback only with `try_lock` (like the engine in the output; it is busy only at the moment the stream changes). The input is opened by the host thread at the engine's request: `LiveInput::set_wanted` → an atomic → `Host::follow_monitoring` on every loop iteration (at least every 250 ms); the input is shared with recording and the level meter and is closed when nobody needs it; without running output the request has no effect; if it fails to open — one log entry per request. In the engine, `monitor.rs` (`InputListener`) on every segment: picks the listening audio tracks from the snapshot and the input table (`MonitorMode::hears_input(armed)`); the input is needed if someone is listening or armed (levels and instant recording start). The input block is added, by the track's channels (`InputChannels::sides`), into its node's buffer before the mixer — from there it goes through the track's fader, mute/solo, effects, and PDC, on top of its clips. Jitter buffer: we start when the input holds a block + margin (128 frames); if it runs short — the tail of the block is silent, `EngineLosses::monitor_underruns` +1 (logged by `engine_watch`), and the margin doubles up to 4096; if more than "block + 2 margins + segment" accumulates — the excess is discarded. When nobody is listening, the input is drained so latency does not build up. If the input rate ≠ the output rate, the input is not monitored (we don't do real-time resampling); `MonitorStatus::problem` says so, and the UI colors "IN" and shows the text. The engine's input table is `link/monitor.rs` (`MonitorTable`, a `u64` cell per track, atomics only).

**Multiple tracks.** There is one input: the recorder accumulates channels 1–2 in full, and on `stop` each armed track gets its own (`split.rs: track_sound`: `Stereo` — stereo, mono for a mono input; `Left`/`Right` — a mono file). The latency trim (configured or estimated + PDC, `take.rs`) is shared. Start errors: no armed audio tracks, the project has no file, the input failed to open (no device / no microphone access), a take is already in progress; arming and input changes during a take are rejected; deleted tracks are silently dropped.

**Takes.** Recording over an audio clip on the same track that it covers at least halfway, or that it lies entirely inside (of several — the one covered more, `split.rs: covered_clip`), does not create a new clip but becomes a new active take of that clip (`TakeControl::add_take`). Model: `ClipContent::Audio { sample, takes }` — `sample` plays, `takes` holds all takes in recording order (empty — a single sound; then the field is absent in JSON). The clip does not move or change length; all takes share its `offset_frames`, warp, pitch, volume, and fades, so a new take's audio is aligned to the clip start (`split.rs: align`): anything recorded before the clip start is trimmed, a late start becomes silence at the front; crossfades with neighbors do not change (the position is the same). Choosing the active take (`set_active_take`) and removal (`remove_take`; active → the last remaining one; one left → a regular clip; the only sound cannot be removed) are one undo step each; a new take from recording is inside the "Record audio" step. Removing a sample from the project removes it from takes; the clip is deleted only if that sound was its only one. The snapshot and processing (`clip_audio`, `ProcessJob`) use the sounding takes, so changing the take of a warped clip recomputes the audio.

**Take comping (by segments).** `ClipContent::Audio::comp: Vec<CompSegment { start_ticks, take }>` — from `start_ticks` (relative to the clip start) until the next segment, take `take` plays; ascending, the first at 0, neighbors are different takes (identical ones merge; if only one take remains, there is no comp and it becomes active); empty — the whole clip plays `sample` (the field is absent in JSON). The contract is `TakeControl::set_comp` (the whole comp, validated: the clip's takes, starts inside the clip, ascending, no more than `MAX_COMP_SEGMENTS`) and `choose_take_range(clip, from, to, take)` (the range `[from, to)`, the rest unchanged — the UI calls this), one undo step each; `set_active_take` and a new take from recording clear the comp; `remove_take` gives the removed take's segments to their neighbors. The comp follows the clip: split divides it (`take_rules::split_comp`), shortening drops segments past the end (`fit_comp`); warp, pitch, offset, volume, and fades are shared. How it sounds is one formula `Clip::take_span(i, &TempoMap)` (`daw-contracts/src/takes.rs`, no allocations): piece `i` with half of the transitions to its neighbors; a transition is an equal-power crossfade of `COMP_CROSSFADE_SECONDS` = 10 ms in tempo at the seam, no longer than half of the shorter adjacent segment. The engine (`audio_voices.rs`) starts one voice per piece (`AudioVoice::part`; audio — `clip_audio[(clip, take)]` or the take's sample), each from the "frames from the clip start" position, and multiplies by `sin` of the transition fraction — like overlapping clips; when the comp is edited during playback, voices follow their pieces, and the voice of a vanished piece (or of a piece with a different take) goes away. Export uses the same engine (`daw-render: clip_audio` — per take). RPC: `clips.setComp { id, segments }`, `clips.chooseTakeRange { id, from, to, take }`. UI: `ui/pianoroll/TakeLanes.tsx` in the audio clip panel — one waveform row per take (`clipWaves.takeColumns`), sounding pieces are highlighted (`domain/takes.ts: takeRanges`), dragging along a row calls `actions.clips.chooseTakeRange` (ends snapped to the timeline grid — `domain/takes.ts: draggedRange`, the grid comes from `TracksView` via `ClipPanel`; Alt — no snapping), clicking the name calls `setActiveTake`; on the timeline, a comped clip's waveform is assembled from the pieces of its takes, and its label is "⧉ comp". Mock — `mock/takeRules.ts` (the same rules). Tests: rules — `take_rules.rs`, contract — `daw-project/src/tests/takes.rs`, formula — `daw-contracts/src/takes.rs`, engine (seam without a click, the right take frames, editing during playback) — `daw-engine/src/tests/comp.rs`, export = live audio — `daw-bootstrap/tests/render_comp.rs`, wire — `daw-rpc/tests/warp.rs`.

**Loop recording.** With a loop region, playback jumps back at its end during an audio take, while the input arrives as one straight run. `AudioRecorder::start` remembers the loop region (`Running::loop_region`); on `stop`, after the latency cut, `passes.rs: passes` (pure) cuts the run where the jumps were: the first pass runs from the take start to the loop end (a pre-roll before the loop included), each next one is a whole loop, a stop mid-loop leaves a last pass that did not reach the end (`Pass::reached_end`); boundaries follow the tempo map and are summed in fractional frames, so many passes do not drift. One pass (no jump, or a take started at or past the loop end) is an ordinary take. With several, `take.rs: place_passes` gives each track one clip on the loop region — the clip the loop covers (`covered_clip` over the loop) or a new one at the loop start made from the first pass — and every pass becomes its take (`TakeControl::add_take`), aligned to the clip start like a single take (`split.rs: align`; the pre-roll is cut). The last pass that played to the loop end is made active (`set_active_take`); a pass cut short by stop stays as a take that does not play. Files are named "Recording <track> (pass N)"; all passes are written and imported before any clip changes, so a clip that does not fit loses no audio ("saved to Samples, but the clip was not created"). Everything stays one "Audio recording" undo step. Tests: `passes.rs` (cuts, pre-roll, mid-loop start, tempo change, no drift), `tests/take.rs` (a new clip with three passes, the clip under the loop, a pre-roll, a take past the loop end). Mock — `mock/loopPasses.ts` (the same cut in seconds) and `placePasses` in `mock/handlers/audioRecord.ts`. Note recording keeps its own loop recording inside the take clip (`daw-recorder`).

**Limitations.** A new take from recording clears the comp (undo brings it back). The loop region is read when the audio take starts: moving it during the take is not followed. Every loop pass is a take with no upper limit (a long take over a short loop makes many takes; one undo removes them all). Comp seams are exactly 10 ms (not configurable). A new take is recorded at the project tempo: in a warped clip whose source tempo is different, it will be stretched like the earlier ones (warp is shared). Takes with different sample rates are aligned precisely only if `offset_frames = 0` (the offset is shared, in frames). A recording that covers a clip by less than half and does not lie inside it becomes a new clip (if there is room). Monitoring works only when the input and output rates match; monitoring latency = device buffers + margin (from ~3 ms) + the track's PDC; with different devices the clocks drift — occasional clicks (visible in the log). Arming and input selection are not saved in the project. Input channels are only 1 and 2. The clips of a monitoring track play along with the input (they are not muted).

**How to add something similar** (e.g. inputs 3–4): a variant in `InputChannels` + `sides`/`file_channels`, recording and monitoring queues for more channels (`capture.rs`, `live.rs`), labels — `domain/recordInput.ts`.

**Recording audio from an input.** RPC `audioRecord.*` (`api.audioRecord`), actions — `actions/audioRecord.ts`: `setArmed`, `setInput`, `stop` (selects the created clips via `showCreated`, warns with a toast when `droppedFrames > 0`) and `pressRecord` — the shared "● Record" transport button: if a take is in progress — stop; if there are armed audio tracks — note recording is armed and the take starts on all of them at once; otherwise — as before, note recording only. Note recording itself (arming, the record quantize) is `actions/noteRecord.ts`, which `pressRecord` asks. Recording state for the interface is `state/recordingStatus.ts`: a single poll ~15 times per second (`state/poller.ts`), turned on by actions (`ctx.followRecording()`) and at startup, and turning itself off when there is no take and nothing is armed; read via `session.recordingStatus()` (the take in progress or `null`), `session.trackInput(track)` (arming, input, track levels) and `session.monitorProblem()`. Audio track header: "●" arms recording (red — armed, blinking — take in progress, a click during a take — stop), next to it "1–2▾" (or right-click on "●") — the track input: the `InputMenu` menu (the shared `ContextMenu`, `fixed` above everything so the header does not grow; choices by the input device's channel count — `domain/recordInput.ts`), and an armed track shows its input level; "IN" — input monitoring, click cycles: off → auto ("IN·A") → on (`MonitorButton`; all of this is in `ui/tracks/TrackInput.tsx`; the tooltip warns about feedback with speakers and shows `monitorProblem`). The red badge with "Stop" is in the transport bar (`AudioRecordBadge` in `ui/transport/TransportBar.tsx`). A clip's takes are in the audio clip panel (`TakeList` in `ui/pianoroll/AudioClipPanel.tsx`: "active" and ✕); on the timeline the label is "⧉ 2/3" (`domain/clips.ts: clipLabel`, take list — `domain/takes.ts`). The "Recording latency, ms" field (`recordLatencyMs`, empty = auto) is in the "Audio" settings section. Mock: `mock/handlers/audioRecord.ts` (arming and input, time from the clock, pseudo-levels, a single "Record audio" undo step, a take over a covered clip), take rules — `mock/takeRules.ts`, `tracks.setMonitor` — `mock/handlers/tracks.ts`, `clips.setActiveTake/removeTake` — `mock/handlers/clips.ts`.
