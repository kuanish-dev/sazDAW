# Channel utility: polarity, width, mono, time alignment

The engineer's utility controls on every track and bus: polarity (often called "phase") invert per side, stereo width, a mono switch and fine time alignment, to line up multi-mic drums or a DI with its amp mic.

* **Why on the strip, not a "Utility" effect.** Engineers expect these on the channel (a console's input section; Ø and track delay sit on the channel in most DAWs) and need them on many channels at once: aligning eight drum mics should not mean inserting eight effects. On the strip they are always there, save and undo like volume and pan, and need no place in the insert chain. The time alignment also fits plugin delay compensation directly as a node's own latency, the documented way to add "something similar" there. Like the stage place, it is a property of the channel.
* **Contract** (`daw-contracts/src/graph.rs`): `Strip` gains `polarity: Polarity { invert_left, invert_right }`, `width` (`0..=MAX_WIDTH` = 2: 0 mono, 1 as recorded, 2 twice the side), `mono` (sums to `(L + R) / 2` whatever the width, which is kept for when it is off) and `delay_ms` (`±MAX_CHANNEL_DELAY_MS` = 10 ms: positive later, negative earlier). They sit flat in the node JSON (`polarity: { invertLeft, invertRight }`, `width`, `mono`, `delayMs`) and are required (no serde defaults, rule 10: older project files do not open). `GraphControl::set_polarity`, `set_width`, `set_mono`, `set_delay` (`daw-project/src/graph.rs`): width and delay are clamped and a knob gesture merges into one undo step (`edit_keyed`, keys `width:{id}` and `delay:{id}`); polarity and mono are one step each. The master and effects are `graph::NO_UTILITY` (GR-126); not a number is `WIDTH_NOT_A_NUMBER` (GR-127) / `DELAY_NOT_A_NUMBER` (GR-128).
* **Where in the sound.** Before the node's volume and pan, like a console's input section (`mixer/mod.rs: process`): the pre-fader sends and the inserts hear the result, and so does a channel's stage voice. Order: polarity, then mid/side width (mono is width 0), then the delay.
* **Engine** (`daw-engine/src/mixer/utility.rs`, `ChannelUtilities`). One slot per possible node with two delay lines (`stage/dsp.rs: DelayLine`, read at whole samples), allocated by `new`/`prepare` for `MAX_CHANNEL_DELAY_MS` at the stream rate. A slot follows its node id across snapshots through the mixer's `Carry` (`compile.rs: bind_utilities`); a channel new to the mixer takes a free slot, cleared. The lines always take the channel's sound in, so a delay set later plays real history at once. Every change glides over one segment: a polarity flip fades that side through silence, a width or mono change moves the side gain, a delay change crossfades from the old tap to the new one. Neutral settings leave the sound exactly as it is. No allocations or locks on the audio thread.
* **Time alignment and PDC.** The delay is whole samples at the stream rate (`round(ms × rate / 1000)`; the interface shows both units). Later is a plain delay in the channel's own lines and holds nothing else back. Earlier cannot be played ahead of time, so the channel's lead is its own latency for compensation (`latency.rs: own_latency`): the rest of the mix waits for it, the transport shows the extra "PDC N ms", and the channel plays that much earlier relative to everything else. Each parallel path then needs a compensation line (the same cost as a latent plugin on one track, up to `MAX_DELAY_LINES`). Nudging within the earlier range glides (the compensation lines crossfade to a new delay); switching a channel between "not earlier" and "earlier" re-lays the compensation once, a short jump like turning a latent plugin on.
* **Automation and MIDI learn.** Only the width is automatable: `ParamTarget::NodeWidth { node }` (`0..=MAX_WIDTH`, JSON `{ "type": "nodeWidth", "node" }`), valid on sources and buses (`ops::validate_target`), removed with the node (`ops::drop_node`), overriding the width for the segment (`GraphMixer::override_width`); a MIDI knob spans its whole range. Polarity and mono are switches and the delay would bend the pitch while it moved, so they are not.
* **Bounce and freeze.** The copy's sound already holds the polarity, width and a later alignment, so the copy starts neutral; a lead cannot be rendered, so the copy keeps the source's negative `delay_ms` (`daw-project/src/bounce.rs: place`).
* **RPC / MCP:** `graph.setPolarity { id, invertLeft, invertRight }`, `graph.setWidth { id, width }`, `graph.setMono { id, mono }`, `graph.setDelay { id, ms }` (`daw-rpc/src/graph.rs`); `project.get` carries the fields in every source and bus.
* **Frontend.** `ui/common/ChannelUtility.tsx` on the mixer strip (above the pan) and in the graph inspector (under M/S): Ø (both sides), L and R (one side), Mono, the Width knob (right-click: automation, MIDI learn; dimmed while mono) and the Delay knob with its value in ms and, under it, in samples at the stream rate with ‹ › one-sample nudges. The rate is read once per view (`ui/common/streamRate.ts`, via `actions.audio.status`; 48 kHz until read). Units, ranges and the neutral values are the pure `domain/channelUtility.ts`; actions `graph.setPolarity/setWidth/setMono/setDelay` show the value at once (`patchProject`), the width also tells live automation writing (`ParamTouch`). Automation lanes "· width" come from `domain/automation.ts`. The mock repeats the rules and codes (`mock/handlers/graph.ts`, `mock/handlers/automation.ts`, the copy's lead in `mock/handlers/bounce.ts`); new strips get `neutralUtility()`.
* **Limitations.** The master has no utility: checking the whole mix in mono is the live master meter's monitoring switch (see "Live master meter" ([docs/features/master-meter.md](master-meter.md))), which is not saved or exported, while a channel's mono is part of the mix. Export and track renders are not trimmed by the total PDC latency, so a channel set earlier makes them start that much later, as a latent plugin does. The lines hold 10 ms, so a room mic farther than about 3.4 m needs a delay effect.
* **Tests:** contract — `daw-project/src/tests/channel_utility.rs` (and the width knob in `midi_mappings.rs`, the copy's lead in `bounce.rs`); JSON — `daw-contracts/src/graph/tests.rs`; engine — `daw-engine/src/tests/utility.rs` (polarity, width and mono, width automation, later delay, earlier through PDC, gliding changes); RPC wire — `daw-rpc/tests/all/graph.rs`.
* **Adding a similar channel control:** a `Strip` field and a `GraphControl` setter (with its code), the value in `NodeRt` (`compile.rs: rebuild_nodes`), the DSP in `ChannelUtilities::process`; if it is automatable, a `ParamTarget` variant through every match (ops, MIDI learn, render, mixcheck, engine automation) and `domain/automation.ts`; then the mock, the actions and `ChannelUtility.tsx`.
