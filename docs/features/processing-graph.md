# Processing graph: nodes, connections and their rules

* **The rules.** The graph has no cycles: a source (instrument, audio track) only outputs sound (`NodeKind::accepts_input` — no), the master only receives (`has_output` — no), effects and buses ("processors") connect to each other in any order — this enables a compressor on a bus (bus → effect → master) and a limiter on the master (all inputs → effect → master). Sidechain goes only into an effect; a pre-fader send only from a source or a bus (see "Sends" ([docs/features/sends.md](sends.md))). The rules are written in one place — `Graph::check_edge` (`daw-contracts/src/graph.rs`); the frontend repeats them in `domain/graph.ts` (`checkEdge`, `acceptsInput`, `hasOutput`) for hints, and the mock checks them with the backend's codes (`mock/graphOps.ts: checkEdge`, built on the same predicates).
* **Order and engine.** Processing order is topological over connections (`Graph::order`), computed on the control side and shipped to the engine in the snapshot; the mixer (`daw-engine/src/mixer/`) follows it strictly, and solo (`compile.rs: mark_heard`) and meters work over connections, including bus → effect → bus chains. A meter (post-fader level) exists on every node with a fader — tracks and buses — and on the master (`compile.rs: assign_meters`); the track header and the graph nodes show it.
* **Inserting an effect without breaking the path:** `GraphControl::insert_effect` (after a source, effect or bus: the node's outputs move to the effect) and `insert_effect_before` (before the master, a bus or an effect: the node's regular inputs move to the effect, sidechain stays; RPC `graph.insertEffectBefore`). In the UI — "＋ Effect" in the source and bus inspector and "＋ Effect on master" on the master (`ui/graph/Inspector.tsx`), and "＋ Effect on selected" in the graph toolbar (`GraphToolbar.tsx`); the new effect's position — `graphLayout.ts: insertedEffectPosition`; "Arrange" lays out columns by the depth of the signal path (`autoLayout`).
* **A configured effect in one call.** `add_effect`, `insert_effect` and `insert_effect_before` take `params` on top of the catalog defaults (RPC field `params`, optional), checked and clamped like `set_effect_param` (`ProjectGraph::new_effect`); a bad name or value creates nothing, and the effect with its params is one undo step. It exists for the AI: building a mix used to cost one `graph.setEffectParam` call per knob. The UI creates effects with defaults and passes nothing.
