# Tempo map: tempo and time signature changes through the song

* **Model and contract.** `Project::tempo_map: TempoMap` (`daw-contracts/src/tempo_map.rs`) is the single source of tempo and time signature; its first points (tick 0) are "the project tempo and signature". An invalid map cannot be created: `TempoMap::new` and JSON reading run the same checks. Editing goes through `TempoControl` (`daw-contracts/src/tempo.rs`; implementation `ProjectTempo`, `daw-project/src/tempo.rs`; `Controls.tempo`): lists are replaced whole, every edit is one undo step through the core. The transport does not store tempo.
* **One set of math** — `TempoMap` methods (no allocations, so the audio thread uses them; a ramp is an exact integral, not a numeric one). Tests — `tempo_map/tests.rs`. The frontend mirrors it in `common/tempoMap.ts`, plus bar counting and snapping, `gridLines`, `barPosition` and the pure point edits `with*` (signature edits keep later changes at their bar numbers).
* **Clock and engine.** `TransportClock::advance` takes the map from the engine's snapshot (before the first snapshot — a default map created in advance, so the audio thread never allocates). It cuts segments at map points and keeps them short inside a ramp (`RAMP_SEGMENT_FRAMES`); the segment end comes exactly from the map, so the position does not drift. `BlockTiming` carries the segment's tempo, signature and `signature_start`; VST3 `ProcessContext`, the tempo-synced delay and the metronome follow from it (accents count from `signature_start`, so after "3/4 → 4/4" the accent follows the new bar at once).
* **Who else converts ticks ↔ time — all via the map:** export (`daw-render/src/export/range.rs`), the length of a plain audio clip (`ProjectClips::add_audio_clip`; `Clip::ticks_to_source_frames`/`source_frames_to_ticks` count from the clip start — split and warp use them), warp to tempo (see [warping.md](warping.md)), audio recording (`daw-audio-recorder/src/take.rs`: take end, alignment to the covered clip), note recording (a new clip starts at `bar_start`), drum part preview (the tempo in the start bar), telemetry (`tick.tempo`/`tick.signature` at the heard position), MIDI files (`daw-midi/src/file/tempo.rs`: a ramp is written as a staircase of average-tempo steps that keeps the time; clip export writes the tempo and signature at the clip start; `MidiFileIo::import_tempo` replaces the whole map in one step).
* **RPC and MCP** (`daw-rpc/src/tempo.rs`): `tempo.get`, `tempo.set`, `tempo.setSignature` (song start), `tempo.setChanges`, `tempo.setSignatureChanges` (whole lists, one undo step; the descriptions carry a worked example in ticks), `midi.importTempo`. `project.get` carries `tempoMap`.
* **UI.** Actions — `transport/tempo.ts` (`TempoActions`; the value shows at once via `patchProject`). The transport bar's BPM and signature fields show and edit the point in effect at the playback position (`tick.tempo`); "Settings" → "Project" edit the values at the start. There is no tempo lane (owner's choice: tempo changes and ramps are edited through MCP/RPC `tempo.setChanges` or taken from a MIDI file via `midi.importTempo`). The timeline header is the bar ruler, its own canvas (`rulerRender.ts`, `RULER_HEIGHT` in `timelineLayout.ts`; see "Timeline ruler strip" in [cue.md](cue.md)); grid and bar numbers come from `gridLines`. Signature flags ("7/8" after the bar number): geometry `tracks/tempoLayout.ts`, drawing `tempoRender.ts`, mouse `tempoPointer.ts` (double or right click), menu `TempoMenu.tsx`. Mock — `mock/handlers/tempo.ts` (repeats the `TempoMap::new` checks with the backend's codes); the mock's position follows the map.
* **Adding something similar** (e.g. another ramp shape): a field in `TempoChange` and a rule in `TempoMap::new` → math in `tempo_map.rs` and `common/tempoMap.ts` with tests → the transport clock cuts the segment if needed → RPC description.
* **Bars come only from the map.** Everything that counts song bars takes them from the map, not from `BAR_TICKS`: timeline snapping (`snapNearestInBars`/`snapDownInBars`: the "Bar" grid `BAR_GRID` means the map's bar boundaries, finer steps count from the bar start; used by move, resize, split, loop, sample drop and automation points), "clip per bar" by double click and `NewNoteClip` without a length (`TempoMap::bar_length_at`), clip paste (`tracks/clips.ts: paste`), markers (`tracks/markers.ts`, `markerPointer.ts`), the automation grid (`automation/patternRender.ts` — `gridLines`), clip length in bars (`barsBetween`), drum part start (`daw-patterns/src/plan.rs: bar_start_tick`; the mock does the same), the note recording clip, the console commands `clip`/`clips`/`loop` (`daw-app`).
  **A note clip** keeps an even grid of the signature at its start (`pianoroll/noteClip.ts: clipBarTicks`; backend auto length `daw-project/src/note_rules.rs: fit_length`): the piano roll and "Steps" bars, the "Bar" grid, Shift + arrow, the spare bar, "Content length". A signature change in the middle of a clip does not cut its grid; a clip moved into another signature recalculates its auto length on the next note edit.
  **Constant 4/4** (`BAR_TICKS`) stays where it is meant: drum pattern designs and the demo beat (16 steps per bar; in 3/4 a pattern plays longer than a song bar), limits (`MAX_CLIP_LOOP_TICKS`, note recording snap), the timeline's width margin, the console step row.
  Tests: `daw-contracts/src/tempo_map/tests.rs`, `daw-patterns/src/plan.rs`, `daw-bootstrap/tests/all/drum_part.rs` (`start_bar` in 3/4), `daw-project/src/tests/tempo.rs` (a clip in 7/8).
* **Limitations.** A warped clip with a tempo change inside follows a curve (see "Warping across tempo changes" in [warping.md](warping.md)); WSOLA places attacks early by roughly (stretch − 1) × 50 ms, as with a single stretch. A plain audio clip does not change length if the tempo under it changes later. VST3's `projectTimeSamples` and the metronome's PDC shift use the segment tempo (an approximation). A MIDI tempo ramp is a staircase; on import it stays a staircase.
