# Tempo map: tempo and time signature changes through the song

* **Model and contract.** `Project::tempo_map: TempoMap` (`daw-contracts/src/tempo_map.rs`; JSON `tempoMap: { tempos: [{ tick, bpm, ramp }], signatures: [{ tick, signature: { numerator, denominator } }] }`, `#[serde(default)]`) is the single source of tempo and time signature: the first points are at tick 0 ("the project tempo and signature"); the old `Project::tempo`/`time_signature` are gone (old files open at 130 BPM 4/4 — rule 10). `TempoChange.ramp` — the tempo moves smoothly (linearly in ticks) from the previous point to this one; otherwise it is a step at the point; the first point never has a ramp. A signature change sits at a bar start of the previous signature. An invalid map cannot be created: `TempoMap::new` (and reading from JSON) checks that the first points are at tick 0, ticks strictly increase, none is beyond `MAX_CLIP_TICK`, there are no more than `MAX_TEMPO_CHANGES` (512) and `MAX_SIGNATURE_CHANGES` (256), and signature changes are on a bar. Editing goes through the contract `TempoControl` (`daw-contracts/src/tempo.rs`; implementation `ProjectTempo`, `daw-project/src/tempo.rs`; in `Controls.tempo`): `set_tempo_changes`, `set_signature_changes`, `set_tempo_map` (the whole map), `set_tempo`/`set_time_signature` (only the point at tick 0). Every edit is one undo step through the core. `TransportControl` no longer knows about tempo.
* **One set of math** — `TempoMap` methods (no allocations): `tempo_at`, `signature_at`, `seconds_at`/`tick_at_seconds` (a ramp is an exact integral: time under a linear tempo is a logarithm, the inverse is an exponential; seconds up to each point are precomputed in `new`, lookup is binary search), `frames_between`, `tick_after_frames`, `next_change`, `in_ramp`, `bar_start`, `bar_index`, `bar_tick`, `bar_length_at`. Tests — `tempo_map/tests.rs` (exact values, ramp vs. numeric integral, round trip, bars 3/4 → 4/4, rejections, JSON). The frontend repeats it in `domain/tempoMap.ts` (plus `barLengthAt`, `barsBetween`, snapping `snapNearestInBars`/`snapDownInBars`, `gridLines` for the grid, `barPosition`, the `tempoMapProblem` check for the mock, and pure edits `withTempoAt`/`withTempoPoint`/`withMovedPoint`/`withoutPoint`/`withRampToggled`/`withSignatureFrom`/`withSignatureAt`/`withoutSignature`; signature edits keep later changes at their bar numbers).
* **Clock and engine.** `TransportClock::advance(max_frames, rate, &TempoMap)`: the engine passes the map from its snapshot (before the first snapshot — a default map created in advance). A segment is cut at map points (`next_change`, like at a loop boundary); inside a tempo ramp it is no longer than `RAMP_SEGMENT_FRAMES` (512). The segment end is computed exactly from the map (`tick_after_frames`; an end near a point "snaps" to it), `ticks_per_frame` is the segment average, so the position does not drift and note error inside a ramp segment is a fraction of a millisecond. `BlockTiming::tempo` is the tempo at the segment start, `time_signature` and `signature_start` (the tick of the signature change) are the segment's signature, `bar_start(tick)` is the bar start. VST3 (`ProcessContext`: tempo, signature, bar start), the tempo-synced delay, and the metronome follow from this automatically (beats and accents are counted from `signature_start`, so after "3/4 → 4/4" the accent immediately follows the new bar). An audio clip entered in the middle starts its audio at `frames_between(clip start, position)`.
* **Who else converts ticks ↔ time — all via the map:** export (`daw-render/src/export/range.rs`: length — `frames_between(range start, end)`; the engine plays by the snapshot's map), the length of a regular audio clip (`ProjectClips::add_audio_clip` — from the clip's position; `Clip::ticks_to_source_frames`/`source_frames_to_ticks` — also from the clip start: split and warp), warp to tempo (a single stretch by the tempo at the clip start, or a curve if the tempo changes inside the clip), audio recording (`daw-audio-recorder/src/take.rs`: the take end and alignment to the covered clip), note recording (a new clip starts at a bar start per the map, `bar_start`), drum part preview (the tempo in the start bar), telemetry (`tick.tempo` and `tick.signature` — at the heard position; the heard position under PDC goes through the map's seconds), MIDI files (`daw-midi/src/file/tempo.rs`: project export writes the map's tempo and signature events, a ramp becomes a staircase of up to 32 steps no finer than a sixteenth, each step at the average tempo, preserving time; clip export — the tempo and signature at the clip start; `MidiFileIo::import_tempo` replaces the map with the file's map in one step: no event at tick 0 — 120 BPM and 4/4; consecutive identical tempos are merged).
* **RPC and MCP** (`daw-rpc/src/tempo.rs`): `tempo.get`, `tempo.set { bpm }`, `tempo.setSignature { numerator, denominator }` (song start), `tempo.setChanges { changes }`, `tempo.setSignatureChanges { changes }` (whole lists, one undo step; the descriptions include the example "breakdown from bar 64 to 128, ramp up to 140 by bar 80" in ticks), `midi.importTempo { path }`. `project.get` carries `tempoMap`. The old `transport.setTempo`/`transport.setSignature` are gone.
* **UI.** Actions — `actions/tempo.ts` (`TempoActions`: `setTempoAt`, `setSignatureAt`, `setSignatureFrom`, `removeSignature`; the value is shown immediately via `patchProject`). The transport panel's BPM field shows the tempo at the playback position (`tick.tempo`); editing it changes the point in effect there (with no changes — the song tempo); the signature fields work the same way. The "bar:beat:tick" position and seconds — `barPosition`/`secondsAt` via the map. "Settings" → "Project" edit the tempo and signature at the start. Timeline: the header is the bar ruler (`RULER_HEIGHT` = `BAR_RULER_HEIGHT`, `timelineLayout.ts`); there is no tempo lane in the interface (owner's choice: tempo changes and ramps are edited through MCP/RPC `tempo.setChanges` or tempo from a MIDI file via `midi.importTempo`); it is its own canvas (`rulerRender.ts`), see "Timeline ruler strip" ([docs/features/cue.md](cue.md)). The grid and bar numbers — `gridLines` via the map (bars of different lengths). Signature flags ("7/8" after the bar number): geometry — `ui/tracks/tempoLayout.ts`, drawing — `tempoRender.ts`, mouse — `tempoPointer.ts` (double or right click on a flag), menu — `TempoMenu.tsx` (signature from a list, remove). Mock — `mock/handlers/tempo.ts` (the same `tempoMapProblem` checks); the mock's position follows the map.
* **Adding something similar** (e.g. another ramp shape): a field in `TempoChange` and a rule in `TempoMap::new` → math in `tempo_map.rs` and `domain/tempoMap.ts` with tests → the transport clock cuts the segment if needed → RPC description.
* **Bars come only from the map.** Everything that counts "song bars" takes them from the map, not from `BAR_TICKS`: timeline snapping (`domain/tempoMap.ts: snapNearestInBars`/`snapDownInBars`: the "Bar" grid (`domain/time.ts: BAR_GRID`) is the map's bar boundaries, other steps are counted from the bar start, and the bar end is also a grid point; used by move, resize, split, loop, sample drop and automation points), "clip per bar" by double click and `NewNoteClip` without a length (a bar of the signature at the clip's position — `TempoMap::bar_length_at`), clip paste (`actions/clips.ts: paste` — nearest bar boundary), markers ("＋ Marker" and Alt + double click — `barStart`, dragging the flag — nearest boundary), the automation grid (`automationRender.ts` — `gridLines`), clip length in bars in the clip panel (`barsBetween`), drum part start (`daw-patterns/src/plan.rs: bar_start_tick` — `bar_tick(start_bar)`; the mock does the same), the note recording clip (`bar_start`), the console commands `clip`/`clips`/`loop` (`daw-app`). **A note clip** keeps an even grid of the signature at its start internally (`domain/noteClip.ts: clipBarTicks`): the piano roll and "Steps" bar, bar and beat lines, the "Bar" grid, Shift + arrow, the spare bar, "Content length" in bars, and auto content length in the backend (`daw-project/src/note_rules.rs: fit_length(content, bar)`). A signature change in the middle of a clip does not cut its grid; a clip moved into a different signature recalculates its auto length on the next note edit. **Constant 4/4** (`BAR_TICKS`) remains where it is intended: drum pattern designs and the demo beat (16 steps per bar; in 3/4 a pattern plays longer than a song bar), limits (`MAX_CLIP_LOOP_TICKS`, note recording snap up to `BAR_TICKS`), the timeline's width margin (`visibleBars`), the width of a step row in the console. Tests: `daw-contracts/src/tempo_map/tests.rs`, `daw-patterns/src/plan.rs`, `daw-bootstrap/tests/drum_part.rs` (`start_bar` in 3/4), `daw-project/src/tests/tempo.rs` (a clip in 7/8); frontend — the `domain/tempoMap.ts` functions, verified against the mock.
* **Limitations.** A warped clip with a tempo change inside follows a curve (see "Warping across tempo changes" ([docs/features/warping.md](warping.md))); WSOLA places attacks early by roughly (stretch − 1) × 50 ms — the same as with a single stretch. A regular audio clip does not change length if the tempo under it is changed later (as before). VST3's `projectTimeSamples` and the PDC shift for the metronome use the segment tempo (an approximation). A MIDI tempo ramp is a staircase; on import the staircase stays a staircase.
