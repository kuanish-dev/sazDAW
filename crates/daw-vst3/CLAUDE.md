# `daw-vst3`

**Host for VST3 effects and instruments** — the only crate with `unsafe`: `Vst3Plugins` (`PluginScanner`: scan on button press + cache), `Vst3Scanner` ("find VST3 plugins in folders"), `Vst3EffectFactory`/`Vst3Effect` (`EffectFactory`/`Effect`), `Vst3InstrumentFactory`/`Vst3Instrument` (`InstrumentFactory`/`Instrument`), `Vst3Editors` (`PluginEditors`: native plugin windows; window state goes into the project via `PluginStates`), `Vst3CrashGuard` (`PluginCrashGuard`: report on a plugin crash) and the scan helper `daw-plugin-scan` (the crate's binary: one bundle in a separate process).

Depends on: contracts.

Map of the whole code: [ARCHITECTURE.md](../../ARCHITECTURE.md). Cross-layer features it takes part in: [midi-controllers](../../docs/features/midi-controllers.md).

## Place in the app

Installed VST3 plugins become ordinary catalog kinds next to the built-in ones: effects (`vst3:distortion`) in `EffectRegistry`, instruments (`vst3:surge_xt`) in `InstrumentRegistry`. The rest of the app knows nothing about VST3. Module roles are listed at the top of `src/lib.rs`.

The entry point is `Vst3Plugins` (`PluginScanner`, `Controls.plugins`). Only `daw-bootstrap/src/plugins.rs` builds it; that file is also the only place for `VST3_DIRS` (where we look), `GUARD_FILE` and `scan_helper` (where the helper is). The headless test session has no plugins and no cache, so tests do not depend on the machine, unless `SessionConfig::plugin_dirs` points it at the fixtures.

## Scanning and the catalog

* **Only on demand, in a separate process.** Plugins are NOT searched for or loaded at startup: a third-party plugin may crash while loading, and startup must be fast and safe. "Settings" → "Plugins" → "Scan" (`ui/settings/PluginsSection.tsx`) → `actions.plugins.scan` → RPC `plugins.scan` → `PluginScanner::scan`; the UI then re-reads the catalog (`refreshCatalog`).
* **The helper `daw-plugin-scan`** (`src/bin/daw_plugin_scan.rs` → `isolated.rs: helper_main`, the same `Vst3Scanner::scan_bundle`) loads one bundle per process, killed after `SCAN_TIMEOUT`. Any helper failure becomes a `failed` entry (also logged, source `vst3`) and the other bundles are still scanned. The answer goes through a file, not stdout, because plugins print their own garbage there; the helper's log entries are copied into the app log. Protocol: top of `isolated.rs`.
* **Where the helper lives.** Next to the app executable: `SazDAW.app/Contents/MacOS` (put there by `scripts/make-dmg.sh`) or `target/debug|release`; `tauri dev`/`tauri build` build it via `beforeDevCommand`/`beforeBuildCommand` in `tauri.conf.json`. Missing helper → `scan` fails with `SCAN_HELPER_MISSING` and changes nothing. We do not use Tauri's `externalBin`: it needs the target-suffixed file already when `daw-desktop` is built, which would break the workspace's `cargo build`/`cargo test` unless the helper was built first. In-process loading (`Vst3Plugins` without `with_scan_helper`) is for tests only.
* **The `plugins.json` cache** goes through `PluginCacheStore` (`PluginCacheFile` in `daw-persistence`): only `daw-vst3` knows the document format, only `daw-persistence` knows the state paths. At startup `Vst3Plugins::load_cached` fills the catalog without opening any plugin file.
* **Lazy loading.** Factories and `PluginSource` (`source.rs`, shared with plugin windows) open the bundle on the first `create` and keep it loaded until the app exits: unloading and reloading foreign libraries is riskier than a few megabytes. A plugin removed after the scan fails `create` with a clear error and a log entry.
* **Replacing the set on the fly.** The registries (`daw-catalog`) keep factories in groups under a `RwLock`; `Vst3Plugins` replaces the whole `vst3` group through `EffectGroups::replace_group`/`InstrumentGroups::replace_group`. Effects already created in projects are not affected. Only the command thread and export read the catalog, never the audio thread, so the lock is safe. A rescan reuses the `PluginSource` of an unchanged plugin (`catalog.rs: factories_of`): the bundle is not reloaded and the `&'static str` strings the contract requires leak only once (`text.rs: leak`).
* **Effect or instrument**: `scanner.rs: plugin_kind`. **Installed list**: `PluginScanner::installed()` from `PluginDirectory`, without loading plugins; RPC `plugins.list` (`daw-rpc/src/plugins.rs`).

## Parameters: real units outward

A VST3 plugin understands only normalized 0…1 values; outward (catalog, project, UI, RPC) its parameters are `p<id>` in real units, like built-in effects. `p<id>` is built and parsed only in `param_name.rs`.

* **Shape** (switch / number / choice) is decided once during the scan (`instance/params.rs`, pure logic in `instance/display.rs`) and cached as `ParamDesc`. The real values are the numbers the plugin *displays*, not the VST3 "plain" value, which often differs (nih-plug, JUCE); why and when the plugin's own conversion wins: top of `instance/display.rs`.
* **Conversion** (`scale.rs: ParamScales`) is a per-instance table built on the control side with the same `read_parameters` as the scan, so it matches the catalog. The audio thread cannot call the controller, so `set_param` only looks the id up (no allocations) and queues the normalized value. The plugin window's `ParamBridge` converts back with its own instance's table.
* **Users of the values.** `ParamInfo::fit` validates project values (a choice is an integer index). Choice automation is interpolated as a number, the plugin gets the nearest step, the UI places points only on integers (`domain/automation.ts`, `Range.whole`). UI: `ui/common/ParamControl.tsx` (a choice as a list, a number as a knob; `domain/knob.ts` goes logarithmic for wide ranges).
* **Limit `MAX_EXPOSED_PARAMS`.** Only the first eligible parameters (not hidden, read-only, program-change or bypass) go to the contract, UI and cache: synths have thousands (Surge XT) and nobody needs such a list. The full count is `PluginInfo.params_total`; the rest exist only in the plugin window and the plugin state.

## Audio

* **Queues, not calls.** `set_param` and note calls only write into fixed-capacity queues (`pending.rs`, `notes.rs`); the next `process`/`render` hands them to the plugin (`IParameterChanges`/`IEventList`, offset 0). `PendingChanges` holds `MAX_EXPOSED_PARAMS` entries because all project parameters go to the plugin in the first block. `ProcessRunner` (`runner.rs`) preallocates everything; blocks over `MAX_FRAMES` go in chunks.
* **Instruments** (`instrument.rs`): "no inputs, stereo main output" (`instance/layout.rs`, reapplied on every start because plugins may forget it). The host tracks sounding notes with their `noteId`s; on overflow a `NoteOn` is dropped but a `NoteOff` is retried later — a stuck note is worse than a lost one. The result is **added** to the block; a block with `NaN`/`inf` becomes silence. MIDI controllers are parameter changes the plugin names through `IMidiMapping` (`midi_map.rs`, `instance/midi.rs`): see [midi-controllers](../../docs/features/midi-controllers.md).
* **Failures.** A plugin that fails to load during a scan or creation is logged (source `vst3`) and skipped or refused (`LOAD_FAILED`); the scan does not fail. Audio-thread failures (refused block, queue overflow, unmapped controller) cannot be logged there: `BlockFaults` (`faults.rs`) counts them and logs on the control side, on the next `prepare` and on destruction. The engine destroys effects (including `terminate`) on the control side through its garbage queue, never on the audio thread.

## Crash protection

On macOS a plugin window cannot be embedded from another process (`NSView` does not cross process boundaries), so plugins run inside the app process and a crash in `process` brings the app down. The protection (like Reaper's, but without moving the plugin out of process) only names the culprit and lets the user disable it.

* **The "who is processing" marker** (`guard/`: `map.rs` file layout, `marker.rs` slots, `mod.rs` `Vst3CrashGuard`). `<state folder>/plugin-guard.bin` is memory-mapped: marking is one atomic store on the audio thread (no allocations, locks or system calls), and the pages survive a crash in the kernel cache. Each catalog instance gets a slot on creation (`CatalogEntry::create_with` → `PluginInstance::watch`), and creation itself runs marked; `PluginInstance::guarded` marks `prepare` and `process`/`render`, and its `Drop` marks termination. Plugin-window instances have no slot. Leaving clears only its own mark (`compare_exchange`), so export on another thread does not interfere. No free slot or no file → plugins run unmarked, reason logged.
* **Report on the next launch.** `PluginCrashGuard` (`daw-contracts/src/plugin_crash.rs`, `Controls.plugin_crash`): a crash = the "session running" flag was not cleared while someone was processing. The report names the plugin, the last recent project and where the plugin sits in it (the file is read through `ProjectStorage`, not opened). The roots (`app/src-tauri` on `RunEvent::Exit`, `daw-app`, `daw-mcp`) call `end_session` on a normal exit. After a crash `Startup::open` (`daw-bootstrap/src/lib.rs`) does NOT open the last project: the same plugin would crash the app again before it could be disabled. RPC `plugins.lastCrash`, `plugins.dismissCrash`. UI: `actions/startup.ts: afterFirstRead` → `actions.plugins.offerCrashReport` asks in a system dialog whether to disable the plugin (`domain/plugins.ts: crashQuestion`), then dismisses the report; the autosave restore offer comes after. Mock: open the page with `?pluginCrash` (`mock/handlers/plugins.ts`).
* **Disabling a plugin.** `PluginScanner::set_disabled`, RPC `plugins.setDisabled`; the list is `Preferences::disabled_plugins`, changed only by `set_disabled`, which rebuilds the catalog at once. The factory stays in the catalog, hidden (`EffectFactory::listed`/`InstrumentFactory::listed` = `false`, so `daw-catalog` leaves it out of `kinds()`), and `create` refuses with `DISABLED`. A project using it opens without that instrument (silent track) or effect (the node does no processing), with a message in `project.takeWarnings`; existing instances keep working until the project is reopened. UI: "Settings" → "Plugins" ("Disabled" toggle, "failed" marks from the last scan); `actions.plugins.setDisabled` re-reads the catalog and the preferences so the next `preferences.set` does not bring the old list back.
* **Limits (honestly).** It is a guess from the marker, not isolation:
  * a crash on another thread (plugin window, our code, the plugin's own thread) while the audio thread is inside a plugin is blamed on that plugin;
  * a crash in the plugin window (main thread) or in the plugin's own threads outside `process` is not caught at all;
  * a plugin hanging in `process` is not detected (only if the user kills the app does the marker point at it);
  * one marker per state folder: two apps running at once with the same state folder confuse the report;
  * signals (`SIGSEGV`) are not intercepted: recovering from memory corruption caused by foreign code is impossible. Panics in our own code already go to the log (`install_panic_hook`);
  * a plugin that crashed while loading during a scan never gets into the catalog, so it needs no disabling.

## Plugin state (presets)

* **Contract**: `PluginState` and `PluginStates` (`daw-contracts/src/plugin_state.rs`) — opaque bytes from the component's and controller's `getState`, kept in `InstrumentSpec::state` / `NodeKind::Effect::state`.
* **On creation** `CatalogEntry::create_with` applies the state on the control side (`instance/state.rs`, byte stream `stream.rs`), and the project params go on top in the first block. A rejected state is logged and the instance is still created: the project must open. Built-in kinds ignore state.
* **A new state recreates the sounding instance.** `ProjectPluginStates` (`daw-project/src/plugin_states.rs`) implements `PluginStates`; DSP sync (`daw-project/src/service/sync.rs`) keeps the state in `InstrumentKey`/`EffectKey`, because state cannot be handed to a live instance from the audio thread. Parameter changes still go through `set_param`; undo restores by the same recreation.
* **State comes only from the plugin window** (see "Plugin windows"): without a window there is nowhere for a new state to come from.
* **`project.get` returns the project without states** (`daw-rpc/src/project.rs: without_plugin_states`) for RPC, UI and AI: they are bytes for plugins, and `project.get` runs after every edit. The project file keeps them; the frontend and the mock know nothing about state.

## Transport time (`ProcessContext`)

The engine calls `Instrument::set_timing`/`Effect::set_timing(&BlockTiming)` before each segment (`daw-engine/src/engine.rs: process_segment`); `PluginClock` (`context.rs`, no allocations) fills a preallocated `ProcessContext` before each `process`. Decisions: `projectTimeSamples` is an approximation from the segment tempo (plugins sync to `projectTimeMusic`); the position is the transport (source) position, **not** shifted by PDC, so instrument plugins stay in time with the notes and an effect after a delayed path gets the sources' position. Without the engine (drum part preview, tests) only continuous time is valid.

## Current limitations

macOS only; plugin windows — see their section; additional output buses are not used; no sidechain; export runs in `kRealtime` mode (`instance/mod.rs: PROCESS_MODE`; `kOffline` would need a new `StreamConfig` field at every place one is created — not done, it does not affect the sound of most plugins); `ProcessContext` has no system time, SMPTE or chords; a plugin that crashes in `process` still brings the app down (the protection only finds and disables it).

## How to add a similar one

A new plugin format (CLAP) is a separate crate following the same pattern: scanner + `EffectFactory` + `Effect`, assembled in `daw-bootstrap`.

## Plugin windows (native VST3 UI)

Contract `PluginEditors` (`daw-contracts/src/plugin_editor.rs`), implementation `Vst3Editors` (`editors.rs`), app windows `app/src-tauri/src/plugin_window.rs`. Target: `EditorTarget::Effect { node } | Instrument { track }`.

* **A separate instance for the window.** `open` creates a NEW instance (`editor.rs: Editor`) only for the UI; audio goes through the engine's instance, and neither it nor the project knows about the window. No native view (`createView` returns null) or a built-in kind is an error (a toast in the UI; the parameters stay knobs). The plugin is found by kind through `PluginDirectory`, sharing `PluginSource` with the factories (the bundle loads once).
* **Order.** `open` → the app creates the window → `attach(id, NSView)` → `sync` on a timer → `resize` → `close`. One window per target: a second `open` fails (`EDITOR_ALREADY_OPEN`), the app raises the existing window instead.
* **Window → project ("ask, don't walk into someone else's office").** The window's `IComponentHandler` (`editor_host.rs: EditHandler`) forwards edits to `ParamBridge` (`param_bridge.rs`, pure logic), which writes real values only through contracts: `GraphControl::set_effect_param` / `TrackControl::set_instrument_param` (`project_params.rs`). So a window edit is heard, saved and undoable. A `beginEdit`…`endEdit` gesture is one undo step (`HistoryControl::begin_group/end_group`; closed forcibly when the window closes). Writes are rate-limited (`MIN_WRITE_INTERVAL`) without losing the last value. Parameters beyond `MAX_EXPOSED_PARAMS` travel only in the plugin state (one log entry per window).
* **Project → window (`sync`, ~100 ms, main thread).** Changed project values go into the window's controller, so it follows automation and other panels; a held knob and unwritten values are not overwritten. A target gone from the project makes `sync` fail, and the app closes the window. A plugin's resize request (`IPlugFrame::resizeView`) is returned from `sync`, so the window resizes on the next tick, without callbacks from foreign code.
* **Window state ↔ project** (`editors.rs` + pure `editor_state.rs: StateSync` + `PluginStates`). The user picks presets in the window's instance, so its whole state is carried over. On open the window loads the saved state, then the project params. Knobs the project knows do NOT write state (recreation on every move would interrupt the sound); other changes (`restartComponent`, unknown parameters) write it after `SETTLE` of quiet, if it differs from the last agreed one — one "Plugin state" undo step and a recreation. It is also written on window close and in `store_states`: the `PluginStateFlush` contract, implemented by the app's `PluginWindows` on the main thread and called by the RPC table before every method registered with `add_flushing` (save, render, export…), whether the call came from the window or the in-app AI server. Undo/redo of a state is picked up on `sync` (`StateSync::outside`). Failures go to the `vst3` log; a deleted target is not a failure. Autosave does not poll windows: changes reach the project within a second.
* **Threads.** EVERYTHING that touches the plugin or the window runs on the MAIN thread (`AppHandle::run_on_main_thread`); the timer thread only asks the main thread to tick while windows are open. `Vst3Editors` is `Send`/`Sync` only for the trait; safety relies on "call from the main thread". Dropped on another thread, it deliberately leaks open windows with a log entry — better than undefined behaviour.
* **The app window** is a `tauri::window::WindowBuilder` with no web page (the `unstable` feature of `tauri`); the plugin's parent is `Window::ns_view()`. The host makes no AppKit calls itself, so `app/src-tauri` needs no `unsafe` (the workspace's `unsafe_code = "forbid"` would not allow a targeted `allow` anyway). `close(id)` runs before the `NSWindow` is destroyed; closing the main window or ⌘Q closes all plugin windows first, and closing the main window quits the app.
* **The only exception to "everything through `daw-rpc`".** `pluginEditor.open` is handled by name in the app's `rpc` command (`app/src-tauri/src/main.rs`) BEFORE the shared table: the window needs Tauri's `AppHandle`, and `daw-rpc` intentionally knows nothing about Tauri. Frontend: `api.pluginEditor.open` → `actions/pluginEditor.ts` (errors as a toast) → the "Plugin window" button in `ui/effects/EffectPanel.tsx` and `ui/tracks/InstrumentWindow.tsx`, only for `vst3:…` kinds (`domain/plugins.ts: isPluginKind`); the browser mock (`mock/handlers/plugins.ts`) answers with an error.
* **Keys in the instrument window** (`keys/`). A plugin window has no web page, so the main window's hotkeys (`state/keyboardPiano.ts`) do nothing there. On `attach` of an instrument window `EditorKeys` installs a local `NSEvent` monitor (only our own app's events, so no input permissions) and `KeyPlayer` plays on that track through `LiveNoteSink`. The layout matches `app/src/domain/keyboard.ts` but by macOS key codes: **when changing the layout in one place, update the other**. Plugin windows have their own octave; closing a window releases its notes. Other platforms do not intercept window keys yet.
* **Limitations.** A new window state reaches the sound by recreating the instance (a second after a preset change, on window close, before saving), cutting off sounding notes. A plugin that changes its state without `restartComponent` and without touching parameters reaches the project only on window close or save. With a separate controller, the window's component does not process audio and may miss edits from the window — the project parameters on top of the state carry them. Not supported: window hotkeys, `IPlugViewContentScaleSupport`, `IComponentHandler2/3`, `IContextMenu`, `checkSizeConstraint`, several windows per target. A plugin crashing in its window brings the app down.

## Tests

* Unit tests cover the pure parts (`ParamBridge` with stub `GraphControl`/`TrackControl`/`HistoryControl`, `StateSync`, `MemoryStream`, `PluginClock`, `NoteQueue`, `KeyPlayer`) and the window's COM objects. Integration tests are one test program, `tests/all/`: scan, sound, state, windows (created and closed without showing), the isolated scan, on the fixtures and on Surge XT if installed. Elsewhere: `daw-project/src/tests/plugin_states.rs` (the `PluginStates` contract), `daw-bootstrap/tests/all/plugin_state.rs` (window → state → file → open → undo), `daw-engine/src/tests/timing.rs` (segment timing).
* Embedding into a real `NSView`, the Tauri window, dragging, input and focus are checked by the owner by hand: CI runners have no GPU for OpenGL interfaces, so there is no such test.
* **Test plugins (dev-only fixtures).** `test-plugins/synth` (`Synth.vst3`, kind `vst3:synth` once scanned) and `test-plugins/distortion` are nih-plug plugins with native windows (separate workspaces, GPL) that exist only to test this host: `crates/daw-vst3/tests`, `daw-bootstrap/tests` (`start_with_fixture_plugins`: a headless session with `SessionConfig::plugin_dirs` → `test-plugins/*/target/bundled`, scanned in-process) and `daw-rpc/tests/all/settings.rs`. Build them with `scripts/build-test-plugins.sh`; without the bundles those tests print `SKIPPED` and pass. They are not shipped and the app never loads them: the DAW's instruments and effects are built in (the owner's rule: never VST3 plugins of our own).
