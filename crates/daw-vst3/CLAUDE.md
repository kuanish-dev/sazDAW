# `daw-vst3`

**Host for VST3 effects and instruments** — the only crate with `unsafe`: `Vst3Plugins` (`PluginScanner`: scan on button press + cache), `Vst3Scanner` ("find VST3 plugins in folders"), `Vst3EffectFactory`/`Vst3Effect` (`EffectFactory`/`Effect`), `Vst3InstrumentFactory`/`Vst3Instrument` (`InstrumentFactory`/`Instrument`), `Vst3Editors` (`PluginEditors`: native plugin windows; window state goes into the project via `PluginStates`), `Vst3CrashGuard` (`PluginCrashGuard`: report on a plugin crash) and the scan helper `daw-plugin-scan` (the crate's binary: one bundle in a separate process).

Depends on: contracts.

Map of the whole code: [ARCHITECTURE.md](../../ARCHITECTURE.md). Cross-layer features it takes part in: [midi-controllers](../../docs/features/midi-controllers.md).

## VST3 (`daw-vst3`)

This crate turns installed VST3 effects and instruments into ordinary catalog kinds: effects like `vst3:distortion` go into `EffectRegistry`, instruments like `vst3:surge_xt` go into `InstrumentRegistry`, next to the built-in ones, and the rest of the application knows nothing about VST3. The only entry point is `Vst3Plugins` (implements the `PluginScanner` contract, lives in `Controls.plugins`); only `daw-bootstrap` (`plugins.rs`) builds it. The test `build_session` uses an empty scanner (`found: 0`) so tests do not depend on the machine.

* **List of installed plugins.** `PluginScanner::installed()` returns the plugins currently in the catalogs (`InstalledPlugin { kind, name, vendor, path, type, params, paramsTotal, disabled }`); it is built from the `PluginDirectory` (the same kinds as in the catalog) without loading plugins. Order: instruments, then effects, by name. `folders()` is where `scan` looks (`VST3_DIRS`; empty in the test session). RPC `plugins.list` → `{ folders, plugins }` (`daw-rpc/src/plugins.rs`).
* **Scanning happens only on demand and in a separate process.** Plugins are NOT searched for or loaded at startup: a third-party plugin may crash while loading, and startup must be fast and safe. "Project" → "Scan plugins" → action `plugins.scan` → RPC `plugins.scan` → `PluginScanner::scan`. The response is `{ found, effects, instruments, failed: [{ path, reason }] }` (`found` is the total); a failure of an individual plugin goes both into the response and into the log (`source: "vst3"`), and the scan continues. After the scan the UI re-reads the catalog (`refreshCatalog`). Each bundle is loaded by the **helper** `daw-plugin-scan` (a `[[bin]]` of the `daw-vst3` crate: `src/bin/daw_plugin_scan.rs` → `isolated.rs: helper_main`, the same `Vst3Scanner::scan_bundle`), one process per bundle, with a `SCAN_TIMEOUT` of 20 s (`isolated.rs: IsolatedScan`). Protocol: `daw-plugin-scan <bundle> <response file>`; the response is JSON `{ outcome: { plugins, failed }, journal }` in a file (not on stdout: plugins print their own garbage there; the helper's output is discarded), and the application copies the helper's log entries into its own log. A signal → a `failed` entry "plugin crashed while loading (signal 11, SIGSEGV)", a timeout → "plugin did not respond within 20 s (hung while loading)" (the process is killed); any other exit code or an unparseable response also becomes a `failed` entry; the remaining bundles are still scanned. Where the helper lives: next to the application executable (`daw-bootstrap/src/plugins.rs: scan_helper`): `SazDAW.app/Contents/MacOS` (put there by `scripts/make-dmg.sh`; `npx tauri build`/`tauri dev` build it themselves via `beforeBuildCommand`/`beforeDevCommand` in `tauri.conf.json`), during development `target/debug|release` (for cargo tests, one folder above `deps`). If the helper is missing, `scan` returns an error saying the plugin scan helper was not found and how to build it (`cargo build -p daw-vst3 --bin daw-plugin-scan`), and changes nothing. We do not use Tauri's `externalBin`: it requires a file with the target-platform suffix already when building `daw-desktop`, and would break the workspace's `cargo build`/`cargo test` unless the helper was built first. In-process loading remains only for tests (`Vst3Plugins` without `with_scan_helper`, e.g. a headless session scanning the `test-plugins/` fixtures).
* **The `plugins.json` cache.** After a scan, the list of `PluginInfo` (bundle path, class id, name, vendor, parameters) is written to `<state folder>/plugins.json` through the `PluginCacheStore` contract (implementation `PluginCacheFile` in `daw-persistence`; the write is atomic: temporary file + rename). Only `daw-vst3` knows the document format, and only `daw-persistence` knows the state paths. At startup `Vst3Plugins::load_cached` restores factories from the cache; no file means no plugins; a corrupted file means a log entry and "no plugins".
* **Lazy loading.** A `Vst3EffectFactory` is created without touching the plugin file: the bundle is opened on the first `create`. If the file is gone (the plugin was removed after the scan), `create` returns an error (the plugin file is missing from disk; rescan plugins) and writes to the log.
* **Replacing the set on the fly.** Both registries (`EffectRegistry`, `InstrumentRegistry`) store factories in groups under a `RwLock`: the built-in ones are assembled at startup, and the `vst3` group is replaced as a whole through the `EffectGroups::replace_group` and `InstrumentGroups::replace_group` contracts (called by `Vst3Plugins`, which knows only the trait). A repeated scan replaces the previous set; effects already created in projects are not affected. The catalog is read by the command thread and by export; the audio thread does not touch it, so the lock is safe; `create` is called after the lock is released. A repeated scan reuses a plugin's `PluginSource` if its `PluginInfo` has not changed (`catalog.rs: factories_of`): the bundle is not reloaded, and parameter strings (the contract's `&'static str`) "leak" once per source. The effect and instrument factories and their shared part (`CatalogEntry`) also live in `catalog.rs`.
* **Where we look.** The `VST3_DIRS` constant in `daw-bootstrap/src/plugins.rs`: `/Library/Audio/Plug-Ins/VST3` and `~/Library/Audio/Plug-Ins/VST3` (`*.vst3` bundles, up to two levels deep). An effect is an "Audio Module Class" class with the `Fx` subcategory, an instrument one with the `Instrument` subcategory (`Instrument|Synth` etc.); if both are present, the plugin is treated as an effect; everything else (analyzers…) is skipped. The type is stored in `PluginInfo.kind` (and in `plugins.json`).
* **Loading a bundle (macOS).** `CFBundle` from the path → executable from `Info.plist` → `dlopen` (libloading) → `bundleEntry(CFBundleRef)` → `GetPluginFactory`; at the end the factory is released, then `bundleExit`, then the library is closed. An effect factory keeps the bundle loaded until the application exits.
* **Parameters → contract: real units.** A VST3 plugin understands only normalized values 0…1, but outward (catalog, project, UI, RPC/model) a parameter is exposed in real units, like built-in effects: `ParamInfo { name: "p<id>", label: "Cutoff, Hz", min: 40, max: 18000, default: …, kind, choices }`. How it is determined (during the scan, `instance/params.rs` + pure logic in `instance/display.rs`, the result is `ParamDesc` in the cache):
  * `stepCount == 1` → `Switch` (0/1);
  * `stepCount` 2…256 → step texts from `getParamStringByValue`: if all are numbers ("-2", "12 st") → `Number`, and the step values are those numbers; if there are names ("Sine", "1/4") → `ParamKind::Choice`, `choices` are the names, and the value is the option index 0…n-1;
  * everything else (a continuous parameter, more than 256 steps) → `Number` along a 129-point curve. The **numbers the plugin displays** are taken as the real values: the plugin's own conversion `normalizedParamToPlain` is used if it matches the plugin's text up to rounding (it is more precise than the text), otherwise the numbers from the text (nih-plug stores gain as a ratio but displays dB; a fraction is 0…1 but displayed as a percentage; in JUCE "plain" = normalized); if the text is not a number or is non-monotonic, the plugin's conversion is used with no units in the label. Units come from `ParameterInfo.units` or the tail of the text ("Hz" in "440 Hz"), shown in the label after a comma (numbers only).

  **Value conversion (`scale.rs`: `ParamScale`, `ParamScales`).** The "real ↔ normalized" table is built when an instance is created, on the control side (with the same `read_parameters` as during the scan, so it matches the catalog): a straight line by two points (arithmetic), a curve by 129 points with inverse linear interpolation, steps by an exact table (nearest step). A non-monotonic/flat curve gets no conversion (0…1). An effect's and instrument's `set_param` is called from the audio thread: it only looks up the id in the table (binary search, no allocations or controller calls) and writes the normalized value into a queue; out-of-range values are clamped. The reverse direction (plugin window → project) is converted by `ParamBridge` using the window instance's table. Projects with old normalized values are not converted (rule 10). Contract: `ParamInfo::fit` (limits; for a choice, an integer index) — the project uses it to validate parameter values; the engine interpolates choice automation as a number, the plugin receives the nearest step, and the UI places points only on integers (`domain/automation.ts`, `Range.whole`). UI: `ui/common/ParamControl.tsx` (node inspector and instrument window) shows a `choice` as a list of options and numbers as a knob (`domain/knob.ts`: ranges with a wide spread such as 40…18000 Hz use a logarithmic scale).

  Hidden and read-only parameters, program switches, and bypass are not included in the list. The `p<id>` name is built and parsed only by `param_name.rs`. **Limit: only the first `MAX_EXPOSED_PARAMS` = 128 eligible parameters, in the plugin's order, are exposed outward (to the contract, UI, cache)**: synthesizers have thousands (Surge XT has 2854), and nobody needs such a list; the full count is stored in `PluginInfo.params_total`. Strings for `&'static str` are intentionally "leaked" when the list is built (at startup from the cache and on each scan).
* **Audio.** `set_param` only converts the value to normalized (`ParamScales`) and writes it into a queue for up to `MAX_EXPOSED_PARAMS` = 128 distinct parameters (`pending.rs`; as many as can come from the project on creation); at the start of the next `process` the values are passed to the plugin through the host's `IParameterChanges` (position 0 frames). `ProcessRunner` pre-creates planar buffers (8192 frames), `ProcessData`, and queues; nothing is allocated in `process`, and blocks larger than 8192 frames are processed in chunks. Latency is `getLatencySamples` after startup.
* **Failures.** A plugin that failed to load during a scan or creation is logged (`source: "vst3"`) and skipped/rejected; the scan does not fail. A plugin that crashes the process while loading only crashes the scan helper (see above). The engine destroys effects (including `terminate`) on the control side through the "garbage" queue (`Garbage`), not on the audio thread. Failures on the audio thread (a block not processed, a parameter or note did not fit in the queue) cannot be logged from there, so they are accumulated in `BlockFaults` counters (`faults.rs`) and logged on the control side: on the next `prepare` and on destruction. Plugin windows may only be closed on the main thread: if `Vst3Editors` is destroyed on another thread, open windows are intentionally "leaked" with a log entry — this is better than undefined behavior.
* **Crash protection (like Reaper, but without moving the plugin into another process).** On macOS a plugin window cannot be embedded from another process (`NSView` does not cross process boundaries), so plugins run inside the application process, and a crash in `process` brings down the application. The protection does two things: it identifies the culprit and lets you disable it:
  * **The "who is processing" marker** (`guard/`: `map.rs` — `GuardMap`, `marker.rs` — `ProcessMarker`/`GuardSlot`, `mod.rs` — `Vst3CrashGuard`). The file `<state folder>/plugin-guard.bin` (`GUARD_FILE` in `daw-bootstrap/src/plugins.rs`) is memory-mapped (`memmap2`, shared; the layout is described at the top of `map.rs`): a signature, a "session running" flag, the index of the slot "currently processing", and 256 "kind + plugin name" slots. A plugin instance from the catalog gets a slot on creation (`catalog.rs: CatalogEntry::create_with` → `PluginInstance::watch`; the signature is written on the control side), and `PluginInstance::guarded` marks "processing" around `process`/`render` (`Vst3Effect`, `Vst3Instrument`), `prepare` (startup), and instance creation and termination. On the audio thread this is a single atomic store into mapped memory: no allocations, locks, or system calls; the pages survive a process crash in the kernel cache. Leaving processing clears only its own mark (`compare_exchange`: export on another thread does not interfere). If there is no free slot or the file could not be opened, plugins run without a marker, and the reason is logged.
  * **Report on the next launch.** The `PluginCrashGuard` contract (`daw-contracts/src/plugin_crash.rs`, `Controls.plugin_crash`): `last_crash() -> Option<PluginCrash { kind, name, project, places }>`, `dismiss()`, `end_session()`. A crash = the "session running" flag was not cleared and someone was processing. `project` is the most recent project from the recent list, `places` is where the plugin sits in it ("track "Bass"", "effect "…""; the file is read through `ProjectStorage`, the project is not opened). The roots (`app/src-tauri` on `RunEvent::Exit`, `daw-app`, `daw-mcp`) call `end_session` on a normal exit. After a crash `Startup::open` does NOT open the last project (otherwise the same plugin would crash the application again before you could disable it) — a `startup` log entry. RPC: `plugins.lastCrash` → `PluginCrash | null`, `plugins.dismissCrash`. UI: once ready, `actions.plugins.offerCrashReport` (`App.tsx`) asks in a system dialog "Last time the application crashed in plugin X (track Y)… Disable the plugin?" [Disable]/[Keep] (text: `domain/plugins.ts: crashQuestion`, button labels: `SystemDialogs.confirm(…, buttons)`), then dismisses the report; after that comes the usual autosave restore offer. In the browser (mock) the dialog is checked with a `?pluginCrash` URL.
  * **Disabling a plugin.** `PluginScanner::set_disabled(kind, disabled)`, RPC `plugins.setDisabled { kind, disabled }`; the list is `Preferences::disabled_plugins` (JSON `disabledPlugins`, empty by default; changed only by `set_disabled`, which immediately rebuilds the catalog). The factory of a disabled plugin stays in the catalog, hidden: `EffectFactory::listed`/`InstrumentFactory::listed` = `false`, the registries (`daw-catalog`) do not return it from `kinds()`, and `create` returns `Unsupported` (the plugin is disabled, after a crash or manually; re-enable it in "Settings" → "Plugins") — and the project opens without that instrument (the track is silent) or effect (the node does no processing), with this message in `project.takeWarnings`. Already created instances keep working until the project is reopened. `plugins.list` returns `disabled: bool`; "Settings" → "Plugins" has a "Disabled" toggle in the table and "failed" marks on plugins that failed to load during the scan (`actions.plugins.setDisabled` re-reads the catalog and the settings, so that the next `preferences.set` does not bring back the old list).
  * **Limits (honestly).** This is a guess based on the marker, not isolation: a crash on another thread (the plugin window, our code, the plugin's own thread) at the moment the audio thread is inside the plugin will be blamed on the plugin; a crash in the plugin window (main thread) or in the plugin's own threads outside `process` is not caught at all; a plugin hanging in `process` is not detected (only if the user kills the application — then the marker will point at the plugin). One marker per state folder: two applications running at the same time with the same state folder will confuse the report (the second overwrites the first's file). Signals (`SIGSEGV`) are not intercepted: recovering from memory corruption caused by foreign code is impossible, so the application crashes as before. Panics in our own code already go to the log (`install_panic_hook`). A plugin that crashed while loading during a scan does not need to be disabled: it never gets into the catalog.
* **How to add something similar.** A new plugin format (CLAP) is a separate crate following the same pattern: scanner + `EffectFactory` + `Effect`, assembled in `daw-bootstrap`.
* **Instruments (VSTi).** `Vst3Instrument` is an `Instrument`: `prepare` sets the arrangement "no inputs, stereo main output" (`setBusArrangements`, checked with `getBusArrangement`); only the first output bus is active, the others and all input buses are disabled; 32-bit samples. `note_on/note_off/all_notes_off` do not touch the plugin: they write events into a `NoteQueue` (`notes.rs`, 256 events, pure code with tests; on overflow a `NoteOn` is dropped, while a `NoteOff` that did not fit is retried on the next `note_off`/`all_notes_off` — a stuck note is worse than a lost one). The host itself tracks sounding notes and gives each a unique `noteId`; a `NoteOff` carries the same `noteId`, and `all_notes_off` turns off all sounding notes. In `render` the events are passed to the plugin through the host's COM object `IEventList` (`host_events.rs`, channel 0, offset 0), the plugin renders into preallocated planar buffers (`ProcessRunner::render_add`, blocks larger than 8192 frames in chunks), and the result is **added** to the block. A block containing `NaN`/`inf` is discarded entirely (silence). `set_param` uses the same change queue as an effect. Factory: kind `vst3:<name>`, label "<name> (VST3)", parameters `p<id>`, `rebuild_on` empty. Lazy bundle loading and instance creation are shared with effects (`source.rs`).
* **Plugin state (preset).** The contract is `PluginState { component, controller }` and `PluginStates` (`daw-contracts/src/plugin_state.rs`): opaque bytes from `IComponent::getState` and `IEditController::getState`; in the model they are `InstrumentSpec::state` and `NodeKind::Effect::state` (`Option<Arc<PluginState>>`, `#[serde(default)]`, base64 in JSON, an empty `controller` and `None` are not written; Surge XT is ~50 KB, a third more in base64 — fine for a project JSON; `Arc` so that the undo history and engine snapshots do not copy the bytes). Factories and catalogs receive the state in `create(params, state)`: `CatalogEntry::create_with` applies it to the new instance on the control side (`instance/state.rs`: the component's `setState`, then the controller's `setComponentState` and `setState`; the byte stream is `stream.rs`, `MemoryStream: IBStream`), and the project parameters are applied on top (in the first block). If the plugin rejects the state, the instance is still created with the parameters, and the rejection is logged (`vst3`). Built-in kinds do not use state. The `PluginStates` implementation is `ProjectPluginStates` (`daw-project/src/plugin_states.rs`): `set` is one undo step "Plugin state" (the same state does nothing); DSP reconciliation (`service/sync.rs`) keeps the state in the instrument and effect key (`InstrumentKey`, `EffectKey`), so a new state **recreates** the sounding instance (it cannot be passed to a live instance from the audio thread), while parameter changes still go through `set_param`. Undo restores the previous state by the same recreation. Changing an instrument's kind discards the state (the same kind keeps it). State comes only from the plugin window (see "Plugin windows"): without a window there is nowhere for a new state to come from. `project.get` (RPC, UI, and AI) returns the project **without** states (`daw-rpc/src/project.rs: without_plugin_states`): these are bytes for plugins, and `project.get` is called after every edit; the project file does contain them. The frontend and the mock know nothing about state.
* **Transport time (`ProcessContext`).** Contract: `Instrument::set_timing` / `Effect::set_timing(&BlockTiming)` (no-op by default); the engine calls them on all instruments and effects before playing each segment (`engine.rs: process_segment` → `InstrumentRack::set_timing`, `GraphMixer::set_timing`). `BlockTiming::loop_region` is the transport loop, if it is enabled and playback is running. A VST3 effect and instrument hold a `PluginClock` (`context.rs`, pure code without allocations): before each `process` a preallocated `ProcessContext` is filled in (`ProcessRunner`, `ProcessData::processContext`): `kPlaying`, tempo, time signature, `projectTimeMusic` (quarter notes = ticks / PPQ), `barPositionMusic` (start of the current bar, from the segment's time-signature change, `BlockTiming::bar_start`), `projectTimeSamples` (ticks / ticks per frame of the segment — an approximation: with tempo changes it differs from the exact frame count; plugins sync to `projectTimeMusic`), `continousTimeSamples`, the loop (`kCycleActive|kCycleValid`, start and end in quarter notes). An instrument plays a segment in chunks between notes, and the position advances by the frames played. The position is the transport (source) position, **not** shifted by PDC: instrument plugins stay in time with the notes; an effect after a delayed path receives the same position as the sources (ahead by the amount of its input's compensation). Without the engine (drum part preview, tests) only continuous time is valid.
* **Current limitations.** macOS only; plugin windows — see the section below; an instrument receives only `NoteOn`/`NoteOff` (no pitch bend, controllers, aftertouch); additional output buses are not used; no sidechain; export runs in `kRealtime` mode (switching the plugin to `kOffline` would require a new `StreamConfig` field at every place it is created — not done; it does not affect the sound of most plugins); `ProcessContext` has no system time, SMPTE, or chords; a plugin that crashes in `process` still brings down the application — the protection only helps find and disable the culprit (see "Crash protection").

### Plugin windows (native VST3 UI)

The contract is `PluginEditors` (`daw-contracts/src/plugin_editor.rs`), the implementation is `Vst3Editors` (`daw-vst3/src/editors.rs`), and the application windows are in `app/src-tauri/src/plugin_window.rs`. A window's target is `EditorTarget::Effect { node } | Instrument { track }`.

* **A separate instance for the window.** `open` creates a NEW "component + controller" pair (`PluginInstance::create`, with an `IConnectionPoint` between them if the controller is a separate class) solely for the UI. Audio goes through the main instance in the engine; the window is a "view of the parameters". The main instance and the project know nothing about the window. The view is created with `createView("editor")`; `null` is an error (the plugin has no native window; the UI shows it as a toast, and the parameters remain knobs). A built-in effect or instrument is also an error (built-ins have no native window). The plugin is located by its catalog kind (`vst3:…`) through `PluginDirectory`: a directory of `PluginSource` shared with the factories (the bundle is loaded once); it is refreshed together with the catalog group on every scan.
* **Order.** `open` (create the view, get its size and whether it can be resized, apply the project values) → the application creates the window → `attach(id, the window's NSView)` (`IPlugView::attached`; `setFrame` is already set in `open`) → `sync` on a timer → `resize` when the window changes → `close` (`removed`, `setFrame(null)`, release the view, then the instance). One target, one window (a second `open` is `Invalid`; in that case the application raises the existing window without calling `open`).
* **Edits from the window → project ("ask, don't walk into someone else's office").** The window's host `IComponentHandler` (`editor_host.rs: EditHandler`) forwards `beginEdit/performEdit/endEdit` to `ParamBridge` (`param_bridge.rs`, pure logic without pointers), which converts the knob value into real units (`ParamScales`) and writes to the project only through contracts: `GraphControl::set_effect_param(node, "p<id>", v)` for an effect and `TrackControl::set_instrument_param(track, "p<id>", v)` for an instrument (`project_params.rs`; the plugin kind is also looked up there from the window's target). That is why a window edit is audible (the project publishes a snapshot to the engine), saved, and undoable. A gesture from `beginEdit` to `endEdit` is one undo step: `HistoryControl::begin_group/end_group` (the group is opened by the first knob and closed when all are released; when the window closes, an unclosed group is closed forcibly). Writes happen at most ~30 times per second per parameter (`MIN_WRITE_INTERVAL`); a held-back value is not lost — it is written by the `sync` tick or by `endEdit`. Parameters beyond the first `MAX_EXPOSED_PARAMS` (128) are unknown to the project: their window edits do not reach the project as parameters (one log entry per window) — they are saved in the plugin state (below). `restartComponent` with `kReloadComponent`/`kParamValuesChanged` and an edit of a parameter unknown to the project produce a "state changed" message for `StateSync`; other flags are not needed.
* **Project → window (`sync`).** About every 100 ms the main thread calls `sync(id)`: it reads the target's current values from the project and writes the changed ones into the window's controller (`setParamNormalized`) — this way the window sees automation and edits from other panels. A knob currently being held and values that have not yet reached the project are not overwritten; echoes of its own values are ignored. If the target is gone from the project (the track or effect was deleted), `sync` returns an error and the application closes the window. A plugin's request to resize (`IPlugFrame::resizeView`, `ResizeFrame`) is remembered and returned from `sync` as `Some((w, h))`: the window resizes on the next tick, without callbacks from foreign code.
* **Window state ↔ project.** The user picks a preset in the window, i.e. in the window's instance, so the window's whole state is carried to the project and back (`Vst3Editors` + pure logic in `editor_state.rs: StateSync` + the `PluginStates` contract). On opening, the window receives the target's saved state (and then the project's parameter values on top), so the window and the sound match; this is remembered as "agreed" (the window's bytes). A change message from the plugin → after `SETTLE` (1 s) of quiet, on a `sync` tick, the window state is written to the project (`PluginStates::set`: undo step "Plugin state", the sounding instance is recreated with it) if it differs from the agreed one. Knobs known to the project do NOT write state (otherwise the sound would be interrupted by recreation on every move) — they go as parameters. On window close and in `store_states` (before the project is saved or rendered: the `PluginStateFlush` contract, which `app/src-tauri`'s `PluginWindows` implements by running `store_states` on the main thread; the RPC table calls it before every method registered with `add_flushing` (save, create, preset and template save, bounce, freeze, export, level analysis, mix check), whether the call came from the window or the in-app AI server) the state is written if it differs from the agreed one (opened and closed without edits — nothing; turned some knobs — one "Plugin state" step and a recreation on close). A target state changed from outside (undo/redo) is picked up by the window on `sync` (`StateSync::outside`): it loads it (or its own initial state, if the project no longer has a state) and re-applies the project parameters (`ParamBridge::forget_shown`). Failures (the plugin did not return or did not accept the state, the write failed) go to the `vst3` log; a deleted target is not a failure. Autosave does not poll windows: changes reach the project within a second, which is enough.
* **Threads.** EVERYTHING that touches the plugin and the window (`open/attach/resize/sync/close`, creating the `NSWindow`) runs on the MAIN thread: `AppHandle::run_on_main_thread`. The window timer is a separate thread that only asks the main thread to tick while there are open windows. `Vst3Editors` keeps windows under a `Mutex` and is marked `Send`/`Sync` only for the trait; safety relies on the convention "call from the main thread". Plugin edits also arrive on the main thread and go straight to the project.
* **Application window.** It is a `tauri::window::WindowBuilder` WITHOUT a web page (requires the `unstable` feature of `tauri`): the parent for the plugin is the window's `NSView` (`Window::ns_view()`), and the host itself makes no AppKit calls, so `unsafe` was NOT needed in `app/src-tauri` (the rule "`unsafe` only in `daw-vst3`" is not violated; `workspace.lints.unsafe_code = "forbid"` would not allow a targeted `allow` anyway). The size comes from `EditorSession` (logical pixels), the title is the plugin name, resizability follows `canResize`. Closing the window → `close(id)` before the `NSWindow` is destroyed (the plugin detaches its view); user resize → `resize` (`IPlugView::onSize`); a plugin's size request → the window resizes. One window instance per target: pressing again raises the existing one. Closing the main window and quitting (⌘Q) close all plugin windows before anything else; closing the main window quits the application (as before, when it was the last one).
* **The only exception to "everything through `daw-rpc`".** The `pluginEditor.open` method (`params: { target: { type: "effect", node } | { type: "instrument", track } }` → `null` or an error) is handled by name in the application's `rpc` command (`app/src-tauri/src/main.rs`) BEFORE the shared table: the window needs Tauri's `AppHandle`, and `daw-rpc` intentionally knows nothing about Tauri (it is only JSON ↔ contracts). All other methods go through `RpcTable` unchanged. Frontend: `api.pluginEditor.open` → `actions/pluginEditor.ts` (errors shown as a toast) → the "Plugin window" button in the effect node inspector (`ui/graph/Inspector.tsx`) and in the instrument window (`ui/tracks/InstrumentWindow.tsx`), only for `vst3:…` kinds; the browser mock responds with an error (the plugin window is available only in the app, not in the browser).
* **Tests.** The "knobs ↔ project" logic (write rate, undo group, echo, `p<id>` names, stub `GraphControl`/`TrackControl`/`HistoryControl`), `StateSync`, `MemoryStream`, `PluginClock`, and the window's COM objects have unit tests in `daw-vst3`; `tests/editors.rs` creates and closes windows on the real Surge XT and Distortion without showing them; `tests/state.rs` tests state on real plugins: our synth's window → project → a new instance sounds the same as with the same parameters; the window follows undo; a corrupted state is a log entry, not a refusal; Surge XT with state and `ProcessContext` produces sound; Distortion — the same for an effect. The `PluginStates` contract (undo step, recreation, undo, target errors, saving) is tested in `daw-project/src/tests/plugin_states.rs`; a full session with the built-in synth (window → state → file → open → undo) in `daw-bootstrap/tests/plugin_state.rs`; segment timing of DSP objects in `daw-engine/src/tests/timing.rs` Embedding the plugin interface into a real window (`NSView`), the Tauri window, dragging, input and focus are checked by the owner by hand: a test of real embedding cannot run on CI runners (no GPU for OpenGL interfaces), so there is none.
* **Limitations.** A new window state reaches the sound by recreating the instance (a second after a preset change, on window close, before saving): notes sounding at that moment are cut off. A plugin that changes its state without reporting it (`restartComponent`) and without touching parameters reaches the project only on window close or save. For plugins with a separate controller, the window's component does not process audio and may not know about edits from the window — those are carried by the project parameters on top of the state. Plugin window hotkeys, `IPlugViewContentScaleSupport`, `IComponentHandler2/3`, `IContextMenu`, `checkSizeConstraint`, and multiple windows per target are not supported. A plugin crashing in its window brings down the application (plugins live in our process).
* **Test plugin.** `test-plugins/distortion` has a simple native UI (`nih_plug_egui`, 360×240, five sliders) — handy for testing windows without Surge XT.
* **Keys in the instrument window.** A plugin window has no web page, so the main window's hotkeys (`keyboardPiano.ts`) do nothing in it. On `attach` of an instrument window, `Vst3Editors` asks `EditorKeys` (`daw-vst3/src/keys/`: `mod.rs` — window subscription, `mac.rs` — `NSEvent` monitor, `piano.rs` — layout) to listen to that window: a local `NSEvent` monitor (only events of our own application; no input permissions needed) passes keys to `KeyPlayer` (`keys/piano.rs`, pure logic with tests), which plays through `LiveNoteSink` on that instrument's track. The layout is the same as in `app/src/domain/keyboard.ts` (Z X C V… and Q W E R…, black keys S D G H J / 2 3 5 6 7, `[` `]` — octave), but by macOS key codes: **when changing the layout in one place, update the other**. Plugin windows have their own octave (4 by default), unrelated to the main window's octave; a key release is caught in any window, and closing the window releases its notes. Other platforms do not intercept window keys yet.
* **Test plugins (dev-only fixtures).** `test-plugins/synth` (`Synth.vst3`, kind `vst3:synth` once scanned; native 720×440 window with envelope and filter curves, an oscilloscope and a keyboard) and `test-plugins/distortion` are nih-plug plugins (separate workspaces, GPL) that exist only to test this host: `crates/daw-vst3/tests` (scan, sound, state, windows, the isolated scan), `daw-bootstrap/tests` (`start_with_fixture_plugins`: a headless session with `SessionConfig::plugin_dirs` pointing at `test-plugins/*/target/bundled`, scanned in-process) and `daw-rpc/tests/all/settings.rs`. Build them with `scripts/build-test-plugins.sh`; without the bundles those tests print `SKIPPED` and pass. They are not shipped, not in the catalog by default, and the app never loads them: instruments and effects of the DAW are built in (the owner's rule: never VST3 plugins of our own).
