# `daw-project`

**Core** (`ProjectService`; `HistoryControl`, `ProjectView`): the sole owner of the model and the edit log — the edit pipeline, undo/redo and edit groups, reconciling DSP objects, publishing snapshots, reading the whole project (see "Project core" below). Each job on the project is its own entity on top of the core: **`ProjectTracks`** (tracks and their instruments; `move_track` — display order, does not affect sound, everything is tied to ids; `set_monitor` — input monitoring mode of an audio track on its node), **`ProjectTakes`** (`TakeControl`: takes of an audio clip — add, choose the active one, remove; rules — `take_rules.rs`), **`ProjectTempo`** (`TempoControl`: the tempo map — tempo and time signature over the course of the song, see "Tempo map" ([docs/features/tempo-map.md](../../docs/features/tempo-map.md))), **`ProjectClips`** (clips on the timeline and the loop; batch `edit_clips` / `remove_clips` / `copy_clips` — one undo step, placement (overlaps, audio clip crossfades) is checked against the resulting state; shared rules in `clip_rules.rs`, tempo fitting and pitch — `warp_rules.rs`; `add_note_clip(NewNoteClip)` creates a clip with its notes and content length in a single undo step — exactly like "empty clip → `replace_notes` → `set_loop_ticks`"; `add_note_clips` — several such clips in one core edit: one undo step, all or nothing), **`ProjectNotes`** (a clip's notes; content rules — auto length, note validation, manual length — are pure functions in `note_rules.rs`, shared with `ProjectClips`; musical edits on a group of notes — `note_transforms.rs`, groove — `groove.rs`, pattern variations — `variation.rs`, see "Musical note edits" ([docs/features/note-edits.md](../../docs/features/note-edits.md))), **`ProjectMarkers`** (`MarkerControl`: "song structure" — section markers), **`ProjectFolders`** (`FolderControl`: track folders; rules — `folder_rules.rs`), **`ProjectGraph`** (processing graph: effects, buses, connections), **`ProjectStage`** (`StageControl`: "where each sound stands in the shared room" — `stage.rs`, see "Virtual stage" ([docs/features/virtual-stage.md](../../docs/features/virtual-stage.md))), **`ProjectAutomation`** (automation lanes), **`ProjectPluginStates`** (`PluginStates`: saved plugin states — presets from their windows, see "VST3" ([crates/daw-vst3/CLAUDE.md](../daw-vst3/CLAUDE.md))). **`ProjectFiles`** (`ProjectIo`): create/open/save/restore a project on top of the service, the storage and the recent list; **`ProjectSampleCatalog`** (`SampleCatalog`: "which sounds are in the project", import, removal: a sample goes away together with its audio clips, samplers have their selection reset, the file on disk stays, the data stays in memory for undo); **`ProjectSampleEditor`** (`SampleEditor`: "everything we do with one sound" — waveform, markers, saving and cutting, its peak, a reversed copy); **`ProjectClipProcessing`** (`ClipProcessing`: normalize and reverse of audio clips — see "Audio clip editing" ([docs/features/audio-clip-editing.md](../../docs/features/audio-clip-editing.md))); **`ProjectMidiMappings`** (`MidiMappingControl`: "which MIDI controller knob moves which parameter" — `midi_mappings.rs`, see "MIDI controllers" ([docs/features/midi-controllers.md](../../docs/features/midi-controllers.md))); **`ProjectCleaner`** (`ProjectClear`: "remove all project content, keeping the project itself" — `clear.rs`, one core edit = one undo step); **`ProjectBounce`** (`TrackBounce`: "replace a track with its sound" — "Bounce to audio", "Freeze"/"Unfreeze", see "Bouncing a track to audio" ([docs/features/bounce.md](../../docs/features/bounce.md))).

Depends on: contracts.

Map of the whole code: [ARCHITECTURE.md](../../ARCHITECTURE.md). ## Project core: history, groups, checkpoints, whole-project reads (`daw-project/src/service/`)

* **Whole-project reads — `ProjectView`** (`snapshot`, `revision`), implemented by the `ProjectService` core itself; in `Controls` it is `controls.view`. Used by `project.get`, export, autosave, and telemetry. `ProjectIo` (`ProjectFiles`) is only the file lifecycle: which file is open, create/open/save/restore, warnings.
* **Tempo and time signature are part of the project** (`Project::tempo_map`, edited via `ProjectTempo`/`TempoControl`, see "Tempo map" ([docs/features/tempo-map.md](../../docs/features/tempo-map.md))): an edit is undoable, marks the project as modified, and is heard immediately — the map travels to the engine in the snapshot. The transport does not store tempo. The loop is also project data; it is only passed to the transport.
* **Edit groups** (`HistoryControl`): `begin_group`/`end_group` nest (inner levels join the outer one; the step is recorded when the outermost one closes; `end_group` reports whether a step was recorded); `cancel_group` returns the project to the state at the outermost `begin_group` and closes all levels (this is how a part build, cutting sample regions, and the starter beat are rolled back); while a group is open, `undo`/`redo` refuse. The group is shared for the whole project: edits from any source during that time become part of it. `mark_baseline` means "as if just opened": empty history, no edits.
* **Checkpoints** (`HistoryControl::checkpoint`/`squash`): a change made of many separate calls (an AI request over MCP) becomes one undo step after the fact. `checkpoint` returns a `HistoryMark` — the number of the step on top of the undo stack (every step gets a session-unique number, `service/history.rs`), or of the stack bottom (`root`) when it is empty; `squash(mark, label)` replaces every step above the mark with one step labelled `label` whose "before" state is the state at the mark, and publishes a new revision so the window re-reads the undo label. Why not a group: a group held open between calls would block the user's undo, and a compound call failing midway (`drums.build`) cancels the whole group — everything the AI did before it; a checkpoint holds nothing open. A mark expires when its point leaves the history: undone past it (and then edited), the history cleared (`root` gets a new number), or the step limit forgets its state (`root` moves to the forgotten step's number, so a mark whose own step was the one forgotten is still the bottom and stays valid). `squash` refuses an empty label (`HS-101`), an expired mark (`HS-301`), and an open group (`HS-302`: edits inside it are not steps yet). Both reset knob-edit merging, so a slider move does not join a step across the mark. RPC: `history.checkpoint`, `history.squash { since, label }`; the MCP instructions ask the AI to wrap each user request in them.
* **DSP reconciliation** (`sync.rs`): create missing instruments and effects → publish a snapshot → remove the extra ones. A failure to create or hand over an object goes to the log (`source: "dsp"`) and to the project warnings; a failed attempt is not repeated on every edit until the kind/parameters change or the project is reopened.
* **Limits** are contract constants next to the traits (`MAX_TRACKS`, `MAX_CLIPS`, `MAX_NOTES_PER_CLIP`, `MAX_LANES`, `MAX_POINTS`, `MAX_REGIONS`…); implementations take them from there.
* When a sample is deleted, resetting instruments' sample selection looks for parameters of kind `ParamKind::Sample` in the catalog, not by name; the built-in sampler's names are the constants `SAMPLER_KIND`, `SAMPLER_SAMPLE_PARAM`, `SAMPLER_ROOT_PARAM` (`daw-contracts/src/instrument.rs`).
