# `daw-rpc`

The command layer for the interface: a method table "name → adapter over a contract" with no dependency on Tauri (JSON in and out, its own tests); one entry point `call(method, params)`, each method with its "what it does" description next to it (`RpcTable::add`).

Depends on: contracts.

Map of the whole code: [ARCHITECTURE.md](../../ARCHITECTURE.md). ## The window's streams (`telemetry.rs`, `feed.rs`)

The window gets two events from one thread of the Tauri root (`app/src-tauri/src/main.rs: spawn_telemetry`), about 30 times a second, without asking:

- **`tick`** (`telemetry.rs: tick`): position, meters, load and the other frequent values, every time.
- **`project`** (`feed.rs: ProjectFeed`): the window's copy of the project. The feed remembers the project as it sent it last (without plugin states) and, when `ProjectView::revision` has grown, sends `{ whole: false, changes, status }` with `changes = ProjectChanges::between(sent, now)` — a moved fader is one graph node. The first update, and the next one after a `WholeRequest::ask` (the Tauri command `project_whole`: the window starts, or a call was refused after it showed the value), is the whole project (`whole: true`). The frontend takes updates in `app/src/core/projectSync.ts` and skips any that comes before its first whole one.

Why the backend sends and the window does not ask: there is no request after every edit and no revision on the window's side. Why the whole project also comes through the feed and not as a call's reply: one thread sends everything in order, so changes can never arrive after a newer whole project. Why the copy lives in the feed and not in the core: it is what one reader has, while the core owns the model. The feed has one reader, the window; AI reads `project.get`. A new `Project` field does not compile until `ProjectChanges::whole`, `between` and `apply` carry it (they list the fields by name); the frontend's `applyChanges` builds a typed `Project`, so `tsc` asks for it there too.

## AI interface: RPC self-description and the MCP server (`daw-rpc`, `daw-mcp`)

**Self-description.** `RpcTable::add(name, description, adapter)`: the one-sentence description sits next to the adapter, so it cannot be forgotten, and `P: JsonSchema` means a method without a parameter schema does not compile. The whole catalog is the `rpc.describe` method. Parameters can be a contract type itself when it derives `Deserialize + JsonSchema` (`clips.addNote` takes `NewNoteClip`). Responses are mostly the contract types themselves, with `serde` attributes matching the UI's JSON shape; a few modules shape a reply for the wire (e.g. `patterns.rs` sends grids as strings).

- **Where:** one module per area (`samples.rs`, `clips.rs`, `patterns.rs`…); `library.home` is in `project.rs`. Tests: `tests/all/<area>.rs`, helpers in `tests/common/`.
- **A new RPC method** = a `table.add(...)` line in the area's module: the AI sees it on its own (full path: the [add-operation](../../.claude/skills/add-operation/SKILL.md) recipe).
- **Bytes for what is read many times a second** (`binary.rs`): a method added with `table.add_binary(...)` also answers through `RpcTable::call_binary` as bytes (the sample windows of the live pictures: `audio.masterWindow`, `audio.nodeWindows`), and as JSON through `call` like any other (MCP, tests). Its reply type implements `BinaryReply`; the format is in the module comment and is mirrored by `app/src/api/wire.ts` (decoding) and `app/src/mock/wire.ts`. The window reaches it through the Tauri command `rpc_binary` (`app/src-tauri/src/main.rs`); any other method there is refused with `RP-502`. Why: a JSON sample costs ten characters and a parse on each side, up to 16 nodes 30 times a second.

**The `daw-mcp` MCP server.** A tool = an RPC method (`.` becomes `_`: `drums_build`), with the description and input schema from `RpcTable::describe`; the protocol logic is the pure function `McpServer::handle`. A method error is a normal result with `isError: true` and the text `CODE: message` (see "Errors as codes" in [errors](../../docs/features/errors.md)), so the AI can fix the request. In `initialize` the server sends short instructions (`INSTRUCTIONS` in `daw-mcp/src/lib.rs`): start with `project_summary`, one undo step per user request via `history_checkpoint` … `history_squash` (see "Project core" in [daw-project](../daw-project/CLAUDE.md)), run `analysis_check` before saying "done". `pluginEditor.open` (plugin windows) is not in the catalog: it needs Tauri and is intercepted in `app/src-tauri/src/plugin_window.rs`.

Three ways to connect an AI (`scripts/build-mcp.sh` prints the commands for Claude Code; the repository root `.mcp.json` has the first and the third):
1. **Inside the application (primary).** The window starts an MCP HTTP server on `127.0.0.1` (`app/src-tauri/src/ai_server.rs`, `daw-mcp/src/http.rs`) after the startup project opens. The AI works in the SAME project that is on screen, through the same contracts; the window gets the AI's edits through its project feed like its own and an AI edit is undone with the normal undo. Port: `DAW_MCP_PORT`; disable: `DAW_MCP=off`; a busy port only logs a warning.
2. **Bridge `daw-mcp --attach`** (`daw-mcp/src/bridge.rs`): for clients that only launch stdio processes; forwards each line to the running application's server.
3. **Headless `daw-mcp`** (`daw-app/src/mcp_main.rs`): its own session without audio by default, with its own state folder (`default_mcp_state_dir`) so it does not share autosaves with the window.

**HTTP server protection** (`http.rs`): local-only, and a request with an `Origin` header (a browser), a foreign `Host` (DNS rebinding), a non-JSON `Content-Type` (browser "simple" requests skip the preflight) or anything but `POST /mcp` is rejected without touching the project. Requests are served one at a time on one thread, so project edits do not race. **Known gap:** there is no access key — any local program running as your user can control the application while it runs; `DAW_MCP=off` if you do not need this.
