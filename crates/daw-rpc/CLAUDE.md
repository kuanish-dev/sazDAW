# `daw-rpc`

The command layer for the interface: a method table "name → adapter over a contract" with no dependency on Tauri (JSON in and out, its own tests); one entry point `call(method, params)`, each method with its "what it does" description next to it (`RpcTable::add`).

Depends on: contracts.

Map of the whole code: [ARCHITECTURE.md](../../ARCHITECTURE.md). ## AI interface: RPC self-description and the MCP server (`daw-rpc`, `daw-mcp`)

**Self-description.** Every `RpcTable` method has a description (one sentence on "what it does", the second argument of `RpcTable::add(name, description, adapter)` — the description sits next to the adapter, so it cannot be forgotten) and a JSON schema of its parameters. The schema is generated from the parameter struct (`P: JsonSchema` in `RpcTable::add`), so a method cannot be added without a schema — it will not compile. Responses are the contract types themselves (`SampleInfo`, `Waveform`, `AudioStatus`, `KindInfo`…) with `serde` attributes matching the UI's JSON shape; there are no separate DTOs. RPC modules are split by area (`samples.rs`, `preview.rs`, `sounds.rs`, `midi.rs`, `live.rs`, `catalog.rs`…); `library.home` (the default folder for new projects) is in `project.rs`. Tests are in `daw-rpc/tests/<area>.rs` with helpers in `tests/common/`. Parameter structs and contract types that come from JSON derive `JsonSchema` (`schemars`); nested types are inlined into the schema without `$ref`. The whole catalog is the `rpc.describe` method (name, description, schema). **A new RPC method = a `table.add(name, description, adapter)` line in the area's module: the AI will see it on its own.** Parameters can also be a contract type itself if it derives `Deserialize + JsonSchema` (`clips.addNote` takes `NewNoteClip`: `{ track, startTick, lengthTicks?, notes?, loopTicks? }` — a clip with notes in one call and one undo step; the mock is `mock/handlers/clips.ts` with content rules in `mock/noteOps.ts`).

**The `daw-mcp` MCP server.** A tool = an RPC method (name with `_` instead of `.`: `drums_build`); the description and input schema come from `RpcTable::describe`, and a method without parameters gets an empty object schema. The protocol is JSON-RPC 2.0; the logic is the pure function `McpServer::handle`. A method error is a normal result with `isError: true` and the text `CODE: message` (a registered error code, see "Errors as codes" ([docs/features/errors.md](../../docs/features/errors.md))), so the AI can fix the request; an unknown tool is a protocol error. In `initialize` the server sends short instructions (start with `project_summary`, not the whole `project_get`; time in ticks, ids, the workflow for drums, batch clips `clips_addNoteMany`, clearing with `project_clear`, one undo step per user request — `history_checkpoint` … `history_squash` (see "Project core" ([crates/daw-project/CLAUDE.md](../daw-project/CLAUDE.md))), and the rule "before saying "done", run `analysis_check` and fix the findings"). `pluginEditor.open` (plugin windows) is not in the catalog.

Three ways to connect an AI (`scripts/build-mcp.sh` prints the commands for Claude Code; the repository root has a `.mcp.json` with the first two):
1. **Inside the application (primary).** The DAW window itself starts an MCP HTTP server at `127.0.0.1:47321/mcp` (`app/src-tauri/src/ai_server.rs`) after the startup project is opened. The AI works in the SAME project that is open on screen: edits go through the same contracts, and the window updates on the usual project-changed event; an AI edit is undone with the normal undo. Connecting: `claude mcp add --transport http daw http://127.0.0.1:47321/mcp`. Port: `DAW_MCP_PORT`; to disable: `DAW_MCP=off`; if the port is busy, the application keeps working and logs a warning.
2. **Bridge `daw-mcp --attach [--port N]`.** For clients that can only launch processes (stdio): lines from stdin are sent as POST requests to the running application's server. If the application is not running, each request gets an error.
3. **Headless `daw-mcp [--audio] [--project PATH] [--state-dir DIR]`.** Its own session, no audio (the AI works with the project in memory; `project_save` and `project_export` produce files); its own state folder (`…/DAW-MCP`) so it does not share autosaves with the window.

**HTTP server protection.** It listens only on `127.0.0.1`. A request is rejected (403/415/405/404, with no effect on the project) if it has an `Origin` header (browsers always send it, ordinary clients never do: a foreign website cannot control the program), a foreign `Host` (DNS rebinding), a `Content-Type` other than `application/json` (that is how "simple" browser requests bypass the preflight check), or a path/method other than `POST /mcp`. Requests are served one at a time on a single thread, so project edits do not race each other. There is no access key: any local program running as your user can control the application while it is running — set `DAW_MCP=off` if you do not need this.
