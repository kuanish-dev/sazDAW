# Architecture

Principle: **SOLID, depend only on contracts**.
The contract (interface) comes first, implementations come second: an implementation must follow the interface and honor the contract;
everything else is its own internal business. Everything goes through interfaces, and the code stays simple. The upper layer uses traits from `daw-contracts`
and does not know how they are implemented. The full list of rules is in `CLAUDE.md`.

## Data flow

```
UI/CLI ──(contracts *Control)──▶ ProjectService ──snapshot Arc<EngineSnapshot>──▶ EngineLink ──ArcSwap──▶ Engine (audio thread)
                                      │                                                ▲
                                      └──DSP objects (Box<dyn Instrument/Effect>)──rtrb────┘
```

* All edits go through `ProjectService::edit`: the state is cloned for history, the edit is applied,
  on error everything is rolled back, then missing DSP objects are created and an immutable snapshot is published.
* The audio thread picks up the fresh snapshot without locks (`ArcSwap`); old snapshots are kept by a "graveyard" on the control side,
  so the last reference is never released in the callback. DSP objects being freed are sent back through a queue.
* Live notes, meters and load are atomics and ring buffers.

## Rules

1. A new entity = its own crate (or module) + a trait in `daw-contracts`.
2. A new instrument or effect is a factory with a parameter table; the engine and the service have no branching on the kind name.
   Parameters that require rebuilding are declared by the factory (`rebuild_on`).
3. Entities with two sides (UI and audio thread) are split into `*Control` (any thread, non-blocking) and a realtime side.
4. The audio callback has no allocations, locks or I/O. Engine tables are preallocated; project limits
   (64 tracks, 64 channels, 12 effects per track) match the capacities.
5. `AudioProcessor` and `Instrument` **add** sound into the buffer.
6. Time is in ticks everywhere (`PPQ = 960`); conversion to seconds, frames and bars is a single piece of math in the `TempoMap` tempo map (`daw-contracts/src/tempo_map.rs`, frontend — `domain/tempoMap.ts`), see "Tempo map".
7. The processing graph has no cycles: a source (instrument, audio track) only outputs sound (`NodeKind::accepts_input` — no), the master only receives (`has_output` — no), effects and buses ("processors") connect to each other in any order — this enables a compressor on a bus (bus → effect → master) and a limiter on the master (all inputs → effect → master). Sidechain goes only into an effect; a pre-fader send only from a source or a bus (see "Sends"). The rules are written in one place — `Graph::check_edge` (`daw-contracts/src/graph.rs`); the frontend repeats them in `domain/graph.ts` (`checkEdge`, `acceptsInput`, `hasOutput`) for hints, and the mock checks them with the backend's codes (`mock/graphOps.ts: checkEdge`, built on the same predicates). Processing order is topological over connections (`Graph::order`, ties broken by the smaller id), computed on the control side and shipped to the engine in the snapshot; the mixer (`daw-engine/src/mixer/`) follows it strictly, solo (`compile.rs: mark_heard`) and meters work over connections, including for bus → effect → bus chains. A meter (post-fader level) exists on every node with a fader — tracks and buses — and on the master (`compile.rs: assign_meters`); it is shown by the track header and the graph nodes. Inserting an effect without breaking the path: `GraphControl::insert_effect` (after a source, effect or bus: the node's outputs move to the effect) and `insert_effect_before` (before the master, a bus or an effect: the node's regular inputs move to the effect, sidechain stays; RPC `graph.insertEffectBefore`). In the UI — "＋ Effect" in the source and bus inspector and "＋ Effect on master" on the master (`ui/graph/Inspector.tsx`), as well as "＋ Effect on selected" in the graph panel; the new effect's position — `graphLayout.ts: insertedEffectPosition`; "Arrange" lays out columns by the depth of the signal path (`autoLayout`).

## Running

```bash
export PATH="/opt/homebrew/opt/rustup/bin:$PATH"
cargo run -p daw-app          # console with the starter beat; `--empty` — empty project; `help` — commands
cargo test --workspace
```

**CI** (`.github/workflows/ci.yml`, GitHub Actions; on push to `main` and on pull requests) runs the same checks that CLAUDE.md requires before a commit. The `rust` job (macOS): `cargo fmt --all --check`, `scripts/build-test-plugins.sh` (tests, clippy and bundles of the dev-only VST3 fixtures in `test-plugins/` — the VST3 host tests load them), `cargo clippy … -D warnings`, `cargo test --workspace`. The `frontend` job (Linux) — `tsc`, `npm run lint`, `vite build` and `scripts/third_party_notices.py --check`. Third-party plugins (Surge XT) are not available in CI: their tests print a skip message and pass. Linux is not used for Rust: the app is macOS-only. A new mandatory check = a line in CLAUDE.md and a step in `ci.yml`.

## Audio: devices and buffer

**Contracts** (`daw-contracts/src/audio.rs`): `AudioDevices` (devices, selection, status, `apply`, `watch_input`, `input_level`) and `AudioSettingsStore` (where the selection is stored). The UI sees them only as `Controls.audio` and the `audio.*` RPC (`daw-rpc/src/audio.rs`).

- **`CpalAudio`** (`daw-audio-cpal`) is the only one that knows about cpal. A cpal stream cannot be moved between threads, so `CpalAudio` starts a **host thread** (`host/`: `mod.rs` — commands, the loop and the shared state `Shared`, `output.rs` — output, `input.rs` — input and capture, `faults.rs` — stream faults): all output and input streams are created, live and are closed in it, and the rest of the code sends it commands (`Start` / `Apply` / `WatchInput` / `Outputs` / `Inputs` / `Stop`) and waits for the reply over a channel. Status, selection and peaks are read directly from the shared state (`Shared` methods, fields hidden), without going through the thread. Starting and stopping output — `CpalAudio::start_output/stop_output` (not to be confused with `AudioCapture::start/stop`). The system audio is hidden behind a small private trait `Backend` (`backend.rs`; the real one is `system.rs`), so the host thread is tested with fake "hardware" without a sound card. Pure rules (choosing by name, valid buffer) — `choose.rs`, peaks — `peaks.rs`.
- **Stream restart.** The engine lives in an `Arc<Mutex<Box<dyn AudioRenderer>>>` outside the output stream. Changing the device or buffer: validate the selection (the device exists, the buffer is within `buffer_range`) while the old sound is still playing → close the old stream → open the new one → `renderer.prepare(new StreamConfig)` before `play()` (sample rate and channel count may change). In the callback the engine is taken via `try_lock`: while the lock is held (only at the moment of the switch) the block is silent — waiting and allocating are not allowed. If the stream fails to open, sound goes back to the previous device, otherwise to the system default; `apply` returns an error and does not save the selection.
- **Startup.** `Session::start_audio()` (`daw-bootstrap`) starts the host with the saved selection; a missing device means starting on the system default + a warning in `AppLog` (source `audio`), not a crash. cpal stream faults are written to `AppLog` and to `status.error`. The cpal error callback can arrive from the audio thread (on macOS — overloads and render failures), so it only counts faults in atomics (`faults.rs`, `StreamFaults`), and the host thread moves them into the log and status (it wakes every 250 ms; overloads — at most once every 5 s, with their count). Test builds (`build_session`) get `CpalAudio::without_devices`: lists are empty, there is nothing to open, the selection is saved.
- **Input is opened only on request** (`watch_input(true)`) and closed on `false`: otherwise macOS would ask for microphone access at startup. In the input callback, peaks of the first two channels (for mono both are equal) are computed into atomics; peak decay happens on the reading side. The audio recording status shows these same peaks (`AudioDevices::input_level`). A denied permission is returned as an error with a hint about the microphone permission; a built `.app` needs the `NSMicrophoneUsageDescription` key (`app/src-tauri/Info.plist`).
- **The `audio.json` file** (`AudioSettingsFile` in `daw-persistence`, next to `recent.json`): `{ output, input, bufferFrames, recordLatencyMs }` (the last one is optional, ms), writes are atomic, a corrupted file means the default selection.
- **Input capture** (`AudioCapture`, `daw-audio-cpal/src/capture.rs`). A single input stream serves both the level meter and recording; it stays open as long as at least one consumer needs it (`watch_input` or capture, a counter in the host thread). In the input callback: peaks and, while capture is on, copying the first two channels into a preallocated `rtrb` ring buffer (~5 seconds at the real stream's sample rate and channel count); no allocations, no locks, only atomics. Frames that don't fit (whole frames) are counted in `dropped_frames` and logged when the take stops. The queue is SPSC: the producer is the callback, the consumer sits under a `Mutex` in `Shared` and is read in `drain` from a regular thread (the remainder is available after `stop` too). The format (`StreamConfig`) is the stream's, 1–2 channels. Changing the input device during recording is rejected. Without hardware (`without_devices`, `build_session`) `start` returns an error.
- **`AudioRecorder`** (`daw-audio-recorder`): recording is armed per track (`set_armed`, `set_input`; more in "Input monitoring, multitrack recording and takes"). `start()` takes the armed audio tracks, checks that the project has a file, opens capture, starts the transport (if it was stopped; only in that case will it stop it at the end) and spawns a thread that every ~20 ms pulls frames and updates the status (seconds, peaks, drops). `stop()` pulls the remainder, trims the latency, hands the tracks their channels and writes a WAV for each (`AssetStore::new_asset_path`, name "Recording <track>"), imports the sample and creates a clip at the start bar (or a new take of a covered clip; with a loop region, one take per loop pass — see "Loop recording"). **One undo step** — `HistoryControl::begin_group/end_group` around the files, import and clips of all tracks; a failure on one track does not undo the others, and the error lists the failures. Placement rules (overlap, length by tempo) are checked by `ClipControl::add_audio_clip` itself; on rejection the sample stays in the project, no clip is created, and the error reads "audio recorded to "Samples", but the clip was not created: <reason>". An empty take is an error; the project is not changed.
- **Recording latency.** Sound from the input arrives later than the program played it: by the input buffer, the output buffer and the interface. `latency_ms = AudioSettings::record_latency_ms`, and if it is `None` — the estimate `2 × buffer_frames (otherwise 512) / output sample rate`; in frames — at the input sample rate. The first `latency_frames` frames are trimmed before writing the WAV (`ClipEdit` cannot change `offset_frames`, and the clip starts at the start bar anyway); the clip length is taken from the remaining frames. A take shorter than the latency is an error. The exact value is tuned by ear and entered in the audio settings.
- **Memory.** Audio accumulates in a `Vec<f32>` up to the `Deps::max_samples` limit (~20 minutes of stereo at 48 kHz, about 460 MB); memory is grown in 10-second chunks rather than by doubling. When the limit is reached: capture and the transport we started are stopped, an error is logged, `status.recording` becomes `false` while `track != null` (the UI sees "waiting for stop"), and the accumulated audio is saved on `stop()`.
- RPC: `audioRecord.setArmed { track, armed }`, `audioRecord.setInput { track, input: "stereo"|"left"|"right" }`, `audioRecord.start`, `audioRecord.stop` → clips, `audioRecord.status` → `{ recording, full, seconds, left, right, droppedFrames, tracks: [{ track, armed, input, left, right }], monitorProblem }`; `tracks.setMonitor { track, mode }`; `clips.setActiveTake { id, take }`, `clips.removeTake { id, take }`; `audio.devices` returns the device channel count (`channels`); `audio.settings` / `audio.apply` carry `recordLatencyMs`.
- Adding a similar setting: a field in `AudioSettings` → file → `CpalAudio::apply` → RPC.

**Live effect visuals** (every built-in effect's editor shows a graph of what it does, drawn from its params so it follows the knobs at once even while stopped, with the node's live sound over it that fades out when playback stops; the Graph page's signal path view shows every effect along a path at once). Contract: `NodeScope::watch_nodes(nodes)` and `node_windows(seen: [NodeCursor]) → [NodeWindow { node, watch, end, input, output, sample_rate }]` (`daw-contracts/src/engine.rs`, `Controls.node_scope`; `NODE_WINDOW_FRAMES` = 4096 mono frames per node, about 85 ms at 48 kHz with bins of about 12 Hz — 2048 would leave the 20–150 Hz end of the EQ graph a handful of bins; `MAX_WATCHED_NODES` = 16). `input` is what came into the node before it changed the sound (before the effect, the same as `output` while bypassed; before the fader for sources, buses and the master), `output` what it sent on, over the same frames. Why the input too: most pictures compare the two — a distortion draws its output against its input, a compressor, limiter or gate measures the input against its threshold (a closed gate's output is silence), a delay lights its echoes by the input that feeds them, a reverb finds its own sound as `output − input × (1 − mix)` — and none of it can be recovered from the output of a nonlinear or dynamic effect. The watched nodes are a set for the whole app, replaced as a whole: the interface sends the union of every picture it shows, so two pictures of one node cannot stop each other, and a node that stays in the set keeps its window while a joining one gets a new `watch` number and starts from silence. Ids beyond the first 16 distinct ones are not watched. Each read is one batched call for all watched nodes, and it is incremental: a reader passes back each node's `watch` and `end` from its previous window (`NodeCursor`) and gets only the frames after it (a whole window for a new watch, no cursor, or a reader more than a window behind), so the traffic stays near the audio rate itself (two lanes × the sample rate per node) instead of two whole 4096-frame windows per node 30 times a second; cursors live with the reader, so the read changes nothing in the engine and several readers (the interface, an AI client over MCP) do not disturb each other. It is its own contract, not more `EngineStats`: watching nodes is a job of its own, and the planned `EngineLink` split gives telemetry its own traits anyway. Engine: `daw-engine/src/scope.rs: NodeTap` in `Telemetry`, `MAX_WATCHED_NODES` preallocated slots, each two `Lane`s of atomics (input, output) moved by one frame count (`end`); `GraphMixer::process` offers every node's input before the effect or fader (`tap.input`, written at the frames the output will take, the count does not move) and its output after (`tap.output`, moves the count). On the audio thread a node costs one atomic load while nothing is watched and a scan of the 16 slots otherwise; only watched nodes are copied, never allocating. The control side (`watch`, `windows`) keeps the watch numbers under a mutex the audio thread never takes. The shared count keeps a node's two windows paired frame by frame even when the set changes between the two writes; a read that lands between them sees the newest input in place of the oldest frame of a whole window, and a slot freed and retaken during a segment may keep a few samples of the old node — both harmless for a picture. The window is mono (the middle of the channels): a hard-panned sound reads up to 6 dB below what an effect's detector sees, and a sidechain key is not captured (a keyed compressor or gate shows its own input; the gain reduction is still the engine's). RPC `audio.watchNodes { nodes }` / `audio.nodeWindows { seen }` (`daw-rpc/src/audio.rs`), actions `audio.watchNodes` / `audio.nodeWindows`, mock `mock/handlers/audio.ts` with `mock/liveSound.ts` (the set, watch numbers and frame counts that run with the clock; the same music for input and output: the mock runs no effects, so an EQ's spectrum ignores its bands and a distortion's trace lies on the 1:1 line there). Frontend: one registry for the app, `state/nodeSounds.ts` (`session.nodeSounds`): pictures `listen(node, hear)`; while anything listens it polls every 33 ms (`createPoller`), tells the engine the set when it changed (and again when a reply lacks a node: another client replaced the set), reads all windows in one call with its cursors, keeps each node's latest 4096 frames and hands every listener `{ input, output, sampleRate, dt, now }`; the last listener leaving stops polling and empties the set, a failed read (the action shows a toast) stops it until the next picture opens. Nodes beyond the first 16 listened to sound silent. `ui/effects/nodeSound.ts: listenToNode(node, hear, onStop)` is the pictures' side: it listens while the component lives and again for another node when it switches (a memo on the node id). Shared pure math: `domain/liveLevels.ts` (peak and RMS of the newest 35 ms, a scrolling history of readings, a fast-up/slow-down follower that makes pictures fade instead of blink off), `domain/plot.ts` (view size, dB → height, SVG line and area paths), `domain/frequencyAxis.ts` (the 20 Hz–20 kHz log axis and grid of the EQ and filter graphs). Each effect's shape is a pure module that **mirrors** its Rust DSP (each Rust module names its mirror; change both sides together), and the graph is a component in `ui/effects/` chosen by kind in `EffectGraph.tsx` (used by `EffectPanel` and the signal path view):
* `eq` → `EqGraph.tsx` + `LiveSpectrum.tsx`: the response curve (`eqCurve.ts` mirrors `eq.rs`, on the biquad mirror `biquad.ts` of `biquad.rs`, shared by every graph of a biquad effect) with draggable band handles over the live spectrum of the output, like Pro-Q by default (what you hear, so a boost or cut reshapes the spectrum under the curve). Spectrum math `domain/spectrum.ts`: the master visualizer's Hann-windowed FFT (`visualizer.ts: magnitudes`); 150 points spread evenly over the log axis, each the power mean of its bins where it covers two or more and the value between the two nearest bins below that; a +4.5 dB/octave tilt around 1 kHz (music falls about that much, so the highs do not hug the floor); its own 0…−90 dBFS scale (a curve's gain scale is far too narrow for a spectrum); smoothing that rises in ~30 ms and falls in ~250 ms.
* `filter` → `FilterGraph.tsx`: the SVF response (`filterCurve.ts`, mirrors `filter.rs`: the analog prototype under the bilinear transform, k = 1/Q, the band-pass normalized, the mix) on +24…−36 dB over the same `LiveSpectrum`; one handle at the cutoff — drag sets the cutoff and, for low- and high-pass, the resonance (the peak's height is Q in dB), the wheel sets the resonance, double-click resets both.
* `compressor`, `limiter`, `gate` → `DynamicsGraph.tsx` (geometry `dynamicsGraph.ts`; curves `compressorCurve.ts` mirrors `dynamics.rs: GainComputer::reduction`, `limiterCurve.ts` the input gain and ceiling, `gateCurve.ts` the threshold, 6-dB hysteresis and depth as two branches, the way up and the way down). Left, the transfer curve with the thresholds dashed and a dot at (input level, output level) of the newest sound, which leaves the curve during attack and release; right, the last 3 s of input level (line), output level (area) and the engine's gain reduction (from `tick.reductions`, unheld, hanging from the top on the same dB scale) against the thresholds; under them the held GR meter (`ReductionMeter`) and, for the gate, Open/Closed from its reduction (open while it takes less than half of its depth).
* `distortion`, `saturator` → `ShaperGraph.tsx` (`shaperCurve.ts` mirrors `Shape::apply` and the saturator's `shapes` with drive, mix and output; the tone filter, oversampling and DC blocker shape the sound over time and are left out of the curve). Left, the transfer curve (input sample → output sample) with the newest 1024 frames traced over it as an X-Y scope — a pure shaper retraces its curve, the tone filter opens it into a loop; right, the input wave (dim) and the output wave (bright) from the latest rising zero crossing (`visualizer.ts: latestTraceStart`). The last trace stays and fades when the sound stops.
* `delay` → `DelayGraph.tsx` (`delayTaps.ts` mirrors the `SYNC_QUARTERS` lengths, the time from the tempo — `tick.tempo`, like the engine's `BlockTiming` — or from ms, feedback per repeat, ping-pong starting on the left, `mix_over_dry`): the dry bar and up to 12 echoes above −48 dB as outlined bars on a time line with the beats dotted; live, each bar fills with the input level of one, two… delays ago, so a hit runs along the echoes and they die away one by one after playback stops.
* `chorus` → `ChorusGraph.tsx` (`chorusSweep.ts` mirrors the LFO: one sine at `rate`, the right voice a quarter turn ahead, `delay ± depth`): both voices' delay over the last 2 s scrolling with the LFO inside the depth band; the dots at "now" and the band light up with the output level. The engine does not report its LFO phase, so the picture turns its own at the same rate: right speed and range, not the engine's exact moment.
* `reverb` → `ReverbGraph.tsx` (`reverbTail.ts` mirrors Freeverb's comb feedback `0.7 + 0.28·room`, the damping lowpass `0.4·damp` and the mean comb length: RT60 at f = 3 × pass time / −log10(feedback × lowpass gain at f)). One time line with "now" a third of the way in: the last 2 s of dry level (line) and the reverb's own level (area, `output − input × (1 − mix)` — exact, the dry part of `Reverb::process`), then the decay fan from "now" — an outline from 0 dB falling to −60 dB in the RT60 of the lows (upper edge) and of 5 kHz (lower edge, faster with damping), and the same fan filled from the reverb's level now — with the lows' RT60 in the corner.
* `multiband` → `MultibandGraph.tsx` (`multibandCurve.ts` mirrors `multiband.rs` and `crossover.rs`: the ordered splits, each band's chain of Linkwitz–Riley halves and later all-passes as complex responses on the biquad mirror, three bands as the top two summed, solo and bypass). On the frequency axis over the live spectrum: the shapes of the bands in use (thin), the whole effect's response with every band at its gain minus its live reduction (bright: what the bands do to the sound now — the sum is flat while nothing compresses), and each band's reduction hanging from the top of its stretch with its value. The live reduction is the engine's band gains (`tick.bands`, held by `createBandGains`), not measured from the window. Split lines drag like EQ handles (double-click resets); under each band its number and S/B chips toggle `band<n>_solo`/`band<n>_bypass`.
* `dynamic_eq` → `DynamicEqGraph.tsx` (`dynamicEqCurve.ts` mirrors `dynamic_eq.rs`: four peaking biquads in a row, each at its gain times how far it is engaged). On the EQ's axes over the live spectrum: the response with every band at its full gain (dashed: as far as it can go) and with the bands where they are now (bright), and at each band a bar from 0 dB to its live gain — the engine's band gains (`tick.bands`, held by `createBandGains`), so the curve breathes with the sound. One handle per band at (frequency, full gain): drag sets both, the wheel sets Q, double-click resets the band; a band with gain 0 is dimmed.

A new long canvas inside a scroll area is built the same way. Code layout by role (where to look for what): the engine is `daw-engine/src/`: `engine.rs` (audio thread: the segment conductor), `link/` (`mod.rs` — `EngineLink`: snapshots and the "graveyard", DSP commands and the `Garbage` release queue with its audio-side end `GarbageBin`, live notes and recording; `telemetry.rs` — format, load, preview position, latency, `Loss` drop counters, and the scopes (`EngineStats`, `NodeScope`, `MasterTap`); the mono check's switch (`MonoCheck`); `monitor.rs` — the input table; `held.rs` — lanes held by live automation writing), `meters.rs` (`Meters`: level meter cells), `scope.rs` (`Lane`s of atomics behind `MasterScope`, the master window for the visualizer, and `NodeTap`, the watched node's input and output windows that the mixer feeds; `MeterTap`, every stereo master frame for the live meter, numbered so its reader can tell what it missed), `instruments.rs` (`InstrumentRack`: track instruments), `playback.rs` (what to play: `notes.rs` — note schedule, `controllers.rs` — controller schedule and chase, `audio_voices.rs` — audio clip voices), `automation.rs` (`AutomationPlayer`), `params.rs` (which parameters to re-send), `preview.rs`. The mixer is `mixer/`: `mod.rs` (node tables, buffers, `process`), `effects.rs` (`EffectPool`: the effect store), `compile.rs` (graph snapshot → tables: nodes, edges, order, audibility under solo, effects, meters, channel utility slots; nodes are looked up by binary search) (also where volume and pan are overridden by automation for the segment), `utility.rs` (the channel utility: polarity, width, mono, fine time alignment), `latency.rs` + `delay.rs` (plugin delay compensation, see "Plugin delay compensation (PDC)"). On a new snapshot, DSP objects receive only the parameters that changed (a new object gets all of them; after `prepare` and at the end of automation — all of them); preview commands do not touch parameters. `EngineLink::send` prepares (`prepare`) an instrument or effect before sending it to the queue; the mixer on the audio thread prepares nothing. The frame of an event within a segment is a single formula, `BlockTiming::frame_at`, for notes, audio clips and the metronome. The `daw-app` console is `src/commands/`: `mod.rs` (word parsing `Words`, help, dispatcher), one file per area (`transport`, `tracks`, `clips`, `graph`, `project`, `library`), each returns `true` if the command is its own; a new command is a line in the right area and in `HELP`; errors are printed by `report`/`checked`; `mute`/`solo` work on tracks and buses. Small app state (`recent.json`, `sound-sources.json`, `preferences.json`; `audio.json` and `metronome.json` are read with the same `read_or_default`) is in `daw-persistence/src/json_state.rs` (`JsonState<T>`: reading, lock, atomic write; a corrupted file and a write failure go to the log with `source: "persist"`, the app does not crash). The note recorder (`daw-recorder`: `lib.rs` — polling and the take, `pairing.rs` — press–release pairs, `take.rs` — each track's clip and loop passes, `shape.rs` — note shape) logs lost records (`source: "record"`, one entry per take; "clip deleted" is normal and not logged); a new clip starts at the beginning of a bar of the current time signature.

Releasing memory on the audio thread: everything the audio thread might release as the last owner (an instrument, an effect, a preview sound and an audio clip voice's sound) goes into the `Garbage` queue (`GarbageBin::throw`), and the control side releases it explicitly with `DspSink::collect_garbage`: when sending a command, in the `daw-engine-watch` watchdog thread (`daw-bootstrap/src/engine_watch.rs`, ~20 Hz) — so the queue does not overflow during long playback without edits — and in offline export on every chunk. The same thread logs (`source: "engine"`) every increase of `EngineStats::losses`: live notes and recording notes that did not fit into the queues, and "leaked" objects. Audio clip voices hand their sound to the same queue when they are dropped (end of the sound, stop, seek, change of the processed sound); a voice past the end of the sound is never started at all. A queue overflow is a leaked reference (counted in `EngineLosses::leaked_garbage`), not a release on the audio thread.

Autosave (`daw-persistence/src/autosave.rs`) logs write failures (`source: "autosave"`), one entry per run of consecutive failures; otherwise edits would silently stop being saved (rule 11). `Autosaver` receives the interval as a function (`AutosaveInterval = Box<dyn Fn() -> Option<Duration>>`, `None` means off) and asks it on every step; the thread wakes up at least once a second (`RECHECK`), so a settings change takes effect immediately. `Session::start_autosave()` passes `preferences.get().autosave_interval()`.

**Interface languages (frontend).** English is the default, Russian the second language; the choice is `Preferences.language` (`"en" | "ru"`, Settings → Appearance → "Language / Язык"), applied live without a restart. **Song markers, track colors and folders.** Model (`daw-contracts/src/model.rs`): `Project.markers: Vec<Marker { id, tick, name }>` (always sorted by tick) and `Project.folders: Vec<Folder { id, name, collapsed, color? }>` (both `#[serde(default)]`); a track has `Track.color: Option<String>` and `Track.folder: Option<FolderId>`. - **Contracts.** `MarkerControl` (`markers.rs`, "where each section begins"): add/edit/remove; one marker per tick, an empty name or one longer than `MAX_MARKER_NAME` — `Invalid`, a tick beyond `MAX_CLIP_TICK` — `OutOfRange`, more than `MAX_MARKERS` — `LimitReached`. `FolderControl` (`folders.rs`, "which tracks are shown together"): create, edit (`FolderEdit`: name, collapsed, color; `null` removes the color), remove (tracks stay in place), `set_folder_tracks` (membership and order as a whole), `set_folder_mute`/`set_folder_solo` (a flag on the source nodes of all its tracks in one undo step — an honest substitute for a "folder bus": a folder does not change the sound or the graph). `TrackControl::set_color`. Every edit is one undo step.
- **Why membership is stored on the track, not as a list in the folder.** This way a track cannot end up in two folders, and a deleted track leaves nothing dangling. The order inside a folder is the order of `tracks`; the rule "a folder's tracks stand together at the topmost of them, an empty folder is deleted" is enforced by a single function, `folder_rules::gather`, called by `move_track`, `remove_track` and all folder edits. Therefore `move_track` does not change membership: a folder track moved down returns to its block, and one moved above the folder lifts the whole folder.
- **RPC** (`daw-rpc/src/markers.rs`, `folders.rs`, `tracks.rs`): `markers.add {tick, name}` → id, `markers.edit {id, tick?, name?}`, `markers.remove {id}`; `tracks.setColor {id, color|null}`; `folders.create {name, tracks}` → id, `folders.edit {id, name?, collapsed?, color?}`, `folders.remove {id}`, `folders.setTracks {id, tracks}`, `folders.setMute/setSolo {id, on}`. The descriptions are written for an AI that marks up a song; the MCP instructions contain a line about `markers_add` and `folders_create`. Tests: `daw-project/src/tests/markers.rs`, `folders.rs`; `daw-rpc/tests/arrangement.rs`.

**Cue (start position) and the timeline ruler strip.**
- **Contract** (`TransportControl`, `daw-contracts/src/transport.rs`): `set_cue(Option<u64>)` / `cue()`. With a cue, `play()` from pause or stop first seeks to it (so pausing and pressing play again restarts from the cue, not where it paused), `stop()` returns to it (else to 0); `set_cue` itself does not move the playhead; while playing, `play()` does not jump. Implementation — one more atomic in `daw-transport` (`NO_CUE` = none), only the control side reads it, the audio thread is untouched; tests in `daw-transport/src/lib.rs`. Loading/creating a project clears the cue (`daw-project/src/service/mod.rs`). An audio take started from a stopped transport begins at the cue (`daw-audio-recorder`).
- **RPC/MCP:** `transport.setCue { tick | null }` (`daw-rpc/src/transport.rs`); the current cue is `cue` in the `tick` telemetry (`telemetry.rs`; `Tick.cue` in `api/types/transport.ts`). Mock — `mock/handlers/transport.ts` + `MockWorld.cue` (cleared by `install`).
- **UI.** `TransportActions.cueAt(tick)` (set the cue, then seek) and `clearCue()`. The ruler strip (the bar ruler) is a separate canvas: `ui/tracks/rulerRender.ts` draws bars, loop, signature and marker flags and the cue flag (geometry — `cueLayout.ts`); the rows canvas (`timelineRender.ts`) draws the marker lines, the loop shade and the dashed cue line; row coordinates start at 0 below the strip. Mouse on the strip: `tempoPointer` → `markerPointer` → `rulerPointer` (click — cue + seek, drag — loop, right-click on the cue flag — remove the cue, elsewhere — clear the loop). Layout (`TracksView.tsx`): the page scrolls vertically; the toolbar and the strip are `sticky` (the strip's `top` is the toolbar's measured height). CSS sticky does not work inside a horizontal scroller, so the strip sits outside the rows' `overflow-x-auto` in a clipped container whose `scrollLeft` is copied from the rows on `scroll`; `Timeline` renders the ruler into it through a `Portal` (from a fragment, so ruler events do not bubble into the rows' pointer). Both canvases draw only the visible window (`createScrollWindow` of the rows). Something similar above the rows (e.g. a chord lane): grow `RULER_HEIGHT`, draw in `rulerRender.ts`, add a `*Pointer.ts` to the strip's chain in `Timeline.tsx`.

**Song loop** (playback that reaches the song end jumps back to bar 1 and plays on).
- **Where and why.** In the transport clock (`daw-transport`), by the same mechanism as the loop region: the segment is cut at the end and the position jumps on the exact frame, and the engine sees an ordinary jump (notes are released, `playback.rs`). A frontend watcher that seeks back would be late by up to a tick (~33 ms) and audible. One rule decides what playback wraps around — `Shared::wrap_region`: the loop region wins; otherwise `(0, song end)` while the song loop is on, not held and the arrangement is not empty. The clock and the control side read the same rule. Playback already at or past the end runs on (as with the loop region), so starting after the last clip to add a new part works.
- **Contract** (`TransportControl`, `daw-contracts/src/transport.rs`): `set_song_loop(on)` / `song_loop()` — the mode, on by default; it belongs to the running app and is not saved (no project or preferences field). The metronome switch, by contrast, is remembered between launches in its own small store (`MetronomeSettingsStore`, `metronome.json`), not in `Preferences`, so the settings page and the transport button never overwrite each other's copy. `set_song_end(Option<u64>)` — set by the project in `ProjectService::sync` (`daw-project/src/service/sync.rs`, next to `set_loop`) on every edit, undo included. `hold_song_loop(bool)` — a recording asks playback to run straight on (a counted hold: each recorder pairs its calls). `wrap_region()` — what playback wraps around now; `BlockTiming::loop_region` carries it to plugins.
- **Song end** — `Project::song_end` (`daw-contracts/src/model.rs`): the tick after the last note or audio clip. Automation clips do not count (no sound of their own). The export's "whole song", the level analysis and the project summary use the same method. The loop point is `Project::song_loop_end`: the song end rounded up to a whole bar of the tempo map, so the looped song keeps its beat.
- **Recording.** A jump back at the song end under a take would cut it, so recording holds the song loop: armed note recording (`daw-recorder`, `RecordControl::set_armed`; an `AtomicBool` swap pairs the hold with one release) and a running audio take (`daw-audio-recorder`, from `start` to `stop`, a failed start or drop). The loop region still wraps while recording: notes loop inside their clip, audio passes become takes (see "Loop recording").
- **Offline engines** (export, bounce, analysis) build their own transport, which never receives a song end, so they never loop.
- **RPC/MCP:** `transport.setSongLoop { enabled }` (`daw-rpc/src/transport.rs`); the tick telemetry has `songLoop` and `wrap` (what playback wraps around now; it replaced the old `loop` field, which only fed the cursor).
- **UI.** The loop button (`IconLoop`) on the transport bar (`ui/transport/TransportBar.tsx`, next to the metronome) calls `TransportActions.setSongLoop`; strings `project.transport.songLoop`/`songLoopHint` (EN + RU). The smooth cursor (`domain/playhead.ts`) stops at the end of `tick.wrap` until the jump arrives. Mock — `mock/songLoop.ts` (`wrapRegion`, the same rule; armed note recording and an audio take hold it), `MockWorld.songLoop`/`recordingAudio`, `transport.setSongLoop` in `mock/handlers/transport.ts`.
- **Tests:** the clock — `daw-transport/src/lib.rs` (frame-accurate jump, loop region priority, off/empty song, past the end, holds); the song end — `daw-contracts/src/model.rs`; project → transport — `daw-project/src/tests/clips.rs`; the recorders' holds — `daw-recorder/src/tests.rs`, `daw-audio-recorder/src/tests/lifecycle.rs`; RPC and telemetry — `daw-rpc/tests/all/tempo.rs`; by ear in a full session — `daw-bootstrap/tests/all/render_playback.rs`. A session test that checks silence after the song turns the song loop off.
- **Something similar** (e.g. jumping back to the cue instead of bar 1): change `Shared::wrap_region` and its contract doc, the mock's `wrapRegion`, and a clock test.

**Keyboard shortcut help** is built from the same tables the keys work from: `GLOBAL_KEYS_HELP` (`state/globalKeys.ts`), `CLIP_KEYS_HELP` (`state/clipKeys.ts`), `PIANO_ROLL_KEYS_HELP` (`ui/pianoroll/editing.ts`), `GRAPH_KEYS_HELP` (`ui/graph/GraphCanvas.tsx`), `KEYBOARD_PIANO_HELP` (`domain/keyboard.ts`), `PATTERN_KEYS_HELP` (`ui/automation/PatternEditor.tsx`); the shared row type and key labels are in `domain/shortcuts.ts`. ## VST3 (`daw-vst3`)

This crate turns installed VST3 effects and instruments into ordinary catalog kinds: effects like `vst3:distortion` go into `EffectRegistry`, instruments like `vst3:surge_xt` go into `InstrumentRegistry`, next to the built-in ones, and the rest of the application knows nothing about VST3. The only entry point is `Vst3Plugins` (implements the `PluginScanner` contract, lives in `Controls.plugins`); only `daw-bootstrap` (`plugins.rs`) builds it. The test `build_session` uses an empty scanner (`found: 0`) so tests do not depend on the machine.

* **List of installed plugins.** `PluginScanner::installed()` returns the plugins currently in the catalogs (`InstalledPlugin { kind, name, vendor, path, type, params, paramsTotal, disabled }`); it is built from the `PluginDirectory` (the same kinds as in the catalog) without loading plugins. Order: instruments, then effects, by name. `folders()` is where `scan` looks (`VST3_DIRS`; empty in the test session). RPC `plugins.list` → `{ folders, plugins }` (`daw-rpc/src/plugins.rs`).
* **Scanning happens only on demand and in a separate process.** Plugins are NOT searched for or loaded at startup: a third-party plugin may crash while loading, and startup must be fast and safe. "Project" → "Scan plugins" → action `plugins.scan` → RPC `plugins.scan` → `PluginScanner::scan`. The response is `{ found, effects, instruments, failed: [{ path, reason }] }` (`found` is the total); a failure of an individual plugin goes both into the response and into the log (`source: "vst3"`), and the scan continues. After the scan the UI re-reads the catalog (`refreshCatalog`). Each bundle is loaded by the **helper** `daw-plugin-scan` (a `[[bin]]` of the `daw-vst3` crate: `src/bin/daw_plugin_scan.rs` → `isolated.rs: helper_main`, the same `Vst3Scanner::scan_bundle`), one process per bundle, with a `SCAN_TIMEOUT` of 20 s (`isolated.rs: IsolatedScan`). Protocol: `daw-plugin-scan <bundle> <response file>`; the response is JSON `{ outcome: { plugins, failed }, journal }` in a file (not on stdout: plugins print their own garbage there; the helper's output is discarded), and the application copies the helper's log entries into its own log. A signal → a `failed` entry "plugin crashed while loading (signal 11, SIGSEGV)", a timeout → "plugin did not respond within 20 s (hung while loading)" (the process is killed); any other exit code or an unparseable response also becomes a `failed` entry; the remaining bundles are still scanned. Where the helper lives: next to the application executable (`daw-bootstrap/src/plugins.rs: scan_helper`): `SazDAW.app/Contents/MacOS` (put there by `scripts/make-dmg.sh`; `npx tauri build`/`tauri dev` build it themselves via `beforeBuildCommand`/`beforeDevCommand` in `tauri.conf.json`), during development `target/debug|release` (for cargo tests, one folder above `deps`). If the helper is missing, `scan` returns an error saying the plugin scan helper was not found and how to build it (`cargo build -p daw-vst3 --bin daw-plugin-scan`), and changes nothing. We do not use Tauri's `externalBin`: it requires a file with the target-platform suffix already when building `daw-desktop`, and would break the workspace's `cargo build`/`cargo test` unless the helper was built first. In-process loading remains only for tests (`Vst3Plugins` without `with_scan_helper`, e.g. a headless session scanning the `test-plugins/` fixtures).
* **The `plugins.json` cache.** After a scan, the list of `PluginInfo` (bundle path, class id, name, vendor, parameters) is written to `<state folder>/plugins.json` through the `PluginCacheStore` contract (implementation `PluginCacheFile` in `daw-persistence`; the write is atomic: temporary file + rename). Only `daw-vst3` knows the document format, and only `daw-persistence` knows the state paths. At startup `Vst3Plugins::load_cached` restores factories from the cache; no file means no plugins; a corrupted file means a log entry and "no plugins".
* **Lazy loading.** A `Vst3EffectFactory` is created without touching the plugin file: the bundle is opened on the first `create`. If the file is gone (the plugin was removed after the scan), `create` returns an error (the plugin file is missing from disk; rescan plugins) and writes to the log.
* **Replacing the set on the fly.** Both registries (`EffectRegistry`, `InstrumentRegistry`) store factories in groups under a `RwLock`: the built-in ones are assembled at startup, and the `vst3` group is replaced as a whole through the `EffectGroups::replace_group` and `InstrumentGroups::replace_group` contracts (called by `Vst3Plugins`, which knows only the trait). A repeated scan replaces the previous set; effects already created in projects are not affected. The catalog is read by the command thread and by export; the audio thread does not touch it, so the lock is safe; `create` is called after the lock is released. A repeated scan reuses a plugin's `PluginSource` if its `PluginInfo` has not changed (`catalog.rs: factories_of`): the bundle is not reloaded, and parameter strings (the contract's `&'static str`) "leak" once per source. The effect and instrument factories and their shared part (`CatalogEntry`) also live in `catalog.rs`.
* **Where we look.** The `VST3_DIRS` constant in `daw-bootstrap/src/plugins.rs`: `/Library/Audio/Plug-Ins/VST3` and `~/Library/Audio/Plug-Ins/VST3` (`*.vst3` bundles, up to two levels deep). An effect is an "Audio Module Class" class with the `Fx` subcategory, an instrument one with the `Instrument` subcategory (`Instrument|Synth` etc.); if both are present, the plugin is treated as an effect; everything else (analyzers…) is skipped. The type is stored in `PluginInfo.kind` (and in `plugins.json`).
* **Loading a bundle (macOS).** `CFBundle` from the path → executable from `Info.plist` → `dlopen` (libloading) → `bundleEntry(CFBundleRef)` → `GetPluginFactory`; at the end the factory is released, then `bundleExit`, then the library is closed. An effect factory keeps the bundle loaded until the application exits.
* **Parameters → contract: real units.** A VST3 plugin understands only normalized values 0…1, but outward (catalog, project, UI, RPC/model) a parameter is exposed in real units, like built-in effects: `ParamInfo { name: "p<id>", label: "Cutoff, Hz", min: 40, max: 18000, default: …, kind, choices }`. How it is determined (during the scan, `instance/params.rs` + pure logic in `instance/display.rs`, the result is `ParamDesc` in the cache):
  * `stepCount == 1` → `Switch` (0/1);
  * `stepCount` 2…256 → step texts from `getParamStringByValue`: if all are numbers ("-2", "12 st") → `Number`, and the step values are those numbers; if there are names ("Sine", "1/4") → `ParamKind::Choice`, `choices` are the names, and the value is the option index 0…n-1;
  * everything else (a continuous parameter, more than 256 steps) → `Number` along a 129-point curve. The **numbers the plugin displays** are taken as the real values: the plugin's own conversion `normalizedParamToPlain` is used if it matches the plugin's text up to rounding (it is more precise than the text), otherwise the numbers from the text (nih-plug stores gain as a ratio but displays dB; a fraction is 0…1 but displayed as a percentage; in JUCE "plain" = normalized); if the text is not a number or is non-monotonic, the plugin's conversion is used with no units in the label. Units come from `ParameterInfo.units` or the tail of the text ("Hz" in "440 Hz"), shown in the label after a comma (numbers only).

  **Value conversion (`scale.rs`: `ParamScale`, `ParamScales`).** The "real ↔ normalized" table is built when an instance is created, on the control side (with the same `read_parameters` as during the scan, so it matches the catalog): a straight line by two points (arithmetic), a curve by 129 points with inverse linear interpolation, steps by an exact table (nearest step). A non-monotonic/flat curve gets no conversion (0…1). An effect's and instrument's `set_param` is called from the audio thread: it only looks up the id in the table (binary search, no allocations or controller calls) and writes the normalized value into a queue; out-of-range values are clamped. The reverse direction (plugin window → project) is converted by `ParamBridge` using the window instance's table. Projects with old normalized values are not converted (rule 10). Contract: `ParamInfo::fit` (limits; for a choice, an integer index) — the project uses it to validate parameter values; the engine interpolates choice automation as a number, the plugin receives the nearest step, and the UI places points only on integers (`domain/automation.ts`, `Range.whole`). UI: `ui/common/ParamControl.tsx` (node inspector and instrument window) shows a `choice` as a list of options and numbers as a knob (`domain/knob.ts`: ranges with a wide spread such as 40…18000 Hz use a logarithmic scale).

  Hidden and read-only parameters, program switches, and bypass are not included in the list. The `p<id>` name is built and parsed only by `param_name.rs`. **Limit: only the first `MAX_EXPOSED_PARAMS` = 128 eligible parameters, in the plugin's order, are exposed outward (to the contract, UI, cache)**: synthesizers have thousands (Surge XT has 2854), and nobody needs such a list; the full count is stored in `PluginInfo.params_total`. Strings for `&'static str` are intentionally "leaked" when the list is built (at startup from the cache and on each scan).
* **Audio.** `set_param` only converts the value to normalized (`ParamScales`) and writes it into a queue for up to `MAX_EXPOSED_PARAMS` = 128 distinct parameters (`pending.rs`; as many as can come from the project on creation); at the start of the next `process` the values are passed to the plugin through the host's `IParameterChanges` (position 0 frames). `ProcessRunner` pre-creates planar buffers (8192 frames), `ProcessData`, and queues; nothing is allocated in `process`, and blocks larger than 8192 frames are processed in chunks. Latency is `getLatencySamples` after startup.
* **Failures.** A plugin that failed to load during a scan or creation is logged (`source: "vst3"`) and skipped/rejected; the scan does not fail. A plugin that crashes the process while loading only crashes the scan helper (see above). The engine destroys effects (including `terminate`) on the control side through the "garbage" queue (`Garbage`), not on the audio thread. Failures on the audio thread (a block not processed, a parameter or note did not fit in the queue) cannot be logged from there, so they are accumulated in `BlockFaults` counters (`faults.rs`) and logged on the control side: on the next `prepare` and on destruction. Plugin windows may only be closed on the main thread: if `Vst3Editors` is destroyed on another thread, open windows are intentionally "leaked" with a log entry — this is better than undefined behavior.
* **Crash protection (like Reaper, but without moving the plugin into another process).** On macOS a plugin window cannot be embedded from another process (`NSView` does not cross process boundaries), so plugins run inside the application process, and a crash in `process` brings down the application. The protection does two things: it identifies the culprit and lets you disable it:
  * **The "who is processing" marker** (`guard/`: `map.rs` — `GuardMap`, `marker.rs` — `ProcessMarker`/`GuardSlot`, `mod.rs` — `Vst3CrashGuard`). The file `<state folder>/plugin-guard.bin` (`GUARD_FILE` in `daw-bootstrap/src/plugins.rs`) is memory-mapped (`memmap2`, shared; the layout is described at the top of `map.rs`): a signature, a "session running" flag, the index of the slot "currently processing", and 256 "kind + plugin name" slots. A plugin instance from the catalog gets a slot on creation (`catalog.rs: CatalogEntry::create_with` → `PluginInstance::watch`; the signature is written on the control side), and `PluginInstance::guarded` marks "processing" around `process`/`render` (`Vst3Effect`, `Vst3Instrument`), `prepare` (startup), and instance creation and termination. On the audio thread this is a single atomic store into mapped memory: no allocations, locks, or system calls; the pages survive a process crash in the kernel cache. Leaving processing clears only its own mark (`compare_exchange`: export on another thread does not interfere). If there is no free slot or the file could not be opened, plugins run without a marker, and the reason is logged.
  * **Report on the next launch.** The `PluginCrashGuard` contract (`daw-contracts/src/plugin_crash.rs`, `Controls.plugin_crash`): `last_crash() -> Option<PluginCrash { kind, name, project, places }>`, `dismiss()`, `end_session()`. A crash = the "session running" flag was not cleared and someone was processing. `project` is the most recent project from the recent list, `places` is where the plugin sits in it ("track "Bass"", "effect "…""; the file is read through `ProjectStorage`, the project is not opened). The roots (`app/src-tauri` on `RunEvent::Exit`, `daw-app`, `daw-mcp`) call `end_session` on a normal exit. After a crash `Startup::open` does NOT open the last project (otherwise the same plugin would crash the application again before you could disable it) — a `startup` log entry. RPC: `plugins.lastCrash` → `PluginCrash | null`, `plugins.dismissCrash`. UI: once ready, `actions.plugins.offerCrashReport` (`App.tsx`) asks in a system dialog "Last time the application crashed in plugin X (track Y)… Disable the plugin?" [Disable]/[Keep] (text: `domain/plugins.ts: crashQuestion`, button labels: `SystemDialogs.confirm(…, buttons)`), then dismisses the report; after that comes the usual autosave restore offer. In the browser (mock) the dialog is checked with a `?pluginCrash` URL.
  * **Disabling a plugin.** `PluginScanner::set_disabled(kind, disabled)`, RPC `plugins.setDisabled { kind, disabled }`; the list is `Preferences::disabled_plugins` (JSON `disabledPlugins`, empty by default; changed only by `set_disabled`, which immediately rebuilds the catalog). The factory of a disabled plugin stays in the catalog, hidden: `EffectFactory::listed`/`InstrumentFactory::listed` = `false`, the registries (`daw-catalog`) do not return it from `kinds()`, and `create` returns `Unsupported` (the plugin is disabled, after a crash or manually; re-enable it in "Settings" → "Plugins") — and the project opens without that instrument (the track is silent) or effect (the node does no processing), with this message in `project.takeWarnings`. Already created instances keep working until the project is reopened. `plugins.list` returns `disabled: bool`; "Settings" → "Plugins" has a "Disabled" toggle in the table and "failed" marks on plugins that failed to load during the scan (`actions.plugins.setDisabled` re-reads the catalog and the settings, so that the next `preferences.set` does not bring back the old list).
  * **Limits (honestly).** This is a guess based on the marker, not isolation: a crash on another thread (the plugin window, our code, the plugin's own thread) at the moment the audio thread is inside the plugin will be blamed on the plugin; a crash in the plugin window (main thread) or in the plugin's own threads outside `process` is not caught at all; a plugin hanging in `process` is not detected (only if the user kills the application — then the marker will point at the plugin). One marker per state folder: two applications running at the same time with the same state folder will confuse the report (the second overwrites the first's file). Signals (`SIGSEGV`) are not intercepted: recovering from memory corruption caused by foreign code is impossible, so the application crashes as before. Panics in our own code already go to the log (`install_panic_hook`). A plugin that crashed while loading during a scan does not need to be disabled: it never gets into the catalog.
* **How to add something similar.** A new plugin format (CLAP) is a separate crate following the same pattern: scanner + `EffectFactory` + `Effect`, assembled in `daw-bootstrap`.
* **Instruments (VSTi).** `Vst3Instrument` is an `Instrument`: `prepare` sets the arrangement "no inputs, stereo main output" (`setBusArrangements`, checked with `getBusArrangement`); only the first output bus is active, the others and all input buses are disabled; 32-bit samples. `note_on/note_off/all_notes_off` do not touch the plugin: they write events into a `NoteQueue` (`notes.rs`, 256 events, pure code with tests; on overflow a `NoteOn` is dropped, while a `NoteOff` that did not fit is retried on the next `note_off`/`all_notes_off` — a stuck note is worse than a lost one). The host itself tracks sounding notes and gives each a unique `noteId`; a `NoteOff` carries the same `noteId`, and `all_notes_off` turns off all sounding notes. In `render` the events are passed to the plugin through the host's COM object `IEventList` (`host_events.rs`, channel 0, offset 0), the plugin renders into preallocated planar buffers (`ProcessRunner::render_add`, blocks larger than 8192 frames in chunks), and the result is **added** to the block. A block containing `NaN`/`inf` is discarded entirely (silence). `set_param` uses the same change queue as an effect. Factory: kind `vst3:<name>`, label "<name> (VST3)", parameters `p<id>`, `rebuild_on` empty. Lazy bundle loading and instance creation are shared with effects (`source.rs`).
* **Plugin state (preset).** The contract is `PluginState { component, controller }` and `PluginStates` (`daw-contracts/src/plugin_state.rs`): opaque bytes from `IComponent::getState` and `IEditController::getState`; in the model they are `InstrumentSpec::state` and `NodeKind::Effect::state` (`Option<Arc<PluginState>>`, `#[serde(default)]`, base64 in JSON, an empty `controller` and `None` are not written; Surge XT is ~50 KB, a third more in base64 — fine for a project JSON; `Arc` so that the undo history and engine snapshots do not copy the bytes). Factories and catalogs receive the state in `create(params, state)`: `CatalogEntry::create_with` applies it to the new instance on the control side (`instance/state.rs`: the component's `setState`, then the controller's `setComponentState` and `setState`; the byte stream is `stream.rs`, `MemoryStream: IBStream`), and the project parameters are applied on top (in the first block). If the plugin rejects the state, the instance is still created with the parameters, and the rejection is logged (`vst3`). Built-in kinds do not use state. The `PluginStates` implementation is `ProjectPluginStates` (`daw-project/src/plugin_states.rs`): `set` is one undo step "Plugin state" (the same state does nothing); DSP reconciliation (`service/sync.rs`) keeps the state in the instrument and effect key (`InstrumentKey`, `EffectKey`), so a new state **recreates** the sounding instance (it cannot be passed to a live instance from the audio thread), while parameter changes still go through `set_param`. Undo restores the previous state by the same recreation. Changing an instrument's kind discards the state (the same kind keeps it). State comes only from the plugin window (see "Plugin windows"): without a window there is nowhere for a new state to come from. `project.get` (RPC, UI, and AI) returns the project **without** states (`daw-rpc/src/project.rs: without_plugin_states`): these are bytes for plugins, and `project.get` is called after every edit; the project file does contain them. The frontend and the mock know nothing about state.
* **Transport time (`ProcessContext`).** Contract: `Instrument::set_timing` / `Effect::set_timing(&BlockTiming)` (no-op by default); the engine calls them on all instruments and effects before playing each segment (`engine.rs: process_segment` → `InstrumentRack::set_timing`, `GraphMixer::set_timing`). `BlockTiming::loop_region` is the transport loop, if it is enabled and playback is running. A VST3 effect and instrument hold a `PluginClock` (`context.rs`, pure code without allocations): before each `process` a preallocated `ProcessContext` is filled in (`ProcessRunner`, `ProcessData::processContext`): `kPlaying`, tempo, time signature, `projectTimeMusic` (quarter notes = ticks / PPQ), `barPositionMusic` (start of the current bar, from the segment's time-signature change, `BlockTiming::bar_start`), `projectTimeSamples` (ticks / ticks per frame of the segment — an approximation: with tempo changes it differs from the exact frame count; plugins sync to `projectTimeMusic`), `continousTimeSamples`, the loop (`kCycleActive|kCycleValid`, start and end in quarter notes). An instrument plays a segment in chunks between notes, and the position advances by the frames played. The position is the transport (source) position, **not** shifted by PDC: instrument plugins stay in time with the notes; an effect after a delayed path receives the same position as the sources (ahead by the amount of its input's compensation). Without the engine (drum part preview, tests) only continuous time is valid.
* **Current limitations.** macOS only; plugin windows — see the section below; an instrument receives only `NoteOn`/`NoteOff` (no pitch bend, controllers, aftertouch); additional output buses are not used; no sidechain; export runs in `kRealtime` mode (switching the plugin to `kOffline` would require a new `StreamConfig` field at every place it is created — not done; it does not affect the sound of most plugins); `ProcessContext` has no system time, SMPTE, or chords; a plugin that crashes in `process` still brings down the application — the protection only helps find and disable the culprit (see "Crash protection").

### Plugin windows (native VST3 UI)

The contract is `PluginEditors` (`daw-contracts/src/plugin_editor.rs`), the implementation is `Vst3Editors` (`daw-vst3/src/editors.rs`), and the application windows are in `app/src-tauri/src/plugin_window.rs`. A window's target is `EditorTarget::Effect { node } | Instrument { track }`.

* **A separate instance for the window.** `open` creates a NEW "component + controller" pair (`PluginInstance::create`, with an `IConnectionPoint` between them if the controller is a separate class) solely for the UI. Audio goes through the main instance in the engine; the window is a "view of the parameters". The main instance and the project know nothing about the window. The view is created with `createView("editor")`; `null` is an error (the plugin has no native window; the UI shows it as a toast, and the parameters remain knobs). A built-in effect or instrument is also an error (built-ins have no native window). The plugin is located by its catalog kind (`vst3:…`) through `PluginDirectory`: a directory of `PluginSource` shared with the factories (the bundle is loaded once); it is refreshed together with the catalog group on every scan.
* **Order.** `open` (create the view, get its size and whether it can be resized, apply the project values) → the application creates the window → `attach(id, the window's NSView)` (`IPlugView::attached`; `setFrame` is already set in `open`) → `sync` on a timer → `resize` when the window changes → `close` (`removed`, `setFrame(null)`, release the view, then the instance). One target, one window (a second `open` is `Invalid`; in that case the application raises the existing window without calling `open`).
* **Edits from the window → project ("ask, don't walk into someone else's office").** The window's host `IComponentHandler` (`editor_host.rs: EditHandler`) forwards `beginEdit/performEdit/endEdit` to `ParamBridge` (`param_bridge.rs`, pure logic without pointers), which converts the knob value into real units (`ParamScales`) and writes to the project only through contracts: `GraphControl::set_effect_param(node, "p<id>", v)` for an effect and `TrackControl::set_instrument_param(track, "p<id>", v)` for an instrument (`project_params.rs`; the plugin kind is also looked up there from the window's target). That is why a window edit is audible (the project publishes a snapshot to the engine), saved, and undoable. A gesture from `beginEdit` to `endEdit` is one undo step: `HistoryControl::begin_group/end_group` (the group is opened by the first knob and closed when all are released; when the window closes, an unclosed group is closed forcibly). Writes happen at most ~30 times per second per parameter (`MIN_WRITE_INTERVAL`); a held-back value is not lost — it is written by the `sync` tick or by `endEdit`. Parameters beyond the first `MAX_EXPOSED_PARAMS` (128) are unknown to the project: their window edits do not reach the project as parameters (one log entry per window) — they are saved in the plugin state (below). `restartComponent` with `kReloadComponent`/`kParamValuesChanged` and an edit of a parameter unknown to the project produce a "state changed" message for `StateSync`; other flags are not needed.
* **Project → window (`sync`).** About every 100 ms the main thread calls `sync(id)`: it reads the target's current values from the project and writes the changed ones into the window's controller (`setParamNormalized`) — this way the window sees automation and edits from other panels. A knob currently being held and values that have not yet reached the project are not overwritten; echoes of its own values are ignored. If the target is gone from the project (the track or effect was deleted), `sync` returns an error and the application closes the window. A plugin's request to resize (`IPlugFrame::resizeView`, `ResizeFrame`) is remembered and returned from `sync` as `Some((w, h))`: the window resizes on the next tick, without callbacks from foreign code.
* **Window state ↔ project.** The user picks a preset in the window, i.e. in the window's instance, so the window's whole state is carried to the project and back (`Vst3Editors` + pure logic in `editor_state.rs: StateSync` + the `PluginStates` contract). On opening, the window receives the target's saved state (and then the project's parameter values on top), so the window and the sound match; this is remembered as "agreed" (the window's bytes). A change message from the plugin → after `SETTLE` (1 s) of quiet, on a `sync` tick, the window state is written to the project (`PluginStates::set`: undo step "Plugin state", the sounding instance is recreated with it) if it differs from the agreed one. Knobs known to the project do NOT write state (otherwise the sound would be interrupted by recreation on every move) — they go as parameters. On window close and in `store_states` (before the project is saved or rendered: the `PluginStateFlush` contract, which `app/src-tauri`'s `PluginWindows` implements by running `store_states` on the main thread; the RPC table calls it before every method registered with `add_flushing` (save, create, preset and template save, bounce, freeze, export, level analysis, mix check), whether the call came from the window or the in-app AI server) the state is written if it differs from the agreed one (opened and closed without edits — nothing; turned some knobs — one "Plugin state" step and a recreation on close). A target state changed from outside (undo/redo) is picked up by the window on `sync` (`StateSync::outside`): it loads it (or its own initial state, if the project no longer has a state) and re-applies the project parameters (`ParamBridge::forget_shown`). Failures (the plugin did not return or did not accept the state, the write failed) go to the `vst3` log; a deleted target is not a failure. Autosave does not poll windows: changes reach the project within a second, which is enough.
* **Threads.** EVERYTHING that touches the plugin and the window (`open/attach/resize/sync/close`, creating the `NSWindow`) runs on the MAIN thread: `AppHandle::run_on_main_thread`. The window timer is a separate thread that only asks the main thread to tick while there are open windows. `Vst3Editors` keeps windows under a `Mutex` and is marked `Send`/`Sync` only for the trait; safety relies on the convention "call from the main thread". Plugin edits also arrive on the main thread and go straight to the project.
* **Application window.** It is a `tauri::window::WindowBuilder` WITHOUT a web page (requires the `unstable` feature of `tauri`): the parent for the plugin is the window's `NSView` (`Window::ns_view()`), and the host itself makes no AppKit calls, so `unsafe` was NOT needed in `app/src-tauri` (the rule "`unsafe` only in `daw-vst3`" is not violated; `workspace.lints.unsafe_code = "forbid"` would not allow a targeted `allow` anyway). The size comes from `EditorSession` (logical pixels), the title is the plugin name, resizability follows `canResize`. Closing the window → `close(id)` before the `NSWindow` is destroyed (the plugin detaches its view); user resize → `resize` (`IPlugView::onSize`); a plugin's size request → the window resizes. One window instance per target: pressing again raises the existing one. Closing the main window and quitting (⌘Q) close all plugin windows before anything else; closing the main window quits the application (as before, when it was the last one).
* **The only exception to "everything through `daw-rpc`".** The `pluginEditor.open` method (`params: { target: { type: "effect", node } | { type: "instrument", track } }` → `null` or an error) is handled by name in the application's `rpc` command (`app/src-tauri/src/main.rs`) BEFORE the shared table: the window needs Tauri's `AppHandle`, and `daw-rpc` intentionally knows nothing about Tauri (it is only JSON ↔ contracts). All other methods go through `RpcTable` unchanged. Frontend: `api.pluginEditor.open` → `actions/pluginEditor.ts` (errors shown as a toast) → the "Plugin window" button in the effect node inspector (`ui/graph/Inspector.tsx`) and in the instrument window (`ui/tracks/InstrumentWindow.tsx`), only for `vst3:…` kinds; the browser mock responds with an error (the plugin window is available only in the app, not in the browser).
* **Tests.** The "knobs ↔ project" logic (write rate, undo group, echo, `p<id>` names, stub `GraphControl`/`TrackControl`/`HistoryControl`), `StateSync`, `MemoryStream`, `PluginClock`, and the window's COM objects have unit tests in `daw-vst3`; `tests/editors.rs` creates and closes windows on the real Surge XT and Distortion without showing them; `tests/state.rs` tests state on real plugins: our synth's window → project → a new instance sounds the same as with the same parameters; the window follows undo; a corrupted state is a log entry, not a refusal; Surge XT with state and `ProcessContext` produces sound; Distortion — the same for an effect. The `PluginStates` contract (undo step, recreation, undo, target errors, saving) is tested in `daw-project/src/tests/plugin_states.rs`; a full session with the built-in synth (window → state → file → open → undo) in `daw-bootstrap/tests/plugin_state.rs`; segment timing of DSP objects in `daw-engine/src/tests/timing.rs` Embedding the plugin interface into a real window (`NSView`), the Tauri window, dragging, input and focus are checked by the owner by hand: a test of real embedding cannot run on CI runners (no GPU for OpenGL interfaces), so there is none.
* **Limitations.** A new window state reaches the sound by recreating the instance (a second after a preset change, on window close, before saving): notes sounding at that moment are cut off. A plugin that changes its state without reporting it (`restartComponent`) and without touching parameters reaches the project only on window close or save. For plugins with a separate controller, the window's component does not process audio and may not know about edits from the window — those are carried by the project parameters on top of the state. Plugin window hotkeys, `IPlugViewContentScaleSupport`, `IComponentHandler2/3`, `IContextMenu`, `checkSizeConstraint`, and multiple windows per target are not supported. A plugin crashing in its window brings down the application (plugins live in our process).
* **Test plugin.** `test-plugins/distortion` has a simple native UI (`nih_plug_egui`, 360×240, five sliders) — handy for testing windows without Surge XT.
* **Keys in the instrument window.** A plugin window has no web page, so the main window's hotkeys (`keyboardPiano.ts`) do nothing in it. On `attach` of an instrument window, `Vst3Editors` asks `EditorKeys` (`daw-vst3/src/keys/`: `mod.rs` — window subscription, `mac.rs` — `NSEvent` monitor, `piano.rs` — layout) to listen to that window: a local `NSEvent` monitor (only events of our own application; no input permissions needed) passes keys to `KeyPlayer` (`keys/piano.rs`, pure logic with tests), which plays through `LiveNoteSink` on that instrument's track. The layout is the same as in `app/src/domain/keyboard.ts` (Z X C V… and Q W E R…, black keys S D G H J / 2 3 5 6 7, `[` `]` — octave), but by macOS key codes: **when changing the layout in one place, update the other**. Plugin windows have their own octave (4 by default), unrelated to the main window's octave; a key release is caught in any window, and closing the window releases its notes. Other platforms do not intercept window keys yet.
* **Test plugins (dev-only fixtures).** `test-plugins/synth` (`Synth.vst3`, kind `vst3:synth` once scanned; native 720×440 window with envelope and filter curves, an oscilloscope and a keyboard) and `test-plugins/distortion` are nih-plug plugins (separate workspaces, GPL) that exist only to test this host: `crates/daw-vst3/tests` (scan, sound, state, windows, the isolated scan), `daw-bootstrap/tests` (`start_with_fixture_plugins`: a headless session with `SessionConfig::plugin_dirs` pointing at `test-plugins/*/target/bundled`, scanned in-process) and `daw-rpc/tests/all/settings.rs`. Build them with `scripts/build-test-plugins.sh`; without the bundles those tests print `SKIPPED` and pass. They are not shipped, not in the catalog by default, and the app never loads them: instruments and effects of the DAW are built in (the owner's rule: never VST3 plugins of our own).

## Drum patterns (`daw-patterns`)

A pattern is a drawing on a 16th-note grid, one row per drum: `X` accent, `x` normal, `o` soft, `.` rest (`"X... .... X... ...."`). Roles: `groove` (the main rhythm), `fill` (a full bar, placed as the last bar of a phrase), `break` (a stop/drop), `intro`, `ending`. A pattern is 1 or 2 bars; `data.rs` has ~50 of them. A new pattern = a new entry in the `PATTERNS` table; the `every_builtin_pattern_is_valid` test checks grid lengths, drums, and duplicates.

**A part** = `DrumPartRequest { startBar, slots: [{ pattern, repeat }], replace }`: patterns are placed one after another starting at `startBar` (zero-based bars). `DrumPartBuilder::build` validates everything up front (patterns, drums, occupied space) and then builds in a single undo group (`begin_group`/`end_group`); on a failure midway it rolls the group back. Each drum gets one track of the right kind: an existing one (the topmost) or a newly created one (names in `createdTracks`); each pattern and drum gets one note clip `bars × repeat` bars long, whose content is a single pattern (`loop_ticks` is fixed), so repeats loop inside the clip, and editing one drawing changes all repeats. Notes follow General MIDI (kick 36, snare 38…), so MIDI export looks familiar. Occupied space: `replace: false` — rejected with an error, `true` — the drum clips in that range are deleted.

**Your own sounds.** A pattern only says "kick, snare, hi-hat…" — what plays them is decided by the request: `lanes: [{ lane, target }]` (drums without an entry are `auto`). `target`: `auto` — a built-in drum (your track of the same kind is used if there is one, otherwise one is created); `skip` — the drum does not play; `{ type: "track", id, pitch? }` — your track (notes at pitch `pitch`, by default the track's step-input pitch; for a sampler that is the root note, so the sound plays unshifted); `{ type: "sample", id }` — your sample from the project: a sampler track "Kick: sample name" is created. Several drums can be sent to one track — their hits merge into one clip (coinciding notes of the same pitch become one, louder). Everything is validated before any edits: an unknown drum, an audio track instead of an instrument track, a nonexistent track or sample — rejected without leaving traces. The sound choices in the dialog are remembered between builds (`session.drumKit`); a choice that no longer exists is treated as `auto`. Example: `drums.build { "slots": [{"pattern":"rock_basic","repeat":4}], "lanes": [{"lane":"kick","target":{"type":"track","id":5}}, {"lane":"snare","target":{"type":"sample","id":2}}, {"lane":"crash","target":{"type":"skip"}}] }`.

**Preview.** `DrumPartPreviewer` (`DrumPartPreview`) plays a part WITHOUT changing the project: the same patterns and the same drum sounds (`lanes`) that a build would produce are rendered once into a temporary 48 kHz stereo buffer (one instrument per track/drum, created through `InstrumentCatalog`, at the project tempo), cymbal tails are wrapped around to the start of the loop, and the buffer goes to the engine's existing preview voice (`DspCommand::PreviewPlay`, looped) — no engine changes were needed. It plays until `stop` is called; a new `play` replaces the previous one; at most 16 bars. The "drum → sound" choice is resolved by the shared `LaneKit` (`kit.rs`), which the part build also uses, so what you hear matches what will be built.

RPC: `patterns.list` (`{ style?, role? }`, patterns with grids as strings), `patterns.get { id }`, `drums.build`, `drums.preview` (the same request as `build`), `drums.stopPreview`. UI: the "🥁 Drum part" button above the timeline (in the dialog each pattern has "▶ Listen" and there is "▶ Preview part" — looped until you press "■ Stop"; closing the dialog stops the sound) (`ui/drums/DrumPartDialog.tsx`), actions `session.actions.drums.*`. Example for AI: `drums.build { "slots": [{"pattern":"intro_crash_start"},{"pattern":"rock_basic","repeat":6},{"pattern":"fill_tom_cascade"},{"pattern":"rock_drive","repeat":7},{"pattern":"fill_snare_roll"},{"pattern":"ending_crash_stop"}] }`. The browser mock (`mock/handlers/drums.ts`) knows only 8 patterns and builds a part with separate edits rather than one undo step.

## Chord parts (`daw-patterns`: `chord_part.rs`, `strum.rs`, `voicing.rs`)

A chord progression strummed on one instrument track. **Contract** (`daw-contracts/src/chord_part.rs`): `ChordPartRequest { target, startBar, strum, bars, repeat, replace }` — `target` is `{ "type": "track", id }` or a new track `{ "type": "new", kind }` (named after the kind's label); `bars` holds one or two chord **symbols** per bar (`[["C"], ["G"], ["Am", "F"]]`; the second chord starts in the middle of the bar), read by `Chord::parse`: a root C…B with an optional `#`/`b`, then `""`, `m`, `7`, `maj7`, `m7`, `sus2`, `sus4`, `dim`, `aug`. **Strums** (`STRUMS`, data in the contract like `TRACK_COLORS`): one 4/4 bar of eighth notes — `D` down, `U` up, `X` a muted down stroke (a "chuck"), lower case softer, `.` nothing; `four` `D.U.X.U.`, `six` `D.DU.UDU`, `eight` `DUXUDUXU` — the "бой четвёрка / шестёрка / восьмёрка" of the Russian guitar tradition. Like drum patterns they are not reshaped for another meter.

* **How the instrument plays** (`voicing.rs`, by the target's instrument kind): the guitars (`GUITAR_KIND`, `ELECTRIC_GUITAR_KIND`: E2–E4 standard tuning, the same shapes) and the ukulele (`UKULELE_KIND`, re-entrant G4 C4 E4 A4) voice the chord like a player — one note per string, an open string where it is a chord tone, a fretted one within one hand position (four frets), positions up to the 7th scored by: all chord tones, more strings, open strings, a lower position; the guitar's lowest note is the root (C = x32010, D = xx0232, G7 = 320001). The bass (`BASS_GUITAR_KIND`) plays the root from E1 up an octave, on down strokes only. Any other instrument plays a block chord from C3.
* **Strumming** (`strum.rs`): a down stroke runs over the strings from the first to the last, an up stroke back over the top four, each string 12 ms later (`spread_ticks`, at the part's starting tempo, at most 1/12 of a step) and 3 velocity steps softer; the bar's first stroke is accented. A string rings until a stroke hits it again, the chord changes, or a muted stroke stops every string (its own notes are 1/8 of a step: the strings damp them at once). Everything ends with the progression; the clip's content is one pass (`loop_ticks`), so repeats loop inside it and editing one pass changes all.
* **Build** (`ChordPartBuilder`): `chord_part::plan` checks everything first (the strum `PT-074`, no bars `PT-174`, too many `PT-275`, one or two chords per bar `PT-175`, symbols `PT-103`, repeats `PT-271`, the track `TR-001`/audio `PT-176`/kind `TR-002`, the start bar `PT-272`) and works out the notes; occupied space is `PT-370` or replaced; then one undo group ("Chord part"): the new track, the removed clips, one note clip; a failure rolls the group back. **Preview** (`ChordPartPreviewer`): the same plan, every repeat, played by the target's instrument (a new kind with its defaults) into a buffer and looped by `render.rs` (shared with the drum preview); at most 16 bars (`PT-274`).
* **RPC:** `chords.strums`, `chords.build`, `chords.preview`, `chords.stopPreview`; the MCP instructions mention the workflow. **UI:** "🎸 Chord part" above the timeline (`ui/chords/ChordPartDialog.tsx`): the progression as bars (`ProgressionBars`: select a chord, split a bar in two with ½, add and remove bars), the key's own chords and any root + type (`ChordPalette`; until edited, the starting I–V–vi–IV / i–VI–III–VII follows the key), the rhythm (`StrumPicker`, arrows from `domain/chordPart.ts: strumArrows`), the track (a new acoustic or electric guitar, ukulele or bass, or yours), start, repeats, replace; "▶ Listen" loops the part and plays it anew after every edit. Pure logic — `domain/chordPart.ts`; actions — `session.actions.chords.*`. The browser mock (`mock/handlers/chords.ts`) writes block chords from C3 on every stroke with separate edits.
* **Tests:** symbols and strums — `daw-contracts/src/chord_part.rs`; voicings (the open shapes, every chord on every instrument) — `voicing.rs`; strokes, ringing, chucks, chord changes, the bass — `strum.rs`; one undo step, voicing on a real session, occupied space, refusals, preview and playback — `daw-bootstrap/tests/all/chord_part.rs`; wire — `daw-rpc/tests/all/chords.rs`.
* **A new strum:** a row in `STRUMS` (and the mock's `STRUM_GRIDS`). **A new string instrument:** its kind in `daw-strings` and a tuning row in `voicing.rs: style`.

## AI interface: RPC self-description and the MCP server (`daw-rpc`, `daw-mcp`)

**Self-description.** Every `RpcTable` method has a description (one sentence on "what it does", the second argument of `RpcTable::add(name, description, adapter)` — the description sits next to the adapter, so it cannot be forgotten) and a JSON schema of its parameters. The schema is generated from the parameter struct (`P: JsonSchema` in `RpcTable::add`), so a method cannot be added without a schema — it will not compile. Responses are the contract types themselves (`SampleInfo`, `Waveform`, `AudioStatus`, `KindInfo`…) with `serde` attributes matching the UI's JSON shape; there are no separate DTOs. RPC modules are split by area (`samples.rs`, `preview.rs`, `sounds.rs`, `midi.rs`, `live.rs`, `catalog.rs`…); `library.home` (the default folder for new projects) is in `project.rs`. Tests are in `daw-rpc/tests/<area>.rs` with helpers in `tests/common/`. Parameter structs and contract types that come from JSON derive `JsonSchema` (`schemars`); nested types are inlined into the schema without `$ref`. The whole catalog is the `rpc.describe` method (name, description, schema). **A new RPC method = a `table.add(name, description, adapter)` line in the area's module: the AI will see it on its own.** Parameters can also be a contract type itself if it derives `Deserialize + JsonSchema` (`clips.addNote` takes `NewNoteClip`: `{ track, startTick, lengthTicks?, notes?, loopTicks? }` — a clip with notes in one call and one undo step; the mock is `mock/handlers/clips.ts` with content rules in `mock/noteOps.ts`).

**The `daw-mcp` MCP server.** A tool = an RPC method (name with `_` instead of `.`: `drums_build`); the description and input schema come from `RpcTable::describe`, and a method without parameters gets an empty object schema. The protocol is JSON-RPC 2.0; the logic is the pure function `McpServer::handle`. A method error is a normal result with `isError: true` and the text `CODE: message` (a registered error code, see "Errors as codes"), so the AI can fix the request; an unknown tool is a protocol error. In `initialize` the server sends short instructions (start with `project_summary`, not the whole `project_get`; time in ticks, ids, the workflow for drums, batch clips `clips_addNoteMany`, clearing with `project_clear`, one undo step per user request — `history_checkpoint` … `history_squash` (see "Project core"), and the rule "before saying "done", run `analysis_check` and fix the findings"). `pluginEditor.open` (plugin windows) is not in the catalog.

Three ways to connect an AI (`scripts/build-mcp.sh` prints the commands for Claude Code; the repository root has a `.mcp.json` with the first two):
1. **Inside the application (primary).** The DAW window itself starts an MCP HTTP server at `127.0.0.1:47321/mcp` (`app/src-tauri/src/ai_server.rs`) after the startup project is opened. The AI works in the SAME project that is open on screen: edits go through the same contracts, and the window updates on the usual project-changed event; an AI edit is undone with the normal undo. Connecting: `claude mcp add --transport http daw http://127.0.0.1:47321/mcp`. Port: `DAW_MCP_PORT`; to disable: `DAW_MCP=off`; if the port is busy, the application keeps working and logs a warning.
2. **Bridge `daw-mcp --attach [--port N]`.** For clients that can only launch processes (stdio): lines from stdin are sent as POST requests to the running application's server. If the application is not running, each request gets an error.
3. **Headless `daw-mcp [--audio] [--project PATH] [--state-dir DIR]`.** Its own session, no audio (the AI works with the project in memory; `project_save` and `project_export` produce files); its own state folder (`…/DAW-MCP`) so it does not share autosaves with the window.

**HTTP server protection.** It listens only on `127.0.0.1`. A request is rejected (403/415/405/404, with no effect on the project) if it has an `Origin` header (browsers always send it, ordinary clients never do: a foreign website cannot control the program), a foreign `Host` (DNS rebinding), a `Content-Type` other than `application/json` (that is how "simple" browser requests bypass the preflight check), or a path/method other than `POST /mcp`. Requests are served one at a time on a single thread, so project edits do not race each other. There is no access key: any local program running as your user can control the application while it is running — set `DAW_MCP=off` if you do not need this.

## Project core: history, groups, checkpoints, whole-project reads (`daw-project/src/service/`)

* **Whole-project reads — `ProjectView`** (`snapshot`, `revision`), implemented by the `ProjectService` core itself; in `Controls` it is `controls.view`. Used by `project.get`, export, autosave, and telemetry. `ProjectIo` (`ProjectFiles`) is only the file lifecycle: which file is open, create/open/save/restore, warnings.
* **Tempo and time signature are part of the project** (`Project::tempo_map`, edited via `ProjectTempo`/`TempoControl`, see "Tempo map"): an edit is undoable, marks the project as modified, and is heard immediately — the map travels to the engine in the snapshot. The transport does not store tempo. The loop is also project data; it is only passed to the transport.
* **Edit groups** (`HistoryControl`): `begin_group`/`end_group` nest (inner levels join the outer one; the step is recorded when the outermost one closes; `end_group` reports whether a step was recorded); `cancel_group` returns the project to the state at the outermost `begin_group` and closes all levels (this is how a part build, cutting sample regions, and the starter beat are rolled back); while a group is open, `undo`/`redo` refuse. The group is shared for the whole project: edits from any source during that time become part of it. `mark_baseline` means "as if just opened": empty history, no edits.
* **Checkpoints** (`HistoryControl::checkpoint`/`squash`): a change made of many separate calls (an AI request over MCP) becomes one undo step after the fact. `checkpoint` returns a `HistoryMark` — the number of the step on top of the undo stack (every step gets a session-unique number, `service/history.rs`), or of the stack bottom (`root`) when it is empty; `squash(mark, label)` replaces every step above the mark with one step labelled `label` whose "before" state is the state at the mark, and publishes a new revision so the window re-reads the undo label. Why not a group: a group held open between calls would block the user's undo, and a compound call failing midway (`drums.build`) cancels the whole group — everything the AI did before it; a checkpoint holds nothing open. A mark expires when its point leaves the history: undone past it (and then edited), the history cleared (`root` gets a new number), or the step limit forgets its state (`root` moves to the forgotten step's number, so a mark whose own step was the one forgotten is still the bottom and stays valid). `squash` refuses an empty label (`HS-101`), an expired mark (`HS-301`), and an open group (`HS-302`: edits inside it are not steps yet). Both reset knob-edit merging, so a slider move does not join a step across the mark. RPC: `history.checkpoint`, `history.squash { since, label }`; the MCP instructions ask the AI to wrap each user request in them.
* **DSP reconciliation** (`sync.rs`): create missing instruments and effects → publish a snapshot → remove the extra ones. A failure to create or hand over an object goes to the log (`source: "dsp"`) and to the project warnings; a failed attempt is not repeated on every edit until the kind/parameters change or the project is reopened.
* **Limits** are contract constants next to the traits (`MAX_TRACKS`, `MAX_CLIPS`, `MAX_NOTES_PER_CLIP`, `MAX_LANES`, `MAX_POINTS`, `MAX_REGIONS`…); implementations take them from there.
* When a sample is deleted, resetting instruments' sample selection looks for parameters of kind `ParamKind::Sample` in the catalog, not by name; the built-in sampler's names are the constants `SAMPLER_KIND`, `SAMPLER_SAMPLE_PARAM`, `SAMPLER_ROOT_PARAM` (`daw-contracts/src/instrument.rs`).
## Warping audio clips to tempo, pitch, and crossfades

**Model** (`daw-contracts/src/warp.rs`, `Clip` fields): `warp: Option<Warp { source_bpm }>` — the audio was recorded at `source_bpm` and is stretched by a factor of `source_bpm / tempo`, so a loop stays in beats; the length of such a clip in ticks does NOT depend on the tempo (it is computed in beats of the source tempo: `Clip::ticks_to_source_frames` / `source_frames_to_ticks` — the single formula, used by split, the rules, and the engine). `pitch_semitones` (±24, to hundredths) — pitch without changing length, both with and without warp. Processing: time-stretch by `stretch × 2^(s/12)` (WSOLA: ~40 ms Hann windows, the window offset chosen by waveform similarity — coarsely on decimated mono, then precisely) and resample the frames back to `stretch` (cubic interpolation, with a low-pass filter when shrinking) — `daw-stretch/src/{wsola,resample}.rs`. 30 s of stereo takes ~0.2 s in release.

**Editing** (`ClipControl::edit_clip`, rules in `daw-project/src/warp_rules.rs`): `ClipEdit.warp` — `Some(Some(WarpEdit { source_bpm }))` enables warp / changes the tempo (`None` — guess: a number with "bpm" in the file name, otherwise a standalone number 60–200 in the name, otherwise length = 1/2/4/8/16 bars of 4/4 at a tempo of 70–180, closest to 120; if nothing is guessed — the project tempo), `Some(None)` (JSON `null`) disables it. When warp changes, the clip keeps the same piece of audio: the length is recalculated; an explicit `lengthTicks` in the same edit takes precedence. RPC is the same `clips.edit`: `{ "warp": {} }` to guess, `{ "warp": { "sourceBpm": 128 } }`, `{ "warp": null }`, `{ "pitchSemitones": -2.5 }` (there is no separate `guessBpm`: guessing is part of enabling, and the guessed value is visible in the response). MCP sees this from the method description.

**Audio outside the audio thread.** Contract `ProcessedAudio` (`ready` — the finished result, or queue in the background without waiting; `compute` — with waiting, for export; `finished` — a counter of completed computations; `retain` — what is still needed). The key is `ProcessJob { sample, stretch (to 1e-6), pitch (to 0.01), curve? }`. Implementation `StretchCache` (`daw-stretch/src/cache.rs`): one background thread `daw-stretch`; a job that stopped being needed while waiting in the queue is not computed (moving the tempo quickly doesn't pile up work); a failure goes to the log (`source: "stretch"`), with no retries; memory — `retain` drops everything not in the latest snapshot. A stretch outside 0.25…4 is rejected (the sound would be ruined and memory would grow several-fold). The core (`service/sync.rs: collect_clip_audio`) puts `EngineSnapshot::clip_audio: (ClipId, take) → ClipAudio { data, start_frame }` into the snapshot for every sounding take of a clip with warp or pitch (`Clip::sounding_takes`: the active one or the comp takes): the finished audio, and while new audio is being computed — the previous audio of the same take of the clip (not silence); if no processing is needed — the sample itself. `start_frame` is the audio frame at the start of the clip. The job is `ProcessJob::for_clip(clip, take, &TempoMap, rate)`. A tempo change is a project edit: the snapshot and the new computation follow automatically; a finished background computation does not publish a snapshot, so it is noticed by the watcher `daw-bootstrap/src/clip_audio_watch.rs` (a ~20 Hz thread): `finished` grew → `ProjectService::refresh_clip_audio()` (only if such clips exist). Export (`daw-render`) finishes computing the audio via `compute` and on failure refuses with a clear error.

**Warping across tempo changes.** If the tempo changes inside a warped clip (there is a point with a different tempo, or the clip starts inside a ramp), there is no single stretch: the job carries a curve `StretchAnchor { source, output }` (source audio frame → processed frame from the clip start): a beat of the audio lands on the tick where the source tempo puts it, and the time of that tick is taken from the map. Points — the start, every tempo point inside, a 120-tick step inside ramps, the end; linear in between. Only the clip's piece is processed (`start_frame` = 0). `daw_stretch::process_curve` is the same WSOLA, but the "expected" position of the input window is taken from the curve (`wsola::stretch_mapped`; a constant stretch is a special case of it, so a clip without a tempo change inside sounds exactly as before, and its jobs are unchanged). The cache key is the points themselves: they depend only on the tempo points inside the clip and the tempo at its start, and on the clip's position, offset, and source tempo, so a tempo change outside the clip recomputes nothing, while moving or trimming a clip with a tempo change inside does recompute. Each piece of the curve stays within 0.25…4. Tests: `daw-stretch/src/tests.rs` (click beats after a step and inside a ramp land where the map puts them; a straight curve = a single stretch), `daw-contracts/src/warp.rs`, `daw-project/src/tests/warp.rs`.

**Engine** (`daw-engine/src/audio_voices.rs`): a clip with warp or pitch (`Clip::has_sound_processing`) plays only from `clip_audio` (no entry — it stays silent rather than playing the file out of time); the position in the audio = `start_frame` (for a sample — `offset_frames`, for a single stretch — `offset_frames × stretch`, for a curve — 0) + frames from the clip start along the tempo map. If the clip's audio in a new snapshot is different (recomputed for a new tempo), the playing voice switches to it at the same clip position, and the old audio goes to the release queue (like everything in the audio thread).

**Crossfades.** Audio clips on the same audio track may overlap at their edges: at most two at any point, a clip does not lie inside another and does not start on the same tick as it (`clip_rules.rs: check_track`, on the resulting state; note clips still do not overlap). An overlap plays as an equal-power crossfade the length of the overlap (`Clip::crossfades` gives the fade-in and fade-out lengths; the voice multiplies by `sin` of the overlap fraction on top of the regular fades): these are two ordinary voices, with no allocations. The frontend repeats the placement rules in `domain/clips.ts` (`trackPlacementProblem`, `canPlace`, `crossfades`; used by sample drop `domain/dropSample.ts`; the mock `mock/clipRules.ts` checks the same rules with the backend's codes), and the timeline draws an overlap as shading with an "X" (`timelineRender.ts: drawCrossfade`). Drag an audio clip onto the edge of another and you get a crossfade.

**UI.** A selected audio clip opens `ui/pianoroll/AudioClipPanel.tsx` in the clip panel: "Warp to tempo" (`actions.clips.setWarp`), "Source tempo" (`setSourceBpm`), "Pitch, semitones" (`setPitch`); the clip label on the timeline is "⟲ 128", "↕ +3" (`domain/warp.ts: warpMarks`), and the waveform reads the audio at the clip's tempo (`clipTempo`). Pure frontend rules (tempo guessing, length recalculation) are in `domain/warp.ts`; the mock applies them without real DSP (lengths only). For similar clip audio processing (reverse, normalization): a field in `Clip` → a condition in `ProcessJob::for_clip`/`Clip::has_sound_processing` → computation in `daw_stretch::process` → an edit rule next to `warp_rules.rs` → a field in the panel.

**Limitations.** WSOLA has no separate transient handling: heavy stretching smears hits; frame resampling is cubic, not polyphase; while audio is being computed after a tempo change, the clip briefly plays the previous computation; the time signature when guessing by length is always 4/4.

## Audio clip editing: fades, gain, trim, normalize, reverse

**Fades.** `Clip { fade_in_ticks, fade_out_ticks, fade_in_shape, fade_out_shape }`; `FadeShape { Linear, EqualPower, SCurve, Exponential }` with one formula `FadeShape::gain(progress)` (`daw-contracts/src/clips.rs`, allocation-free) that the engine applies per frame (`audio_voices.rs: fade_at`, on top of the equal-power crossfades), so export sounds the same; the frontend draws the curves with the same formulas (`domain/fades.ts: fadeGain`). Shapes are set by `ClipEdit { fade_in_shape, fade_out_shape }`; fade lengths are clamped to the clip length (no other cap). A new shape: add the variant and its formula in both places.

**Trimming the start.** `ClipControl::trim_start(id, tick)` (RPC `clips.trimStart`): the left edge moves, the end stays, the content stays in place — an audio clip's `offset_frames` moves by the frames those ticks play (`Clip::ticks_to_source_frames`), stopping at the file start; a note clip's `offset_ticks` turns around its loop; the comp shifts (`take_rules::shift_comp`, also used by split). Pure rule: `clip_rules.rs: trim_start`; the frontend preview and the mock share `domain/clips.ts: trimmedClip`.

**Normalize and reverse** (`ClipProcessing`, `daw-project/src/clip_processing.rs`). Two roles split by rule 8: the clip side decides what changes (gain; which sample and offset), the sample editor does the audio work through its contract — `SampleEditor::peak(id, from, to)` measures, `SampleEditor::reverse_copy(id)` writes a reversed WAV into the project folder and imports it (needs a saved project, `samples::REVERSE_NEEDS_SAVED_PROJECT`). `normalize(ids, peak_db)` is non-destructive: the peak of the source frames each clip plays (all takes, from `offset_frames` for the clip length) sets `gain = 10^(peak_db/20) / peak`, capped at `MAX_CLIP_GAIN` (silent clips keep their gain), one edit. `reverse(id)` points the clip at the reversed copy with the mirrored offset (`total − (offset + played)`), so the same piece plays backwards in place; it is a history group (import + clip edit), cancelled on failure; clips with several takes are refused (`clips::REVERSE_NEEDS_ONE_TAKE`). RPC: `clips.normalize { ids, peakDb? }` (default −0.3 dBFS), `clips.reverse { id }`. Mock: `mock/handlers/clips.ts` (normalize assumes a fixed peak).

**Timeline UI.** `timelineRender.ts: drawAudioHandles` draws the fade curves (shaded above the curve), fade handles on the top edge where each fade ends, and the gain line (when selected or not at 0 dB); geometry and hit-testing are in `timelineLayout.ts` (`audioZoneAt`, `gainLineY`, `draggedGain`, `trimStartAt`). `timelinePointer.ts`: drag a fade handle (grid-snapped, `domain/fades.ts: fadeLengthAt`), drag the gain line (dB tooltip, Shift — fine), drag the left edge (trim, `actions.clips.trimStart` with the drawn `trimmedClip`, shown until the backend replies); edits are drawn as `ClipDraft.edited` and committed once on release. Right-click on an audio clip opens `ClipMenu.tsx` (Normalize — the selection if the clip is in it, Reverse, fade shapes, Delete; on a fade — only that fade's shapes); right-click on a note clip still deletes it. The toolbar gain slider goes to `MAX_CLIP_GAIN` (×4). Tests: shapes — `daw-contracts/src/clips.rs`, engine — `daw-engine/src/tests/audio_clips.rs`, trim — `daw-project/src/tests/clips.rs`, normalize/reverse — `daw-project/src/tests/clip_processing.rs`, wire — `daw-rpc/tests/all/editing.rs`.

## Built-in effects (`daw-effects`)

Each effect is a module with a parameter table `PARAMS` (`ParamInfo` in real units, labels as `L10n` English + Russian pairs, choices via `ParamKind::Choice` with `choices`) and an implementation of `EffectKind` (kind, label, `new`) + `Effect`; the factory is shared (`lib.rs: build::<E>`, `Factory<E>`), and registration is a line in `factories()` (taken by `daw-bootstrap/src/wiring/catalogs.rs`). `clamp_param` normalizes a value via `ParamInfo::fit` (for a choice — an integer index: choice automation arrives as a fraction). `build` calls `reset` at the end, so a new effect's smoothed parameters start at their values immediately.

* **Parameter smoothing** (`smooth.rs`: `Smoothed`, `SMOOTH_MS` = 10 ms): the engine sends parameters once per block, and the step would be audible as a click. The filter smooths cutoff (logarithmically), resonance, mix, and output weights (a type change is a transition between the LP/HP/band outputs); the saturator smooths drive, output, mix, and curve weights. On a time (and tempo) change the delay does a 20 ms transition from the old echo to the new one (`FADE_MS`) rather than "sliding" the time: a fast slide would produce a pitch squeal.
* **`filter` "Filter"** (`filter.rs`): Simper's SVF (trapezoidal) — stable under fast automation of cutoff and resonance up to 12; parameters `type` (LP/HP/Band), `cutoff` 20…20,000 Hz, `resonance` (Q 0.5…12), `mix`. The band output is normalized (0 dB at the cutoff).
* **`gate` "Gate"** (`gate.rs`): `threshold`, `attack`, `hold`, `release`, `range` (how much to attenuate when closed), `sidechain` (the key works like the compressor's: the signal at the node's sidechain input). It opens above the threshold, closes `HYSTERESIS_DB` = 6 dB below it and only after the hold; the level detector has a 10 ms decay.
* **`distortion` "Distortion"** (`distortion.rs`): `drive`, `tone` (Butterworth lowpass 200…16,000 Hz after the curve), `mix`, `output`, `shape` (Soft — tanh, Hard — clipping, Foldback — a triangle fold that turns loud peaks back); drive, mix and output are smoothed; a NaN/inf input sample becomes silence. It replaced the former test plugin `test-plugins/distortion` feature for feature.
* **`saturator` "Saturator"** (`saturator.rs`): `drive`, `type` (Soft — tanh, Tube — offset tanh with even harmonics, Hard — clipping), `output`, `mix`. The curve is computed at double the sample rate (linear interpolation up, 4th-order Butterworth and decimation down) — aliasing is roughly 20 times weaker but does not disappear; DC is removed after the curve (10 Hz).
* **Tempo-synced `delay` "Delay"**: parameter `sync` (Off, 1/2 … 1/32, dotted, triplets). When not "Off", time = 60 / tempo × length in quarter notes; the effect takes the tempo from `Effect::set_timing` (`BlockTiming::tempo`), `Bpm::DEFAULT` before the first segment. "Off" (the default) — time from `time`, in ms. The limit is `MAX_SECONDS` = 2 s.
* **Shared DSP blocks** (pure math without allocations, meant to move to the `daw-dsp` crate of batch 6 of `docs/refactor-audit.md` as they are): `biquad.rs` (RBJ coefficients — shelves, peaking, low/high-pass, the all-pass of a crossover split — and the biquad state), `smooth.rs` (`Smoothed`), `dynamics.rs` (`peak_db` of a stereo frame, `GainComputer` — the soft-knee curve threshold/ratio/knee, `Follower` — attack/release one-pole ballistics), `crossover.rs` (the Linkwitz–Riley band split). An effect that needs one of them takes it from there rather than copying it; the compressor runs on `GainComputer` and `Follower` too. Newer tables are written with `lib.rs: number`/`switch`/`choice`.
* **`multiband` "Multiband compressor"** (`multiband.rs`): a Linkwitz–Riley crossover (`crossover.rs`: each split is 4th order — two Butterworth biquads per side, −6 dB at the split, both sides in phase — and a band that leaves the chain before a later split goes through that split's all-pass, so the bands sum back to the input with a flat magnitude, phase only) splits the sound at `split1`/`split2`/`split3` (each kept at least at the one below it; smoothed in log frequency, the filters follow frame by frame while a split moves) into four bands, or three (`bands`; then the top two play as one band with band 3's settings, and switching crossfades). Per band `band<n>_threshold`, `_ratio`, `_attack`, `_release` (the compressor's curve and ballistics, `dynamics.rs`, knee fixed at 6 dB; detection by the louder channel of the band), `_gain` (after the compression), `_solo` and `_bypass` (a bypassed band passes at 0 dB; solo, bypass and gain are smoothed), then `output`. With every band bypassed the effect is transparent in level. No lookahead, no latency. It reports each band's reduction as band gains (`Effect::band_gains_db`, see "Sidechain, gain reduction and effect graphs") and the deepest band as its gain reduction.
* **`dynamic_eq` "Dynamic EQ"** (`dynamic_eq.rs`): four peaking bands in a row (the EQ's RBJ peaking biquad), each turning only while its own band is loud. Per band `band<n>_freq`, `_q`, `_gain` (the most it turns, ±18 dB; 0 — the band does nothing, so a new dynamic EQ is transparent), `_threshold`, `_ratio`, `_attack`, `_release`; plus `sidechain` (the key works like the compressor's). A band listens through a 0-dB band-pass at its frequency and Q (`Coefficients::band_pass`), to the signal or to the key, by the louder channel; above the threshold (the compressor's curve with a 6 dB knee) it moves by `(level − threshold)·(1 − 1/ratio)` dB in the direction of its gain and at most by the gain: a negative gain is a dynamic cut (a resonance or harshness tamer), a positive one a lift only while the band is there. How far a band is engaged (0…1) follows its attack/release and is multiplied by the smoothed gain, so flipping the gain's sign glides through 0 dB; the band's filter is recomputed while its gain moves (more than 0.01 dB) and while its frequency or Q glide. Reports each band's current gain (`band_gains_db`, signed). No latency.
* **How to add a similar effect:** a module with `PARAMS` and `EffectKind`/`Effect`, a line in `factories()`, the same kind with the same parameters in the mock catalog `app/src/mock/catalog.ts` (choices via the `choice` helper). The UI shows the parameters on its own (`ui/common/ParamControl.tsx`). Tests live in the module: frequency response or behavior, finite and bounded output, no steps when parameters change between blocks (`testing.rs: max_step`), harmonics — `testing.rs: tone`, the reported latency — `testing.rs: assert_latency_at_impulse`. Every kind in `factories()` is also run through the shared contract check (`testing.rs: assert_honours_contract`, from `lib.rs`): every param at and past its edges, NaN and infinities keep the output finite; after `prepare` at another rate and `reset` silence gives silence; `reset` forgets a loud burst.

## Built-in synth (`daw-synth`)

The instrument of kind `synth` (`daw_contracts::SYNTH_KIND`): new tracks' default synth and the starter beat's bass. 8 voices (a free voice, otherwise the oldest), waveform (`ParamKind::Choice`: Sine/Triangle/Saw/Square), AHDSR envelope, a one-pole highpass `low_cut` (20…2,000 Hz; 20 Hz leaves the sound untouched) and a one-pole lowpass `high_cut` (40…18,000 Hz; the mod wheel opens it up to 4 octaves), `gain` in %. `src/engine.rs` is the sound (pure math with tests), `src/lib.rs` the `Instrument` glue: parameters in real units, both cuts (in octaves) and volume glide over 20 ms so knob moves and automation do not click, no allocations or locks in `render`.

* **Envelope graph.** The parameter names `attack`/`hold`/`decay`/`sustain`/`release` (seconds; `sustain` a level 0…1) are the convention `ui/tracks/EnvelopeGraph.tsx` (`domain/envelope.ts`) draws for any instrument; a new instrument gets the graph by naming its envelope the same way.
* **Picture.** For kind `synth` the instrument window also shows `ui/tracks/SynthGraph.tsx`: one cycle of the waveform and the filter response with both cut markers (`domain/synth.ts` mirrors the engine's math).
* **How to add a similar instrument:** a crate depending only on `daw-contracts` with an `InstrumentFactory` (see `daw-sampler`, `daw-drums`), a `register` line in `daw-bootstrap/src/wiring/catalogs.rs`, the same kind and parameters in `app/src/mock/catalog.ts`.

## Built-in strings (`daw-strings`)

Kinds `guitar` (acoustic guitar), `electric_guitar`, `ukulele` and `bass_guitar` (`GUITAR_KIND`, `ELECTRIC_GUITAR_KIND`, `UKULELE_KIND`, `BASS_GUITAR_KIND` in `daw_contracts`: the chord part builder voices chords by them). One physical model, no sound files: **extended Karplus–Strong** (`src/engine.rs`, pure math with tests). A string is a delay line one period long; a pluck fills it with a noise burst — darkened by a one-pole lowpass (brighter with `tone` and a harder pluck), without the harmonics that have a node at the pick position, zero-mean; every trip around the loop passes a two-tap lowpass (high harmonics die first), a first-order allpass (the fractional part of the period, so every note is in tune) and a loss factor (`ring`: seconds until −60 dB for a string near G3, shorter for higher strings). Releasing a note damps the string in 0.12 s like a finger or a palm (a short note is a muted "chuck"). The same note re-plucks its own string; 12 voices, otherwise the quietest is stolen. The voices are summed and a **body** adds two resonances (bandpasses; on the electric kinds a magnetic pickup's — the electric guitar's bright peak near 3 kHz): what makes the kinds differ, together with the pick position and the default parameters (`KINDS` in `src/lib.rs`). The kinds played through an amp (the electric guitar and the bass) have an **overdrive** after it: a `tanh` soft clipper whose input gain grows with `drive` (up to ×21), divided by that gain: quiet playing keeps its level and loud playing is squashed, so the loudness stays near the clean sound's (a little lower at full drive); `drive` 0 skips it.

* **Parameters:** `ring` (s), `tone` (brightness, %), `body` (%), `gain` (volume, %), and on the kinds with an amp `drive` (%, 0 by default: the electric guitar starts clean). `body`, `drive` and `gain` glide over ~20 ms; `ring` and `tone` apply from the next pluck (a string's loop is set when it is plucked). Controllers, pitch bend included, are ignored for the same reason.
* **Realtime:** every voice's 8192-sample delay line (the longest period: 23 Hz even at 192 kHz) is allocated when the instrument is created; `note_on` (filling one period) and `render` never allocate.
* **Frontend:** the kinds and defaults are copied into `app/src/mock/catalog.ts` (`plucked`); a new track's step-input pitch — `domain/strings.ts` (E3 for both guitars, C4, A1).
* **A new string kind:** a row in `KINDS` (body modes, pick position, defaults, `drive: Some(…)` if it has an amp), its constant in `daw_contracts::instrument` if the chord part should know it, the mock catalog row, the labels in `i18n` (`catalog.kinds`).

## Tempo map: tempo and time signature changes through the song

* **Model and contract.** `Project::tempo_map: TempoMap` (`daw-contracts/src/tempo_map.rs`; JSON `tempoMap: { tempos: [{ tick, bpm, ramp }], signatures: [{ tick, signature: { numerator, denominator } }] }`, `#[serde(default)]`) is the single source of tempo and time signature: the first points are at tick 0 ("the project tempo and signature"); the old `Project::tempo`/`time_signature` are gone (old files open at 130 BPM 4/4 — rule 10). `TempoChange.ramp` — the tempo moves smoothly (linearly in ticks) from the previous point to this one; otherwise it is a step at the point; the first point never has a ramp. A signature change sits at a bar start of the previous signature. An invalid map cannot be created: `TempoMap::new` (and reading from JSON) checks that the first points are at tick 0, ticks strictly increase, none is beyond `MAX_CLIP_TICK`, there are no more than `MAX_TEMPO_CHANGES` (512) and `MAX_SIGNATURE_CHANGES` (256), and signature changes are on a bar. Editing goes through the contract `TempoControl` (`daw-contracts/src/tempo.rs`; implementation `ProjectTempo`, `daw-project/src/tempo.rs`; in `Controls.tempo`): `set_tempo_changes`, `set_signature_changes`, `set_tempo_map` (the whole map), `set_tempo`/`set_time_signature` (only the point at tick 0). Every edit is one undo step through the core. `TransportControl` no longer knows about tempo.
* **One set of math** — `TempoMap` methods (no allocations): `tempo_at`, `signature_at`, `seconds_at`/`tick_at_seconds` (a ramp is an exact integral: time under a linear tempo is a logarithm, the inverse is an exponential; seconds up to each point are precomputed in `new`, lookup is binary search), `frames_between`, `tick_after_frames`, `next_change`, `in_ramp`, `bar_start`, `bar_index`, `bar_tick`, `bar_length_at`. Tests — `tempo_map/tests.rs` (exact values, ramp vs. numeric integral, round trip, bars 3/4 → 4/4, rejections, JSON). The frontend repeats it in `domain/tempoMap.ts` (plus `barLengthAt`, `barsBetween`, snapping `snapNearestInBars`/`snapDownInBars`, `gridLines` for the grid, `barPosition`, the `tempoMapProblem` check for the mock, and pure edits `withTempoAt`/`withTempoPoint`/`withMovedPoint`/`withoutPoint`/`withRampToggled`/`withSignatureFrom`/`withSignatureAt`/`withoutSignature`; signature edits keep later changes at their bar numbers).
* **Clock and engine.** `TransportClock::advance(max_frames, rate, &TempoMap)`: the engine passes the map from its snapshot (before the first snapshot — a default map created in advance). A segment is cut at map points (`next_change`, like at a loop boundary); inside a tempo ramp it is no longer than `RAMP_SEGMENT_FRAMES` (512). The segment end is computed exactly from the map (`tick_after_frames`; an end near a point "snaps" to it), `ticks_per_frame` is the segment average, so the position does not drift and note error inside a ramp segment is a fraction of a millisecond. `BlockTiming::tempo` is the tempo at the segment start, `time_signature` and `signature_start` (the tick of the signature change) are the segment's signature, `bar_start(tick)` is the bar start. VST3 (`ProcessContext`: tempo, signature, bar start), the tempo-synced delay, and the metronome follow from this automatically (beats and accents are counted from `signature_start`, so after "3/4 → 4/4" the accent immediately follows the new bar). An audio clip entered in the middle starts its audio at `frames_between(clip start, position)`.
* **Who else converts ticks ↔ time — all via the map:** export (`daw-render/src/export/range.rs`: length — `frames_between(range start, end)`; the engine plays by the snapshot's map), the length of a regular audio clip (`ProjectClips::add_audio_clip` — from the clip's position; `Clip::ticks_to_source_frames`/`source_frames_to_ticks` — also from the clip start: split and warp), warp to tempo (a single stretch by the tempo at the clip start, or a curve if the tempo changes inside the clip), audio recording (`daw-audio-recorder/src/take.rs`: the take end and alignment to the covered clip), note recording (a new clip starts at a bar start per the map, `bar_start`), drum part preview (the tempo in the start bar), telemetry (`tick.tempo` and `tick.signature` — at the heard position; the heard position under PDC goes through the map's seconds), MIDI files (`daw-midi/src/file/tempo.rs`: project export writes the map's tempo and signature events, a ramp becomes a staircase of up to 32 steps no finer than a sixteenth, each step at the average tempo, preserving time; clip export — the tempo and signature at the clip start; `MidiFileIo::import_tempo` replaces the map with the file's map in one step: no event at tick 0 — 120 BPM and 4/4; consecutive identical tempos are merged).
* **RPC and MCP** (`daw-rpc/src/tempo.rs`): `tempo.get`, `tempo.set { bpm }`, `tempo.setSignature { numerator, denominator }` (song start), `tempo.setChanges { changes }`, `tempo.setSignatureChanges { changes }` (whole lists, one undo step; the descriptions include the example "breakdown from bar 64 to 128, ramp up to 140 by bar 80" in ticks), `midi.importTempo { path }`. `project.get` carries `tempoMap`. The old `transport.setTempo`/`transport.setSignature` are gone.
* **UI.** Actions — `actions/tempo.ts` (`TempoActions`: `setTempoAt`, `setSignatureAt`, `setSignatureFrom`, `removeSignature`; the value is shown immediately via `patchProject`). The transport panel's BPM field shows the tempo at the playback position (`tick.tempo`); editing it changes the point in effect there (with no changes — the song tempo); the signature fields work the same way. The "bar:beat:tick" position and seconds — `barPosition`/`secondsAt` via the map. "Settings" → "Project" edit the tempo and signature at the start. Timeline: the header is the bar ruler (`RULER_HEIGHT` = `BAR_RULER_HEIGHT`, `timelineLayout.ts`); there is no tempo lane in the interface (owner's choice: tempo changes and ramps are edited through MCP/RPC `tempo.setChanges` or tempo from a MIDI file via `midi.importTempo`); it is its own canvas (`rulerRender.ts`), see "Timeline ruler strip". The grid and bar numbers — `gridLines` via the map (bars of different lengths). Signature flags ("7/8" after the bar number): geometry — `ui/tracks/tempoLayout.ts`, drawing — `tempoRender.ts`, mouse — `tempoPointer.ts` (double or right click on a flag), menu — `TempoMenu.tsx` (signature from a list, remove). Mock — `mock/handlers/tempo.ts` (the same `tempoMapProblem` checks); the mock's position follows the map.
* **Adding something similar** (e.g. another ramp shape): a field in `TempoChange` and a rule in `TempoMap::new` → math in `tempo_map.rs` and `domain/tempoMap.ts` with tests → the transport clock cuts the segment if needed → RPC description.
* **Bars come only from the map.** Everything that counts "song bars" takes them from the map, not from `BAR_TICKS`: timeline snapping (`domain/tempoMap.ts: snapNearestInBars`/`snapDownInBars`: the "Bar" grid (`domain/time.ts: BAR_GRID`) is the map's bar boundaries, other steps are counted from the bar start, and the bar end is also a grid point; used by move, resize, split, loop, sample drop and automation points), "clip per bar" by double click and `NewNoteClip` without a length (a bar of the signature at the clip's position — `TempoMap::bar_length_at`), clip paste (`actions/clips.ts: paste` — nearest bar boundary), markers ("＋ Marker" and Alt + double click — `barStart`, dragging the flag — nearest boundary), the automation grid (`automationRender.ts` — `gridLines`), clip length in bars in the clip panel (`barsBetween`), drum part start (`daw-patterns/src/plan.rs: bar_start_tick` — `bar_tick(start_bar)`; the mock does the same), the note recording clip (`bar_start`), the console commands `clip`/`clips`/`loop` (`daw-app`). **A note clip** keeps an even grid of the signature at its start internally (`domain/noteClip.ts: clipBarTicks`): the piano roll and "Steps" bar, bar and beat lines, the "Bar" grid, Shift + arrow, the spare bar, "Content length" in bars, and auto content length in the backend (`daw-project/src/note_rules.rs: fit_length(content, bar)`). A signature change in the middle of a clip does not cut its grid; a clip moved into a different signature recalculates its auto length on the next note edit. **Constant 4/4** (`BAR_TICKS`) remains where it is intended: drum pattern designs and the demo beat (16 steps per bar; in 3/4 a pattern plays longer than a song bar), limits (`MAX_CLIP_LOOP_TICKS`, note recording snap up to `BAR_TICKS`), the timeline's width margin (`visibleBars`), the width of a step row in the console. Tests: `daw-contracts/src/tempo_map/tests.rs`, `daw-patterns/src/plan.rs`, `daw-bootstrap/tests/drum_part.rs` (`start_bar` in 3/4), `daw-project/src/tests/tempo.rs` (a clip in 7/8); frontend — the `domain/tempoMap.ts` functions, verified against the mock.
* **Limitations.** A warped clip with a tempo change inside follows a curve (see "Warping across tempo changes"); WSOLA places attacks early by roughly (stretch − 1) × 50 ms — the same as with a single stretch. A regular audio clip does not change length if the tempo under it is changed later (as before). VST3's `projectTimeSamples` and the PDC shift for the metronome use the segment tempo (an approximation). A MIDI tempo ramp is a staircase; on import the staircase stays a staircase.

## Plugin delay compensation (PDC)

A plugin with lookahead (a limiter, a linear-phase EQ) outputs audio later than it received it. Without compensation, parallel paths (a limiter on one bus, nothing on another) would drift apart — "flamming".

* **Contract.** `Effect::latency_samples` and `Instrument::latency_samples` (`daw-contracts`, default 0): the latency in frames, valid after `prepare`, may change after `prepare` and after parameter changes; the call is cheap and made from the audio thread. A VST3 effect and a VST3 instrument read `getLatencySamples` in `prepare` and return the stored value (see the limitations below). The total for everyone else is `EngineStats::latency()` → `EngineLatency { frames, sample_rate }` (`seconds()`); clamping is counted in `EngineLosses::latency_clamped`.
* **Where and when it is computed.** `daw-engine/src/mixer/latency.rs` (`GraphMixer::align_latency`, called by `Engine::apply_snapshot`) — on the audio side on every snapshot application (any edit, a DSP object arriving/leaving; after `prepare` the snapshot is applied again), not on every block. We walk the snapshot's topological order: a node's input = the maximum of the outputs of all its sources, **including sidechain** (the compressor key arrives aligned with the main input); output = input + the node's own latency (an instrument, an enabled effect, and the lead of a channel whose time alignment is set earlier — see "Channel utility"; 0 otherwise, and always 0 for the master). A connection whose audio arrives earlier than that maximum is delayed by the difference. The master's input is the total latency `L`: all timeline audio in the master sounds exactly `L` later than the transport position.
* **A bypassed effect** adds no latency: it does not process audio, and bypassing is a new snapshot after which compensation is recomputed (a short jump when toggling is a deliberate price for simplicity).
* **Delay lines** (`mixer/delay.rs`, `DelayLines`): a pool of `MAX_DELAY_LINES` = 32 rings of `MAX_PDC_FRAMES` = 32,768 stereo frames (~0.68 s at 48 kHz; the limit is in frames because memory is allocated before the sample rate is known) — 8 MB per engine, written at creation. A line is bound to a connection (from, to, sidechain), so edits that do not change that connection do not cut the audio in it; changing the delay amount of the same connection keeps the contents and crossfades from the old delay to the new one over one segment (so nudging a channel earlier moves every other path without a click), and a new connection gets a cleared line. A delay above the limit is clamped to it, and a connection without a free line goes without delay — both cases are counted in `EngineLosses::latency_clamped` (once per snapshot application), and the watcher thread logs any increase (`source: "engine"`). No allocations or locks in the audio thread: the `arrival`/`output` tables live in the preallocated `Scratch`.
* **Timeline and position.** Sources are not shifted earlier (that would require looking ahead through notes and clips); the approach is a uniformly delayed master and a shifted display. `daw-rpc/src/telemetry.rs` reports the **heard** position in `tick.positionTicks` (during playback — the transport position minus `L`, converted to ticks via the tempo map, no less than 0) and `L` in milliseconds in `tick.latencyMs`; the transport panel shows "PDC N ms" next to CPU only if `latencyMs > 0` (the mock sends 0). The metronome and other post-processors receive the segment time shifted by `L` (`Engine::heard`), so the click lands in time with the delayed music (the metronome does not play beats "before zero"). Recorded live notes also get their timing minus `L`: the musician plays to what they hear. Audio recording (`daw-audio-recorder`) trims the recording latency **plus** `L` from the start of the take (`take.rs: save_takes`): a manually entered recording latency stays the device latency, and PDC is added automatically.
* **Limitations.** Sample preview bypasses the graph and is not delayed. A VST3 plugin's latency is read only in `prepare` (the host does not listen to `restartComponent(kLatencyChanged)` yet): a later change is picked up when the plugin is prepared again (a device change or a re-created instance), not on the next edit. In a loop, metronome clicks in the last `L` before the loop end do not sound.
* **Adding something similar** (e.g. the latency of external hardware on a node): a node's own latency is a branch in `GraphMixer::own_latency` (the channel lead is one); tests — `daw-engine/src/tests/latency.rs` (the stub effect `Latent` with real latency).

## Sends: pre/post-fader and connection level automation

A send is an ordinary graph connection with a level (`Edge { from, to, level, sidechain, pre_fader }`); there is no separate "send" entity.

* **Contract.** `Edge::pre_fader` (JSON `preFader`, default `false` — "post-fader"). A **pre-fader** send takes the node's audio before its volume and pan: moving the fader or pan, and their automation, do not affect the send. **The node's mute and another node's solo silence it too** — a muted track is silent entirely (simpler and more predictable; "quiet fader but loud reverb" is done by pulling the fader to zero). Only available on an ordinary connection from a node with a fader — a source or a bus (`Graph::check_pre_fader`); on an effect or the master it is `Invalid`. Toggled by `GraphControl::set_edge_pre_fader` (RPC `graph.setEdgePreFader { from, to, preFader }` → `null`, one undo step). Pre-fader sends (like sidechain) are branches, not the track's path: `insert_effect` and `set_output` do not touch them, `Graph::chain` does not see them; `remove_effect_keep_path` gives the new connection the input send's kind.
* **Level automation.** Target `ParamTarget::EdgeLevel { from, to, sidechain }` (JSON `{ "type": "edgeLevel", "from", "to", "sidechain" }`, `sidechain` defaults to `false`; sidechain connections are automated separately), range `0..=MAX_LEVEL`. A lane lives as long as its connection: the rule is held by a single function `daw-project/src/ops.rs: drop_stale_edge_lanes` (called by `disconnect`, `set_output`, `drop_node`), and `move_edge_lane` moves the lane along with the connection when an effect is inserted. Adding a lane for a nonexistent connection is `Invalid`.
* **Engine** (`daw-engine/src/mixer/mod.rs`). For a source or bus with pre-fader sends, the audio is copied before `apply_gain` into a single preallocated `pre_fader` buffer (nodes are processed one at a time, so one is enough); `tap_pre_fader` fades it out smoothly on mute/solo. "Pre-fader" connections read it instead of the node's output; latency (PDC) is computed and aligned for them like for any connection. Automation overrides the connection level for the segment (`override_edge_level`, reset in `clear_overrides`), and a level change is ramped smoothly across the segment (`EdgeRt::ramp`, `mix_ramped`; the same in the delay line) to avoid steps. Nothing is allocated or locked.
* **Frontend.** The "pre-fader / post" toggle is in `ui/graph/EdgePath.tsx: EdgeControls` (only on an ordinary connection from a track or bus, `domain/graph.ts: canPreFader`), action `actions/graph.ts: setEdgePreFader`; the inspector marks such connections "pre". Lanes "Send: A → B" (and "Sidechain: A → B") are added from the level control's right-click menu like any parameter (`ui/common/ParamMenu.tsx`); labels and ranges — `domain/automation.ts: targetLabel/targetRange`. The mock repeats the rules (`mock/handlers/graph.ts`, `mock/graphOps.ts: dropStaleEdgeLanes/moveEdgeLane`, target check in `mock/handlers/automation.ts`).
* **Tests:** contract — `daw-project/src/tests/sends.rs` and `daw-contracts/src/graph/tests.rs`; engine — `daw-engine/src/tests/sends.rs`; RPC wire — `daw-rpc/tests/graph.rs`.

## Sidechain, gain reduction and effect graphs

* **Picking the key.** `GraphControl::set_sidechain(effect, source: Option<NodeId>)` (RPC `graph.setSidechain { effect, source | null }`, one undo step): removes every sidechain edge into the effect (with their lanes), connects `source → effect` as a sidechain at level 1 and sets the effect's `sidechain` param to 1 (`None` → 0). An effect reads its key only if its catalog has a `sidechain` param (compressor, gate, dynamic EQ) — other kinds are `graph::NO_SIDECHAIN_INPUT` (GR-122); a source the graph rules reject is their code. Implementation `daw-project/src/graph.rs`, mock `mock/handlers/graph.ts`; tests `daw-project/src/tests/sidechain.rs`, RPC wire `daw-rpc/tests/all/graph.rs`. UI: `ui/effects/SidechainPicker.tsx` ("Sidechain from: none / tracks and buses", candidates `domain/graph.ts: sidechainCandidates`) replaces the bare switch in the effect panel; dragging a wire to the card's sidechain port in the graph still works.
* **Band gains.** A band-split effect also says what each band is doing: `Effect::band_gains_db() -> &[f32]` (default empty; at most `MAX_EFFECT_BANDS` = 4, lowest band first, dB: negative a cut, positive a boost — the multiband compressor's reduction per band, the dynamic EQ's moving gains). The mixer reports them after each `process` into a fixed slot per effect-store position next to the reduction (`meters.rs: report_bands`; per band the deepest cut and the highest boost are two atomics, because `fetch_max` on f32 bits orders only non-negative values; no alloc/locks); `EngineStats::band_gains` → `BandGains { node, db }` returns per band the value farthest from 0 dB since the last read (a bypassed effect drops out). Telemetry sends `bands: [{ node, db: [..] }]` in the tick; the graphs hold each reading for a moment and let it back toward 0 dB (`domain/bandGains.ts`, `ui/effects/bandGains.ts: createBandGains`); the mock fakes them (`mock/meters.ts: mockBandGains`). Tests: `daw-engine/src/tests/processors.rs`, per effect in `daw-effects`.
* **Gain reduction meter.** `Effect::gain_reduction_db() -> Option<f32>` (default `None`; compressor, gate, limiter, multiband compressor report it). The mixer asks after each `process` and writes it into a fixed atomic slot per effect-store position (`daw-engine/src/meters.rs: report_reduction`, no alloc/locks); `EngineStats::gain_reductions` takes the deepest value since the last read (only effects processed since then — a bypassed one drops out). Telemetry sends `reductions: [{ node, db }]` in the tick (`daw-rpc/src/telemetry.rs`); the frontend keeps them with decay (`state/levels.ts: createReductions`, `session.reductions`), the mock fakes them (`mock/meters.ts: mockReductions`). Tests: `daw-engine/src/tests/processors.rs`, per effect in `daw-effects`.
* **Effect panel** (`ui/effects/EffectPanel.tsx`, used by the graph inspector and the mixer popover): generic controls for every param (`ParamControl`) plus, by effect kind, a live graph above them (`EffectGraph.tsx`, also used by the signal path view) — `eq` → `EqGraph.tsx` (response curve 20 Hz–20 kHz, ±18 dB, draggable band handles: drag = frequency/gain, wheel on the mid band = Q, double-click = reset; changes go through `graph.setEffectParam` like a knob), `filter` → `FilterGraph.tsx` (one handle: cutoff and resonance), both over the live spectrum (`LiveSpectrum.tsx`); `compressor`/`limiter`/`gate` → `DynamicsGraph.tsx` (transfer curve, level/GR history, GR meter, gate state); `distortion`/`saturator` → `ShaperGraph.tsx`; `delay` → `DelayGraph.tsx`; `chorus` → `ChorusGraph.tsx`; `reverb` → `ReverbGraph.tsx`; `multiband` → `MultibandGraph.tsx` (band split, live response, reduction per band, split handles, solo/bypass chips); `dynamic_eq` → `DynamicEqGraph.tsx` (full-gain and live response, band handles) — see "Live effect visuals". The math is pure and **mirrors** the Rust DSP (`domain/biquad.ts` ↔ `biquad.rs`, `eqCurve.ts` ↔ `eq.rs`, `compressorCurve.ts` ↔ `dynamics.rs: GainComputer::reduction`, and one module per other effect) — change both sides together. A graph for another effect: a pure domain module from its param convention (like `domain/envelope.ts` for instruments) and a `Match` in `EffectGraph`.
* **EQ bands** (`eq.rs`): low cut (12 dB/oct Butterworth high-pass, `low_cut` 20…1000 Hz, off at 20 Hz), low shelf, peaking mid (with Q), high shelf, high cut (low-pass, `high_cut` 1…20 kHz, off at 20 kHz). "Off at the extreme" keeps a new EQ transparent without extra switches.

## Channel utility: polarity, width, mono, time alignment

The engineer's utility controls on every track and bus: polarity (often called "phase") invert per side, stereo width, a mono switch and fine time alignment, to line up multi-mic drums or a DI with its amp mic.

* **Why on the strip, not a "Utility" effect.** Engineers expect these on the channel (a console's input section; Ø and track delay sit on the channel in most DAWs) and need them on many channels at once: aligning eight drum mics should not mean inserting eight effects. On the strip they are always there, save and undo like volume and pan, and need no place in the insert chain. The time alignment also fits plugin delay compensation directly as a node's own latency, the documented way to add "something similar" there. Like the stage place, it is a property of the channel.
* **Contract** (`daw-contracts/src/graph.rs`): `Strip` gains `polarity: Polarity { invert_left, invert_right }`, `width` (`0..=MAX_WIDTH` = 2: 0 mono, 1 as recorded, 2 twice the side), `mono` (sums to `(L + R) / 2` whatever the width, which is kept for when it is off) and `delay_ms` (`±MAX_CHANNEL_DELAY_MS` = 10 ms: positive later, negative earlier). They sit flat in the node JSON (`polarity: { invertLeft, invertRight }`, `width`, `mono`, `delayMs`) and are required (no serde defaults, rule 10: older project files do not open). `GraphControl::set_polarity`, `set_width`, `set_mono`, `set_delay` (`daw-project/src/graph.rs`): width and delay are clamped and a knob gesture merges into one undo step (`edit_keyed`, keys `width:{id}` and `delay:{id}`); polarity and mono are one step each. The master and effects are `graph::NO_UTILITY` (GR-126); not a number is `WIDTH_NOT_A_NUMBER` (GR-127) / `DELAY_NOT_A_NUMBER` (GR-128).
* **Where in the sound.** Before the node's volume and pan, like a console's input section (`mixer/mod.rs: process`): the pre-fader sends and the inserts hear the result, and so does a channel's stage voice. Order: polarity, then mid/side width (mono is width 0), then the delay.
* **Engine** (`daw-engine/src/mixer/utility.rs`, `ChannelUtilities`). One slot per possible node with two delay lines (`stage/dsp.rs: DelayLine`, read at whole samples), allocated by `new`/`prepare` for `MAX_CHANNEL_DELAY_MS` at the stream rate. A slot follows its node id across snapshots through the mixer's `Carry` (`compile.rs: bind_utilities`); a channel new to the mixer takes a free slot, cleared. The lines always take the channel's sound in, so a delay set later plays real history at once. Every change glides over one segment: a polarity flip fades that side through silence, a width or mono change moves the side gain, a delay change crossfades from the old tap to the new one. Neutral settings leave the sound exactly as it is. No allocations or locks on the audio thread.
* **Time alignment and PDC.** The delay is whole samples at the stream rate (`round(ms × rate / 1000)`; the interface shows both units). Later is a plain delay in the channel's own lines and holds nothing else back. Earlier cannot be played ahead of time, so the channel's lead is its own latency for compensation (`latency.rs: own_latency`): the rest of the mix waits for it, the transport shows the extra "PDC N ms", and the channel plays that much earlier relative to everything else. Each parallel path then needs a compensation line (the same cost as a latent plugin on one track, up to `MAX_DELAY_LINES`). Nudging within the earlier range glides (the compensation lines crossfade to a new delay); switching a channel between "not earlier" and "earlier" re-lays the compensation once, a short jump like turning a latent plugin on.
* **Automation and MIDI learn.** Only the width is automatable: `ParamTarget::NodeWidth { node }` (`0..=MAX_WIDTH`, JSON `{ "type": "nodeWidth", "node" }`), valid on sources and buses (`ops::validate_target`), removed with the node (`ops::drop_node`), overriding the width for the segment (`GraphMixer::override_width`); a MIDI knob spans its whole range. Polarity and mono are switches and the delay would bend the pitch while it moved, so they are not.
* **Bounce and freeze.** The copy's sound already holds the polarity, width and a later alignment, so the copy starts neutral; a lead cannot be rendered, so the copy keeps the source's negative `delay_ms` (`daw-project/src/bounce.rs: place`).
* **RPC / MCP:** `graph.setPolarity { id, invertLeft, invertRight }`, `graph.setWidth { id, width }`, `graph.setMono { id, mono }`, `graph.setDelay { id, ms }` (`daw-rpc/src/graph.rs`); `project.get` carries the fields in every source and bus.
* **Frontend.** `ui/common/ChannelUtility.tsx` on the mixer strip (above the pan) and in the graph inspector (under M/S): Ø (both sides), L and R (one side), Mono, the Width knob (right-click: automation, MIDI learn; dimmed while mono) and the Delay knob with its value in ms and, under it, in samples at the stream rate with ‹ › one-sample nudges. The rate is read once per view (`ui/common/streamRate.ts`, via `actions.audio.status`; 48 kHz until read). Units, ranges and the neutral values are the pure `domain/channelUtility.ts`; actions `graph.setPolarity/setWidth/setMono/setDelay` show the value at once (`patchProject`), the width also tells live automation writing (`ParamTouch`). Automation lanes "· width" come from `domain/automation.ts`. The mock repeats the rules and codes (`mock/handlers/graph.ts`, `mock/handlers/automation.ts`, the copy's lead in `mock/handlers/bounce.ts`); new strips get `neutralUtility()`.
* **Limitations.** The master has no utility: checking the whole mix in mono is the live master meter's monitoring switch (see "Live master meter"), which is not saved or exported, while a channel's mono is part of the mix. Export and track renders are not trimmed by the total PDC latency, so a channel set earlier makes them start that much later, as a latent plugin does. The lines hold 10 ms, so a room mic farther than about 3.4 m needs a delay effect.
* **Tests:** contract — `daw-project/src/tests/channel_utility.rs` (and the width knob in `midi_mappings.rs`, the copy's lead in `bounce.rs`); JSON — `daw-contracts/src/graph/tests.rs`; engine — `daw-engine/src/tests/utility.rs` (polarity, width and mono, width automation, later delay, earlier through PDC, gliding changes); RPC wire — `daw-rpc/tests/all/graph.rs`.
* **Adding a similar channel control:** a `Strip` field and a `GraphControl` setter (with its code), the value in `NodeRt` (`compile.rs: rebuild_nodes`), the DSP in `ChannelUtilities::process`; if it is automatable, a `ParamTarget` variant through every match (ops, MIDI learn, render, mixcheck, engine automation) and `domain/automation.ts`; then the mock, the actions and `ChannelUtility.tsx`.

## Virtual stage: placing the channels in one room (`stage.*`)

Drag the instruments around a room and hear them move: left/right, ahead/behind, near/far and up/down, live while the song plays. The listener stands in the middle of the room; on headphones a sound placed behind or above them sounds behind or above.

* **Contract** (`daw-contracts/src/stage.rs`): `StageControl` — job "where each sound stands in the shared room": `room()`, `place(node, pan, StagePlace { depth, height })`, `take_off(node)`, `set_room(Room { size, reverb, listening })`; `MAX_ON_STAGE` = 64. The listener stands in the middle of the room facing ahead, and all three coordinates are 0 at their head: `pan` −1…1 wall to wall, `depth` −1…1 from the wall behind the listener to the wall ahead, `height` −1…1 floor to ceiling. A channel (a track's source or a bus — anything with a `Strip`) stands on the stage while `Strip::stage: Option<StagePlace>` is set (in JSON `stage: { depth, height }` inside the node kind; absent — off the stage, plain pan). Its left/right **is the strip's `pan`**, wall to wall, so the mixer's pan knob, pan automation and MIDI learn move it, and nothing duplicates it. `Project::room` is the one shared room (`size` 0…1 small studio room → concert hall, `reverb` 0…1 open air → live walls, `listening` `speakers`/`headphones`: what the stage is rendered for, saved with the project; two speakers in front cannot put a sound behind the listener, headphones can). Values are clamped; codes (area GR): `NO_STAGE_PLACE` GR-123 (an effect or the master), `NOT_ON_STAGE` GR-124 (a depth/height lane or MIDI mapping of a channel off the stage), `STAGE_NOT_A_NUMBER` GR-125, `TOO_MANY_ON_STAGE` GR-212. Consecutive `place` calls of one channel merge into one undo step (key `stage:<id>`, the knob window), so a drag is one step; so do `set_room` calls. `take_off` keeps the pan and removes the channel's depth/height lanes. Implementation `daw-project/src/stage.rs` (`ProjectStage`).
* **Why on the strip.** The place is a property of the channel, like pan. A built-in effect could not feed one shared room, and a "stage node" with positioned inputs would put the place on connections that every rewiring (inserting an effect, changing the output) would have to carry along. On the strip it stays with the channel through any rewiring, and the engine decides where in the path it acts.
* **Automation and MIDI learn.** `ParamTarget::StageDepth { node }` and `StageHeight { node }` (both −1…1); a lane is valid only while the channel stands on the stage (`ops::validate_target` through `ops::stage_spot`) and goes with it (`ops::drop_stage_lanes` on `take_off`, `drop_node`). The engine plays them as per-segment overrides like pan (`GraphMixer::override_stage_depth/height`). MIDI learn moves them through `StageControl::place` (`MidiMappingDeps::stage`); a stage drag reports pan/depth/height touches to live writing for a channel already on the stage.
* **Engine** (`daw-engine/src/stage/`: `geometry.rs` pure math, `hrtf.rs` the direction cue (the head and the outer ear), `voice.rs` one channel, `room.rs` the shared tail, `dsp.rs` the small filters and the delay line that refactor batch 6 moves to `daw-dsp`). The mixer (`compile.rs: bind_stage`) binds a voice to every placed channel — `MAX_ON_STAGE` preallocated slots keyed by node id, so a channel keeps its lines and its glide across snapshots, and one leaving gives its slot to one arriving in the same snapshot — and runs it **after the last node of the channel's insert path** (`insert_path_end`, the rule of `Graph::insert_path` and `mixerStrips.ts`): the track's effects shape the instrument's own sound first, and a compressor cannot undo the distance. It runs after `tap.output` (an insert's live picture shows its own output). The placed channel's strip applies its volume but not its pan. The room tail joins the master's input before its fader (`render_room`, so the master's picture and meter include it); only channels whose sound reaches the master feed it (`reaches_master`). The lines are allocated in `Stage::new`/`prepare` (`GraphMixer::prepare` runs when the stream opens, outside the callback); `process` allocates and locks nothing. The sound model:
  - *Geometry* (mirrored for the picture by `app/src/domain/stage.ts`): size → width 6–30 m, depth 5–24 m, height 3–10 m, ring time 0.35–2.8 s, wall lowpass 9–4.5 kHz (all geometric). The listener stands in the middle of the room, ears halfway up, facing ahead (+depth); every coordinate reaches to 0.5 m off its walls (`WALL_GAP`). Where a sound comes from is a `Direction` — the unit vector to it split into `lateral` (towards the right ear), `front` (along the nose) and `elevation` (up). Inside 0.5 m of the head (`NEAREST`) the vector shrinks to nothing and the level stops growing, so a source dragged through the listener passes from ahead to behind without a jump.
  - *Direct sound:* one point source (the middle of the channels). Level by the inverse distance law beyond 2 m (−6 dB per doubling; never louder than itself). Air: a one-pole lowpass from 20 kHz up close to about 5 kHz 25 m away. Then the direction cue below.
  - *Direction cue* (`hrtf.rs`) — on **headphones** a compact parametric HRTF instead of a measured set (no file, no allocation, fits most heads about equally well); on **speakers** only what two speakers in front can carry. Everything is tuned against straight ahead: a sound from straight ahead at ear height passes unchanged in both modes, so switching never changes a centred sound's tone. Two parts:
    - *The head* (`Head`, per ear, after the outer ear): on speakers, equal-power panning by `lateral` (×√2, so a centred source keeps its level). On headphones the far ear gets the interaural time difference (Woodworth's spherical head, (a/c)(θ + sin θ), up to ≈ 0.66 ms, a fractional delay), −1.9 dB from the side (`FAR_EAR_LEVEL`) and the head's shadow (Brown–Duda first-order shelf above ≈ 1.25 kHz, −14 dB highs from the side, `FAR_EAR_HIGHS`), and the near ear gets +3.5 dB highs (`NEAR_EAR_HIGHS`). All of it follows `lateral` alone, so it is the same ahead and behind (the cone of confusion, as with a real head).
    - *The outer ear* (`Pinna`: four biquads in a row on the source, before it splits into the ears): it tells ahead from behind and up from down. **Behind** (`rear` = how far `front` is below 0, headphones only): a high shelf −8 dB above 3 kHz (`REAR_HZ`/`REAR_DB`: the forward-facing pinna takes the presence and the air), +3 dB around 1.1 kHz (`REAR_BAND_*`, Blauert's rear directional band: a little body) and the notch below at 7.5 kHz — about −4 dB at 3 kHz, −12 dB at 6 kHz, −17 dB at 7.5 kHz, −8 dB at 16 kHz, within 0.5 dB under 500 Hz. **Height** (both modes): a ±4 dB shelf above 7 kHz (`LIFT_*`) and a notch (`NOTCH_*`, Q 2, up to −9 dB) that moves from 4.6 kHz straight below to 12 kHz straight above; its depth is the larger of |elevation| and `rear`, so it is gone straight ahead at ear height. On speakers `rear` is always 0: behind sounds like its mirror ahead, and the Stage view says so.
    - *How to tune it:* every number is a named constant at the top of `hrtf.rs` with what it does. Stronger or weaker front/back: `REAR_DB` and `REAR_BAND_DB` (the main cue; much beyond −12 dB makes rear sources sound muffled rather than behind). A brighter or darker overall rear tone: `REAR_HZ`. The height impression: `NOTCH_OCTAVES` (how far the notch travels) and `LIFT_DB`. Lateral width on headphones: `FAR_EAR_LEVEL`/`FAR_EAR_HIGHS`. How fast the tone may follow a move: `PINNA_SLEW_SECONDS` in `voice.rs`. Check a change by ear on headphones with a bright source (hi-hats, noise) dragged around the head, then against `stage/tests.rs` (`the_outer_ear_is_flat_ahead_darker_behind_and_moves_its_notch_with_height` pins the shapes, `headphones_tell_behind_from_ahead_and_speakers_cannot` the result through a voice). A measured HRTF set would replace `Pinna` and `Head::direct` with per-direction filters (FIR or fitted biquads) chosen from `Direction`; everything around them stays.
  - *Early reflections:* image sources in all six surfaces — the left and right walls, the walls ahead of and behind the listener, the floor and the ceiling (first order) — each later by its extra path (up to 120 ms), as loud as its path's inverse distance × wall reflectivity (0.8 × reverb), from its own direction and darkened by the walls. On speakers each is panned by its `lateral`. On headphones each reaches the far ear later by its own interaural delay, the far ear also hears it up to 6 dB quieter from the side (the head's shadow folded into its level, `REFLECTION_FAR_EAR`), and the share of it that comes from behind takes the outer ear's rear shelf (`rear_shade`, one per ear) — so a source behind the listener is heard behind in its echoes too (five of its six reflections come from behind). A source near a wall or high up hears that wall early and loud: depth and height are heard in the room's echo pattern, not only in level.
  - *Room tail* (`room.rs`): one feedback delay network of eight lines with a Hadamard mix, per-line damping and the feedback that rings for the ring time. Line lengths are fixed (the size changes how long and how dark it rings), so the size slider never clicks. Each channel feeds it its dry sound × 0.4 × reverb from the moment of its first reflection, leaning halfway to its side. Like a real reverberant field it does not fall with distance, so the direct-to-reverberant ratio is the main distance cue: at half reverb the room is as loud as the direct sound about 8 m away. It sleeps 1.5 ring times after its input stops.
  - *Smoothness:* the place glides (a 40 ms one-pole step per segment), and every per-sample value — gains, interaural delays, shadow, air, reflection delays, levels and rear shares, room send — ramps linearly across the segment, so dragging never clicks; a moving delay bends the pitch a little, like a real moving source. The outer ear's filters take new coefficients every 32 frames from the ramped cue, and the cue itself moves no faster than ahead → behind in 50 ms (`PINNA_SLEW_SECONDS`): a source passing right by the head turns around within a few milliseconds, and the filters' steps would click if the cue followed it.
  - *Not modelled:* head tracking (the sound turns with your head, so front/back confusions stay possible — they are with real binaural recordings too), a measured or personal HRTF (the parametric one is an average head), near-field cues (a source within arm's reach has a much larger level difference between the ears), the travel time of sound (a far instrument would play late), the width of a stereo instrument (it becomes one point), rooms other than a rectangle. Speakers stay plain stereo: a real "behind" there needs surround speakers.
* **RPC / MCP:** `stage.place { node, pan, depth, height }` (depth −1…1, negative behind the listener), `stage.takeOff { node }`, `stage.room`, `stage.setRoom { size, reverb, listening }` (`daw-rpc/src/stage.rs`; MCP tools `stage_*` follow from the table). `project.get` carries `room` and each strip's `stage`; `project.summary` shows `stage` with the track's channel. Each dot (`StageDot.tsx`) is in its track's color and glows with its meter (`session.levels`, like the track header). ## Input monitoring, multi-track recording, and takes

**Contracts.** `MonitorMode { Off, On, Auto }` is a node field `NodeKind::Audio::monitor` (in the project, undoable; default `Off`: with speakers and a microphone close together, monitoring causes feedback), edited via `TrackControl::set_monitor`. `InputChannels { Stereo, Left, Right }` and arming are session state in `AudioRecordControl` (`set_armed`, `set_input`; not written to the project). `InputMonitor` (implements `EngineLink`): the recorder hands the engine a table of `TrackInput { track, armed, channels }`, and the engine answers with `MonitorStatus { listening, input_rate, output_rate }` (`problem()` — a human-readable text). `LiveInput` is the input-reading side for the output audio thread; it is provided by `AudioCapture::take_live_input` (once), and `daw-bootstrap` (`wiring/audio.rs`) passes it to the engine with the command `DspCommand::SetLiveInput`. `TakeControl` (`ProjectTakes`) — clip takes.

**Monitoring signal path.** Besides peaks and the recording queue, the input callback (`daw-audio-cpal/src/capture.rs: InputFeed::feed`) writes channels 1–2 as stereo frames into a second `rtrb` queue (`live.rs`, 16,384 frames, mono goes to both channels) while the engine needs the input. There is one queue for the host's whole lifetime: the writing side moves into each new input stream via `Arc<Mutex<..>>` and is taken in the callback only with `try_lock` (like the engine in the output; it is busy only at the moment the stream changes). The input is opened by the host thread at the engine's request: `LiveInput::set_wanted` → an atomic → `Host::follow_monitoring` on every loop iteration (at least every 250 ms); the input is shared with recording and the level meter and is closed when nobody needs it; without running output the request has no effect; if it fails to open — one log entry per request. In the engine, `monitor.rs` (`InputListener`) on every segment: picks the listening audio tracks from the snapshot and the input table (`MonitorMode::hears_input(armed)`); the input is needed if someone is listening or armed (levels and instant recording start). The input block is added, by the track's channels (`InputChannels::sides`), into its node's buffer before the mixer — from there it goes through the track's fader, mute/solo, effects, and PDC, on top of its clips. Jitter buffer: we start when the input holds a block + margin (128 frames); if it runs short — the tail of the block is silent, `EngineLosses::monitor_underruns` +1 (logged by `engine_watch`), and the margin doubles up to 4096; if more than "block + 2 margins + segment" accumulates — the excess is discarded. When nobody is listening, the input is drained so latency does not build up. If the input rate ≠ the output rate, the input is not monitored (we don't do real-time resampling); `MonitorStatus::problem` says so, and the UI colors "IN" and shows the text. The engine's input table is `link/monitor.rs` (`MonitorTable`, a `u64` cell per track, atomics only).

**Multiple tracks.** There is one input: the recorder accumulates channels 1–2 in full, and on `stop` each armed track gets its own (`split.rs: track_sound`: `Stereo` — stereo, mono for a mono input; `Left`/`Right` — a mono file). The latency trim (configured or estimated + PDC, `take.rs`) is shared. Start errors: no armed audio tracks, the project has no file, the input failed to open (no device / no microphone access), a take is already in progress; arming and input changes during a take are rejected; deleted tracks are silently dropped.

**Takes.** Recording over an audio clip on the same track that it covers at least halfway, or that it lies entirely inside (of several — the one covered more, `split.rs: covered_clip`), does not create a new clip but becomes a new active take of that clip (`TakeControl::add_take`). Model: `ClipContent::Audio { sample, takes }` — `sample` plays, `takes` holds all takes in recording order (empty — a single sound; then the field is absent in JSON). The clip does not move or change length; all takes share its `offset_frames`, warp, pitch, volume, and fades, so a new take's audio is aligned to the clip start (`split.rs: align`): anything recorded before the clip start is trimmed, a late start becomes silence at the front; crossfades with neighbors do not change (the position is the same). Choosing the active take (`set_active_take`) and removal (`remove_take`; active → the last remaining one; one left → a regular clip; the only sound cannot be removed) are one undo step each; a new take from recording is inside the "Record audio" step. Removing a sample from the project removes it from takes; the clip is deleted only if that sound was its only one. The snapshot and processing (`clip_audio`, `ProcessJob`) use the sounding takes, so changing the take of a warped clip recomputes the audio.

**Take comping (by segments).** `ClipContent::Audio::comp: Vec<CompSegment { start_ticks, take }>` — from `start_ticks` (relative to the clip start) until the next segment, take `take` plays; ascending, the first at 0, neighbors are different takes (identical ones merge; if only one take remains, there is no comp and it becomes active); empty — the whole clip plays `sample` (the field is absent in JSON). The contract is `TakeControl::set_comp` (the whole comp, validated: the clip's takes, starts inside the clip, ascending, no more than `MAX_COMP_SEGMENTS`) and `choose_take_range(clip, from, to, take)` (the range `[from, to)`, the rest unchanged — the UI calls this), one undo step each; `set_active_take` and a new take from recording clear the comp; `remove_take` gives the removed take's segments to their neighbors. The comp follows the clip: split divides it (`take_rules::split_comp`), shortening drops segments past the end (`fit_comp`); warp, pitch, offset, volume, and fades are shared. How it sounds is one formula `Clip::take_span(i, &TempoMap)` (`daw-contracts/src/takes.rs`, no allocations): piece `i` with half of the transitions to its neighbors; a transition is an equal-power crossfade of `COMP_CROSSFADE_SECONDS` = 10 ms in tempo at the seam, no longer than half of the shorter adjacent segment. The engine (`audio_voices.rs`) starts one voice per piece (`AudioVoice::part`; audio — `clip_audio[(clip, take)]` or the take's sample), each from the "frames from the clip start" position, and multiplies by `sin` of the transition fraction — like overlapping clips; when the comp is edited during playback, voices follow their pieces, and the voice of a vanished piece (or of a piece with a different take) goes away. Export uses the same engine (`daw-render: clip_audio` — per take). RPC: `clips.setComp { id, segments }`, `clips.chooseTakeRange { id, from, to, take }`. UI: `ui/pianoroll/TakeLanes.tsx` in the audio clip panel — one waveform row per take (`clipWaves.takeColumns`), sounding pieces are highlighted (`domain/takes.ts: takeRanges`), dragging along a row calls `actions.clips.chooseTakeRange` (ends snapped to the timeline grid — `domain/takes.ts: draggedRange`, the grid comes from `TracksView` via `ClipPanel`; Alt — no snapping), clicking the name calls `setActiveTake`; on the timeline, a comped clip's waveform is assembled from the pieces of its takes, and its label is "⧉ comp". Mock — `mock/takeRules.ts` (the same rules). Tests: rules — `take_rules.rs`, contract — `daw-project/src/tests/takes.rs`, formula — `daw-contracts/src/takes.rs`, engine (seam without a click, the right take frames, editing during playback) — `daw-engine/src/tests/comp.rs`, export = live audio — `daw-bootstrap/tests/render_comp.rs`, wire — `daw-rpc/tests/warp.rs`.

**Loop recording.** With a loop region, playback jumps back at its end during an audio take, while the input arrives as one straight run. `AudioRecorder::start` remembers the loop region (`Running::loop_region`); on `stop`, after the latency cut, `passes.rs: passes` (pure) cuts the run where the jumps were: the first pass runs from the take start to the loop end (a pre-roll before the loop included), each next one is a whole loop, a stop mid-loop leaves a last pass that did not reach the end (`Pass::reached_end`); boundaries follow the tempo map and are summed in fractional frames, so many passes do not drift. One pass (no jump, or a take started at or past the loop end) is an ordinary take. With several, `take.rs: place_passes` gives each track one clip on the loop region — the clip the loop covers (`covered_clip` over the loop) or a new one at the loop start made from the first pass — and every pass becomes its take (`TakeControl::add_take`), aligned to the clip start like a single take (`split.rs: align`; the pre-roll is cut). The last pass that played to the loop end is made active (`set_active_take`); a pass cut short by stop stays as a take that does not play. Files are named "Recording <track> (pass N)"; all passes are written and imported before any clip changes, so a clip that does not fit loses no audio ("saved to Samples, but the clip was not created"). Everything stays one "Audio recording" undo step. Tests: `passes.rs` (cuts, pre-roll, mid-loop start, tempo change, no drift), `tests/take.rs` (a new clip with three passes, the clip under the loop, a pre-roll, a take past the loop end). Mock — `mock/loopPasses.ts` (the same cut in seconds) and `placePasses` in `mock/handlers/audioRecord.ts`. Note recording keeps its own loop recording inside the take clip (`daw-recorder`).

**Limitations.** A new take from recording clears the comp (undo brings it back). The loop region is read when the audio take starts: moving it during the take is not followed. Every loop pass is a take with no upper limit (a long take over a short loop makes many takes; one undo removes them all). Comp seams are exactly 10 ms (not configurable). A new take is recorded at the project tempo: in a warped clip whose source tempo is different, it will be stretched like the earlier ones (warp is shared). Takes with different sample rates are aligned precisely only if `offset_frames = 0` (the offset is shared, in frames). A recording that covers a clip by less than half and does not lie inside it becomes a new clip (if there is room). Monitoring works only when the input and output rates match; monitoring latency = device buffers + margin (from ~3 ms) + the track's PDC; with different devices the clocks drift — occasional clicks (visible in the log). Arming and input selection are not saved in the project. Input channels are only 1 and 2. The clips of a monitoring track play along with the input (they are not muted).

**How to add something similar** (e.g. inputs 3–4): a variant in `InputChannels` + `sides`/`file_channels`, recording and monitoring queues for more channels (`capture.rs`, `live.rs`), labels — `domain/recordInput.ts`.
## Live master meter: loudness, true peak, phase, the mono check (`audio.watchMasterMeter`, `audio.masterMeter`, `audio.setMono`)

The meters a mixing or mastering engineer keeps open while the song plays: momentary (400 ms), short-term (3 s) and integrated loudness (ITU-R BS.1770-4 / EBU R128), the loudness range (LRA, EBU Tech 3342), the true peak of the last 400 ms with the maximum held since the reset and a clip light at 0 dBTP, the phase correlation (−1…+1) of the last 400 ms, a vectorscope of the newest frames; and the mono check, which sums the master to mono for the speakers.

* **Where the measuring runs, and why on the control side.** The audio thread only copies the stereo master into a preallocated ring of atomics while the meter is watched (as cheap as the visualizer's window). Everything else runs on the meter's own thread with the export's BS.1770 code (`daw-render/src/loudness.rs`), so a live reading and an exported file's report are the same numbers. Two more reasons: the integrated loudness and the range gate over everything since the reset, a history that grows (the audio thread may not allocate), and the true peak oversamples every frame four times, work the audio callback is better without.
* **Contracts** (`daw-contracts/src/master_meter.rs`): `MasterTap` (engine → meter: `open_tap(on)`, `frames_after(end) → MasterFrames { start, samples, restart, sample_rate }`; `MASTER_TAP_FRAMES` = 2¹⁷, ~2.7 s at 48 kHz), `MasterMeter` (`watch(on)`, `reset()`, `reading() → Option<MasterReading>`, `None` while off), `MonoCheck` (`set_mono(on)`, `is_mono()`), `VECTOR_FRAMES` = 512, `CLIP_DBTP` = 0. In `Controls`: `master_meter`, `mono`.
* **Engine** (`daw-engine/src/scope.rs: MeterTap` in `Telemetry`, `MasterTap` and `MonoCheck` on `EngineLink`): the tap is the mix as it is exported — after the master's effects and fader, before the preview voice, the mono check, the ±1 clamp and the metronome. Frames are numbered by `written`, which only the audio thread moves (and only forward); the reader's numbers count from `opened`, so reopening never races the audio thread over the count. A reader that fell more than the ring behind gets the newest frames with `start` past its `end` (frames that may sit under an unfinished write, one segment's worth, do not count as held). When playback starts from tick 0 (`Plan::started` and the segment at the song start) the tap marks the restart frame, later by the compensation latency, because that is when the song start reaches the master. The mono check sums `(L + R) / 2` in `write_master` before the clamp, so what cancels is heard cancelled. It is an `AtomicBool` of the live engine's link: not in the project (not saved, like the song loop), and an offline engine has its own link (never exported).
* **Meter** (`daw-render/src/live/`): `LiveMeter` keeps the tap open while watched and a thread (`daw-master-meter`, every 50 ms, ended by a newer watch or by the meter going away) moves new frames into the measurement, so no frame is skipped however rarely the interface reads; `reading` and `reset` take the newest frames first. A restart mark is applied at its exact frame once the frames reach it; a new stream rate starts the measurement over (new filters). Frames the tap overwrote before the meter read them (a stall of seconds) are logged (`source: "meter"`). `measure.rs: Measurement` feeds `Loudness` and `TruePeak`, keeps the true peak and the phase sums (L², R², L·R) per 100 ms step for the newest four, and recomputes the readings when a step finishes (the gating runs over the whole history, so not on every read); the reset restarts the integration (to within the step under way) but not the momentary and short-term windows.
* **RPC/MCP** (`daw-rpc/src/audio.rs`): `audio.watchMasterMeter { on }`, `audio.masterMeter` (the reading or `null`), `audio.resetMasterMeter`, `audio.setMono { on }`; the tick has `mono` (`telemetry.rs`). MCP tools follow from the table (`audio_masterMeter`…), so an AI can read the loudness of what plays.
* **Frontend:** `api.audio.*` and `AudioActions` (`watchMasterMeter`, `masterMeter`, `resetMasterMeter`, `setMono`), `MasterReading`/`VECTOR_FRAMES`/`CLIP_DBTP` in `api/types/audio.ts`, `Tick.mono`; the panel and the badge — see "Live master meter" in the Frontend section. Mock: `mock/masterMeter.ts` (plausible readings from the mock master level with the backend's rules: off until watched, a fresh measurement on watch, the reset and playback from tick 0 restart the integration, the held peak and its clip, a vectorscope of the mock music) and `MockWorld.mono`/`meter`.
* **Another live reading** (say, a spectrum average): measure it in `live/measure.rs` from the same frames, add the field to `MasterReading` (contract, then its TS mirror and the mock), and show it in `MasterMeters.tsx` through a pure `domain/` function.
* **Tests:** the BS.1770 math (EBU Tech 3341 and 3342 references, windows, restart) — `daw-render/src/loudness.rs`; the meter against a fake tap (off until watched, the reference sine everywhere, correlation, clip and reset, the restart mark at its frame and one ahead, lost frames logged, a fresh watch) — `daw-render/src/live/tests.rs`; the tap and the mono check (closed until opened, every stereo frame numbered, the mix before the clamp/metronome/mono, a reader far behind, the restart mark, mono only on the output) — `daw-engine/src/tests/scope.rs`; wiring by ear (the demo measured from the start, mono on both speakers) — `daw-bootstrap/tests/all/render_meters.rs`; wire — `daw-rpc/tests/all/audio.rs`, `methods.rs`.

## Audio export: formats, loudness, part of the song (`project.export`)

**Contract** (`daw-contracts/src/export.rs`): `Exporter::export(ExportRequest, progress) → ExportReport`. Request: `{ path, sampleRate, bitDepth, stems, tailSeconds }` plus optional `format: "wav"|"flac"|"mp3"` (WAV by default), `mp3Bitrate` (128/192/256/320, 320 by default), `normalize: { lufs, truePeakDb? }` (target −40…0 LUFS, ceiling −12…0 dBTP, −1 by default), `dither` (on by default for 16 bits; the rule is `ExportRequest::dithers`), `range: "song"|"loop"|{ fromTick, toTick }` (the whole song by default). Without the new fields the behavior is unchanged (except for dither at 16 bits). Response: `{ files (the first is the mix), frames, loudnessLufs, peakDb }` — BS.1770 loudness and true peak of the mix after adjustment; `null` means silence. `ExportRequest::new(path)` is the default request (for tests and the console).

* **Order** (`daw-render/src/export/mod.rs`): checks before rendering (sample rate, format — `encode::check`, loudness target — `loudness::check`), the range (`range.rs`), the mix, then bus stems (`stems.rs`, files `<mix>_<node>_<bus>.<extension>`). The file extension follows the format (`file_for_format`: `.wav/.flac/.mp3` is replaced, anything else is appended to). The same offline engine plays (`load_engine`) with `transport.seek(range start)`.
* **Part of the song** (`range.rs`): "song" — 0…end of the last clip, "loop" — the loop region (none — rejected), a range — as given; the length follows the tempo map plus the tail, at most one hour. Clips starting at the range end or later are removed, clips crossing the end are shortened to it (their fade-out is dropped: otherwise it would shift inside the range) — so the tail holds decaying effects and released notes, not the start of the next part. Notes started before the range start do not sound (as after seeking); an audio clip cut by the range end stops without a fade.
* **Formats** (`encode/`, trait `Encoder { write(chunks), finish }`; `write_file` creates the folder and deletes an unfinished file): WAV — hound (`wav.rs`); FLAC — `flacenc` (pure Rust, Apache-2.0; `flac.rs`: blocks of 4096 frames are encoded while rendering, the STREAMINFO header with MD5 is rewritten at the end; 16/24 bits only); MP3 — LAME 3.100 via `mp3lame-encoder` (`mp3.rs`: CBR, joint stereo, best quality; above 48 kHz LAME resamples down by itself; there is no Xing/LAME tag — decoders see the encoder delay and the padding of the last frame, up to ~0.08 s of silence). Rounding to integers — `pcm.rs: Quantizer`: TPDF dither of ±1 LSB (sum of two uniform values, xorshift with a fixed seed — export is reproducible), without noise shaping; without dither — the old rounding.
* **Loudness adjustment** (`loudness.rs`, `scratch.rs`): the mix is rendered once into a temporary float file (`<file>.render-tmp` next to the export) while measuring loudness (`daw-render/src/loudness.rs: Loudness` at the export sample rate) and true peak (`TruePeak`: 4× sinc oversampling with a 12-tap Hann window); gain = min(target − loudness, ceiling − peak); then the temporary file is read with this gain into the format file and measured again — the report carries what was measured in the written file. There is no limiter: clipping peaks is distortion; if there is not enough headroom, the file is quieter than the target, and this shows in `loudnessLufs`. Stems are rendered with the same gain (sum of stems = mix). Why a file: 20 min at 48 kHz in memory is ~460 MB, and a second render takes twice as long and does not necessarily produce the same sound (randomness in plugins). The price is disk space (4 min at 48 kHz ≈ 90 MB, an hour at 192 kHz ≈ 5.5 GB). The temporary file is deleted on failure too; if it cannot be deleted — an error with the path. Silence (below −70 LUFS or shorter than 0.4 s) is not adjusted — rejected. Loudness and peak are measured even without adjustment (cheap compared to rendering); for MP3 — before compression.
* **Licenses.** `flacenc` is Apache-2.0. LAME is LGPL: `mp3lame-sys` builds it from C sources at build time (a C compiler is needed — Xcode Command Line Tools) and links it statically. When distributing the app, include the LGPL text and a LAME notice and make it possible to rebuild the app with a modified LAME (for an open-source GPL project the sources are enough). Pure-Rust MP3 encoders were not chosen: `shine-rs` is also LGPL and lower quality, `rusty_mp3` is too young.
* **RPC** (`daw-rpc/src/project.rs`): `project.export` with a full description of the fields for the AI. **Interface:** `ui/transport/ExportDialog.tsx` — format, sample rate, bit depth (FLAC without float) or MP3 bitrate, "Normalize to" (−14 streaming, −16 podcasts, −9 club, custom) and the peak ceiling, part of the song (whole / loop / selected clips — `domain/exportAudio.ts: clipsRange`), tail, dither (for integer formats), stems; the path and dialog filter follow the format (`pathForFormat`, as in the backend); which settings apply to which format (FLAC has no float, dither only for integer PCM) and the request built from the form are `domain/exportAudio.ts` (`bitDepthsFor`, `isIntegerPcm`, `exportOptions`); the result is a toast from the `audioExport.render` action (`actions/audioExport.ts`) with loudness and peak (`loudnessSummary`, flags a shortfall from the target). The mock (`mock/handlers/project.ts`) — extension by format, plausible numbers, the same rejections (FLAC float, no loop).
* **Tests:** JSON contract — `daw-contracts/src/export.rs`; encoders (FLAC round-trips bit-exact at 16/24 bits with and without dither, MP3 — duration, size and level at all bitrates, 96 kHz, WAV, cleanup of unfinished files) — `daw-render/src/encode/tests.rs`; dither (triangular, mean 0, touches only the LSB) — `encode/pcm.rs`; K-filter at any sample rate, true peak, momentary and short-term windows, the loudness range (EBU Tech 3342) and the restart — `daw-render/src/loudness.rs`; gain and ceiling — `export/loudness.rs`; range and loop — `export/range.rs`; temporary file — `export/scratch.rs`; full session (−14 LUFS on a tone ±0.5, −1 dBTP ceiling with an honest report, silence rejected, range and loop by length and without clip audio in the tail, FLAC/MP3 with stems readable by the sample decoder) — `daw-bootstrap/tests/render_export.rs`; wire — `daw-rpc/tests/project.rs`.
* **Similar** (a new format): a module in `encode/` with an `Encoder`, an `ExportFormat` variant (+ `extension`), branches in `encode::open`/`check`, a filter in `api/dialogs.ts` and an entry in the dialog.

## Rendering a track to audio (bounce, freeze)

**Contracts** (`daw-contracts/src/bounce.rs`): `TrackRender` — "the sound of one track on its own" (`render_track(project, track, tail) → TrackSound { start_tick, data }`) and `TrackBounce` — "replace a track with its sound" (`bounce`, `freeze`, `unfreeze`); the freeze mark is `InstrumentSpec::frozen: Option<TrackId>` (id of the audio copy), the "sounding" instrument is `Track::sounding_instrument()` (`None` for a frozen one). The track's sound path is `Graph::insert_path` (the same convention as the mixer's `domain/mixerStrips.ts`: the first regular connection is "post-fader", an insert is an effect with nothing else feeding into it; sends do not break the path).

* **What the copy contains.** In this graph the source fader sits BEFORE the inserts (a compressor on the track hears the sound after the track volume), so "pre-fader" would sound different here. Copy = the sound at the output of the track's path: instrument (or audio clips) → track volume and pan (with automation) → inserts (with their automation and the levels of the connections between them). Track mute/solo, the output connection, sends, buses and the master are not included; sidechain inputs of inserts are silent. The copy gets volume 1 and pan 0 and goes to the same place at the same level as the track's path did (`set_output` + `connect`), so the project sounds as before. Sends are not transferred to the copy.
* **Render** (`daw-render/src/track.rs`, `TrackRender for OfflineExporter`): `isolate` builds a project containing only this track, its clips, the nodes of its path and the master at unity (a pure function with tests); the range is from the start of the first clip to the end of the last plus the tail (`check_tail`: `0..=MAX_TAIL_SECONDS`, the same rule as the export tail; 2 s by default); 48 kHz stereo, in memory (at most 20 minutes). The engine is the same offline instance as for export (`load_engine`, seeked to the start of the first clip).
* **Placement** (`daw-project/src/bounce.rs`, `ProjectBounce`): rendering happens BEFORE the undo group (the project is not locked while the sound is computed) → WAV (`SampleWriter`) into the project's `samples/` named "<track> (audio)" / "(freeze)" (`AssetStore::new_asset_path`) → undo group: import the sample (`SampleCatalog`), an audio track (`TrackControl::add_track` + `move_track` right below the source), a clip at the position of the first clip (`ClipControl::add_audio_clip`), volume and output of the copy (`GraphControl`); then `bounce` mutes the source (node mute), while `freeze` writes the freeze mark through the core. Failure — `cancel_group` (the WAV stays in `samples/`). `unfreeze` is one group: remove the copy (`remove_track`) and its samples if they do not play anywhere else, clear the mark; if the copy was deleted manually, only the mark is cleared. A project without a file, no clips, a frozen track (for `bounce`/`freeze`), an audio track (for `freeze`) — rejected with a clear message.
* **Freezing in the engine.** DSP reconciliation (`service/sync.rs`) and offline rendering create an instrument only for `sounding_instrument()`: a frozen instrument is removed from the engine (less load), its notes are silent. `TrackControl::set_instrument` on a frozen track is rejected ("unfreeze first"): the copy sounds with the previous instrument. Templates clear the freeze mark.
* **RPC:** `tracks.bounce { id, tailSeconds? }` → id of the copy, `tracks.freeze { id, tailSeconds? }` → id of the copy, `tracks.unfreeze { id }` (`daw-rpc/src/bounce.rs`). These methods (like `presets.save`, `templates.save`, `project.export` and `analysis.*`) are registered with `add_flushing`: before them, open plugin windows hand their state to the project (`PluginStateFlush`).
* **Interface:** the track menu on right-click on the header (`ui/tracks/TrackMenu.tsx`, "Audio" section): "Bounce to audio", "❄ Freeze" / "Unfreeze"; a frozen track shows ❄ in its header. Actions — `actions/bounce.ts` (a loading indicator while rendering, errors as a toast, the copy is selected after success). Mock — `mock/handlers/bounce.ts` (creates a sample of the right length and a clip; the copy's output is always the master).
* **Limitations.** Latency of insert plugins (PDC) is not compensated in the copy: the copy's sound is late by the inserts' latency (0 for built-in effects). The WAV is 24-bit: sound above 0 dBFS is clipped. Sends and automation of the output connection are not transferred. The sound is computed entirely in memory.
* **Tests:** `isolate` and the range — `daw-render/src/track.rs`; `Graph::insert_path` — `daw-contracts/src/graph/tests.rs`; the `TrackBounce` contract (copy position, output, volume, mute, one undo step, rejections, freeze/unfreeze and DSP) — `daw-project/src/tests/bounce.rs` (render double); full session with the built-in synth — `daw-bootstrap/tests/render_bounce.rs` (the copy's WAV = the track's sound in the mix; the mix after bounce, after freeze and after unfreeze sounds as before); wire — `daw-rpc/tests/arrangement.rs`.
* **Similar** (e.g. "bounce the selected range"): the range is a `TrackRender` parameter, placement is the same `ProjectBounce::place`.

## Checking the result by ear: levels and mix check (`analysis.*`)

Why: an AI building a track through MCP cannot hear — a bass at 0.3 % volume or with a 40 Hz cutoff was silent, and this was only found out by exporting a WAV and computing RMS by hand. Now the check is a single call.

**Contracts** (`daw-contracts/src/analysis.rs`): `MixAnalysis` — "measure how the project sounds" (`levels(project, LevelRequest) → LevelReport`) and `MixCheck` — "find what makes the project sound different from what was intended" (`check(project, from, to) → Vec<Finding>`). These are two jobs (measuring and judging), hence two contracts and two entities; the project is passed as a copy (RPC takes `ProjectView::snapshot`), so the computation neither locks the project nor interrupts playback.

* **Levels** (`daw-render/src/analysis/`, `LevelMeter` on top of `OfflineExporter::load_engine`): targets — `master` (the whole project, as in export), `track` (the track's path up to its output — `track::isolate`, as in "Bounce to audio": without mute/solo, buses and master; a track with no clips in the range is not rendered, its levels are `null`) or `bus` (`stems::stem_graph` + master at unity and the bus output at level 1, without master automation). The range is `[fromTick, toTick)` (the whole project by default), rendered from `fromTick` at 48 kHz (the BS.1770 K-filter is computed for any sample rate — `loudness.rs: k_filter`, at 48 kHz it matches the standard's table; export and the live master meter measure with it too); sections — every `resolutionBars` bars (`TempoMap::bar_index`/`bar_tick`, which account for meter changes). Measurement runs in chunks during rendering (`meter.rs`: `Meter` — peak and RMS over both channels for the whole range and for each section; `loudness.rs: Loudness` — BS.1770-4 integrated loudness: K-filter, 400 ms blocks with a 100 ms step, gates at −70 LUFS and −10 LU) and does not accumulate in memory. Below −90 dBFS — `null`. Values are rounded to 0.1 dB.
* **Cost and limits.** Each target is a separate offline render: `per: track` costs "number of tracks with clips × range length" (the built-in synth renders many times faster than real time), `analysis.check` — tracks + master. The range is at most `MAX_ANALYSIS_SECONDS` (10 minutes); `resolutionBars` — 1…64 (4 by default). Peak is sample peak (not true peak); notes started before `fromTick` do not sound in the range, the tail after `toTick` is not included; solo on tracks outside the bus does not affect bus levels; insert latency (PDC) is not compensated — as in track bounce.
* **Check** (`daw-mixcheck`): rules are pure functions in `rules.rs` (thresholds and heuristics are described at the top of the file): a silent (`silentTrack`, error) or nearly inaudible (`quietTrack`, warning: the loudest bar with clips is below −45 dBFS RMS) track — from per-bar track levels on bars with its clips (frozen tracks are skipped); master clipping (`masterClipping`, bar peak ≥ −0.1 dBFS, bars in `ranges`), silent (`silentMaster`) and quiet (`quietMaster`, < −30 LUFS) master; mute (`mutedTrack`/`mutedBus`) and solo (`soloedTrack`/`soloedBus`); tracks and buses that do not reach the master through regular connections (`notRouted`; a node that is only a sidechain key is not an error), empty buses (`emptyBus`); suspicious instrument parameters (`suspiciousParam`: a numeric parameter with "gain"/"volume"/"cutoff" in its name or label — from the catalog's `ParamInfo` — in the first 1 % of its range, wide ranges starting from a positive minimum — on a log scale); automation outside the target's range (`automationOutOfRange`); disabled (`disabledPlugin`) and missing (`missingPlugin`) plugins, bypassed effects (`bypassedEffect`). Findings are sorted by severity. If the sound could not be computed (invalid range, missing plugin) — a `renderFailed` finding and a log entry (`analysis`); the other rules still work. `MixChecker` only gathers inputs: per-bar track and master levels, kind parameters from the catalogs, `PluginScanner::installed` (disabled) and the catalogs' `defaults` (missing).
* **RPC** (`daw-rpc/src/analysis.rs`): `analysis.levels { fromTick?, toTick?, per?: "track"|"bus"|"master", resolutionBars? }` → `{ fromTick, toTick, sections: [{ bar, fromTick, toTick }], targets: [{ id, name, level: { peakDb, rmsDb } | null, loudnessLufs, sections: [{ peakDb, rmsDb } | null] }] }`; `analysis.check { fromTick?, toTick? }` → `[{ severity: "error"|"warning"|"info", code, message, track?, node?, lane?, ranges?: [[from, to]] }]`. Alongside, for "build and check": `clips.addNoteMany { clips: [NewNoteClip] }` → clip ids (one undo step, all or nothing) and `project.clear { keepTempo?, removeSamples? }` (`ProjectClear`, one undo step; `ProjectIo` is only the file lifecycle, so clearing is its own job). The MCP instructions ask the AI to call `analysis_check` and fix the findings before reporting "done". The frontend and mock do not have these methods: the interface does not call them (this is the AI's job).
* **Tests:** level and loudness math (EBU Tech 3341 reference: a 1 kHz sine at −23 dBFS in both channels = −23.0 LUFS; −20 dBFS in one channel = −23 LUFS), sections, range and bus stem — `daw-render/src/loudness.rs` and `analysis/`; rules on synthetic projects and levels, and assembling findings with doubles — `daw-mixcheck/src/tests.rs`; full session (per-bar levels match the export, the built-in synth at volume 0 is found, master clipping with its bar) — `daw-bootstrap/tests/render_analysis.rs`; `add_note_clips` — `daw-project/src/tests/batch.rs`, clearing — `tests/clear.rs`; wire — `daw-rpc/tests/analysis.rs`; MCP tools — `daw-mcp/tests/protocol.rs`.
* **Similar** (a new rule): a function in `rules.rs` → a line in `MixChecker::check` → a test in `tests.rs`; a new level target is a branch in `targets_of` in `daw-render/src/analysis/mod.rs`.

## Project summary: orienting without reading the whole project (`project.summary`)

Why: `project.get` of a real song carries every note, automation point and parameter; an AI that reads it to answer "what plays in the chorus" fills its context before it starts working. `project.summary` answers "what is here and where" in a few hundred lines, and the MCP instructions tell the AI to start with it.

* **Contract** (`daw-contracts/src/summary.rs`): `ProjectSummary::summarize(project) → Summary` — "describe the project briefly". The project is passed in (RPC takes `ProjectView::snapshot`, as for `analysis.*`); nothing is rendered or changed, it never fails. Levels are not part of it (they need a render): `analysis.levels`.
* **What is in it:** name, starting tempo and meter (+ whether they change), the song end (the end of the last clip) and its bar count, the loop; **sections** from the markers (to the next marker; the last one to the song end) with the tracks that have clips in them; every **track** — instrument kind or audio, frozen, folder, MIDI effects, its source node and channel (volume, pan, mute, solo — inline), inserted effects and output, number of clips and the merged spans where they play, notes in the clips' content and their pitch range, sound names for audio clips; **buses** with their channel, the tracks whose sound reaches them (sidechain keys do not count), their inserts and output; **shared effects** (not an insert of any track or bus path: several inputs, only a send, or none) with the effects after them; master volume; **automation** lanes with their target and spans. Ticks are absolute, spans `[start, end)`, bars from 1 (as in `analysis.levels`).
* **Implementation** (`daw-summary`, `Summarizer`): pure functions over the project. What counts as an insert is the graph's own path rule `Graph::insert_path` (the mixer view uses the same), so the summary and the mixer agree. Tests on a synthetic project with inserts, a send, a sidechain and a shared limiter — `daw-summary/src/tests.rs`; wire — `daw-rpc/tests/all/project.rs`.
* **Similar** (a new field): the field in the contract type → a line in `Summarizer` → a test. The frontend does not call it (the interface has the whole project).

## Project templates and presets

Both jobs live in the application state folder (not in the project) and are implemented in `daw-persistence`; the contracts and shared name rules (`check_preset_name`: no `/ \ :`, control characters or leading dot, up to 64 characters) are in `daw-contracts/src/presets.rs`; on the frontend the same rules are in `domain/presets.ts`.

* **Templates** (`ProjectTemplates`, `TemplateFolder`, `templates.rs`): a template is a small project folder `<state>/templates/<name>/template.dawproj` + `samples/`, written by the same `ProjectStorage` as a project (copying sounds and relative paths work on their own). It includes the structure: tracks with instruments (parameters and plugin state), colors and folders, the graph (effects, buses, connections, faders), the tempo map. Removed: clips, automation, loop, markers and samples, except sampler sounds (parameters of kind `ParamKind::Sample` — per the catalog, `structure_of`); the freeze mark is cleared. `create_project(template, file)`: the template is read, gets the file's name, is written into a new folder (sounds are copied) and opened with `ProjectIo::load`. There are no built-in templates yet.
* **Presets** (`Presets`, `PresetFolder`, `presets.rs`): `<state>/presets/<kind>/<name>.json` = `{ kind, params, state? }` (in the kind's folder name, the colon and other characters are replaced with `_`; the kind inside the file is checked on apply). The target is an `EditorTarget` (a track instrument or an effect node); a preset belongs to a kind and can be applied to any target of that kind. `apply` is one undo group "Preset 'name'": first the plugin state (`PluginStates::set`), then the parameters on top (`TrackControl::set_instrument_param` / `GraphControl::set_effect_param`); parameters the kind no longer has are skipped. RPC: `presets.list { kind }`, `presets.save { target, name }`, `presets.apply { target, name }`, `presets.remove { kind, name }` (`daw-rpc/src/presets.rs`). Mocks — `mock/handlers/templates.ts`, `mock/handlers/presets.ts` (in memory; no plugin states).
* **Tests:** `structure_of` and the preset file format — unit tests in `templates.rs`/`presets.rs`; contracts on a full session — `daw-bootstrap/tests/presets_templates.rs` (instrument and effect presets: save, apply in one undo step, delete, rejected targets and names; templates: structure without clips, sampler sound copied into the new project, the new project opened, overwrite and delete); wire — `daw-rpc/tests/arrangement.rs`.
* **Similar** (e.g. built-in templates): a second, read-only folder in `TemplateFolder::list`/`existing`.

## Musical note edits and the controller lane in the piano roll

* **Contract.** `NoteControl::transform_notes(clip, ids: Option<Vec<NoteId>>, NoteTransform)` (`daw-contracts/src/notes.rs`): one edit is one undo step; no `ids` — all notes of the clip, an empty list — `Invalid`, an unknown note — `NotFound`, a clip without notes — an empty response without a step. `NoteTransform`: `Quantize { grid, strength 0..1, ends }` (grid from the start of the content, nearest line, halfway — forward; `ends` — the end too, no closer than one step to the start), `Humanize { timing_ticks ≤ MAX_HUMANIZE_TICKS, velocity ≤ 126, seed }` (mulberry32 generator: one seed — one result; no seed — taken from the clock), `Transpose { semitones }` (a note beyond 0..127 — `Invalid`, nothing changes: we do not clamp, so a chord is not silently flattened), `FitToScale { root 0..11, scale: Scale }` (nearest degree, halfway — down), `Legato` (up to the start of the next note in the group of any pitch; a chord — up to one common start; the last notes do not change). Groove and variations are below. Timing edits do not push notes past the content (with a manual length the note is moved back). Why a method in `NoteControl` rather than its own trait: the job is the same — "edit the notes of a clip"; only the rule changes; the rules themselves are pure functions in `daw-project/src/note_transforms.rs`, separate from the content rules in `note_rules.rs`.
* **RPC** (`daw-rpc/src/notes.rs`): `notes.quantize { clip, ids?, grid, strength? = 1, ends? = false }`, `notes.humanize { clip, ids?, timingTicks, velocity, seed? }`, `notes.transpose { clip, ids?, semitones }`, `notes.fitToScale { clip, ids?, root, scale: "major"|"minor"|"dorian"|"phrygian"|"lydian"|"mixolydian"|"harmonicMinor"|"pentatonicMajor"|"pentatonicMinor"|"chromatic" }`, `notes.legato { clip, ids? }` → the group's notes after the edit. The interface and the AI use the same logic.
* **Frontend.** The mock repeats the rules one to one — `domain/noteTransforms.ts` (rounding and mulberry32 as in Rust; matching numbers are pinned by the test `humanize_numbers_match_the_frontend_mock`); the list of scales `SCALES` and `inScale` for row highlighting live there too. Actions — `actions/notes.ts` (`quantize`, `humanize`, `transpose`, `fitToScale`, `legato`, `setControllerLane`). Panel — `ui/pianoroll/NoteTools.tsx`: "Quantize / Humanize / Transpose / To scale / Legato" over the selection (no selection — over all notes), parameters in small popovers; "To scale" keeps the piano roll's scale and turns on highlighting of its rows (`render.ts`, `GridView.scale`). ⌥Q quantizes to the current grid (plain Q is taken by the keyboard piano).
* **Controller lane** (`ControllerLaneView.tsx`, collapsible so it does not take space from the note grid): lane choice (Pitch bend, Modulation CC1, Sustain CC64, Expression CC11, Aftertouch, "Other CC…"; lanes with points are marked "●"), dragging draws points on grid steps and replaces the points in the covered span, right-click deletes the nearest point; one gesture is one `notes.setControllerLane` edit (empty — the lane is removed), which shows the lane at once (`patchProject`), like `notes.updateNotes` does for a note drag, so a finished gesture never flashes the old shape. Pure rules — `domain/controllers.ts` (kinds and labels, value limits, `drawStroke`, `removeNear`, `strokeSegment`, and the pencil stroke `startStroke`/`extendStroke`/`strokeOver` shared with automation patterns), step drawing — `controllerRender.ts`, mock checks — `mock/noteOps.ts: setControllerLane` (like `note_rules::set_controller_lane`).
* **Groove** (`NoteTransform::Groove { template, amount }` and `GrooveFromClip { source, amount }`; rules — `daw-project/src/groove.rs`). A groove is a table on a sixteenth-note grid: for each step, a start offset in ticks and a velocity in percent. A note takes the step of the nearest sixteenth from the start of the content (`i % table length`); the offset and the velocity deviation from 100 % are applied scaled by `amount` 0..1; the length is kept, the note does not leave the content. **This is a note edit, not a playback setting:** the offset is added to the current position (straight notes get exactly the template, applying the groove again adds it once more); to revert, undo. `GrooveTemplate` templates (a table per beat of four sixteenths, plain data): `swing { grid: eighth | sixteenth, percent 50..75 }` (the second eighth of the beat at `percent` % of the pair, sixteenths between them halfway; `sixteenth` — MPC swing), `laidBack { ticks ≤ 120 }` ("laid back": everything off the beat is later), `pushed` ("pushed": earlier), `accent { percent 100..200 }` (notes on beats are louder). "Take groove from clip": `ProjectNotes` extracts a table from the reference clip (`extract_groove`: the bar of the meter at its start; for each sixteenth, the average deviation from the line and the average velocity relative to the clip's average velocity; an empty step — no change) and passes it to the pure function through `Surroundings` (another clip is not the business of a function over one content). A deviation larger than half a sixteenth belongs to the neighboring line — strong eighth swing (> 62 %) cannot be extracted this way. RPC: `notes.groove { clip, ids?, template, amount? = 1 }`, `notes.grooveFromClip { clip, ids?, sourceClip, amount? = 1 }`. Tests — `daw-project/src/tests/groove.rs`.
* **Pattern variations** (`NoteTransform::Vary(Variation)`, rule — `daw-project/src/variation.rs`): the only edit that removes and adds notes (the response is the remaining notes of the group, then the new ones with new ids). `Variation { seed?, density −1..1, pitch, rhythm, velocity 0..1, scale?: { root, scale } }` — probabilities per note. Each note of the group, in order, takes exactly six random numbers (mulberry32) regardless of the settings — so moving one slider does not reshuffle the rest: remove (`-density`), neighboring pitch (a scale degree or, without a scale, a neighboring pitch among the group's pitches; at the edge — the other way), rhythm (a sixteenth earlier / later, split in half on the grid, merge with the next note of the same pitch), velocity spread (up to ±32). Notes on the first beat of a bar (bar of the meter at the clip start) are anchors: they do not move or change pitch, and are removed only when `density` < −0.5 (and with probability at most 0.5). Positive density adds `round(density · n)` notes on free sixteenths within the content length; pitch, velocity and length come from a random note of the group. Any change after which notes of the same pitch would overlap or a note would leave the content is skipped. `NoteControl::vary_to_new_clip` — a copy of the clip right after it (`clip_rules::copy_after`, the same as `duplicate_clip`) and a variation of the copy in one core edit: one undo step. RPC: `notes.vary { clip, ids?, seed?, density?, pitch?, rhythm?, velocity?, scale? }` (missing field — 0), `notes.varyToNewClip { … }` → the new clip. Without a seed both pick a random one. Tests — `daw-project/src/tests/variation.rs`, wire — `daw-rpc/tests/note_transforms.rs`.
* **Groove and variation frontend.** Copies of the rules — `domain/groove.ts` (which also holds the ready-made `GROOVE_PRESETS` for the menu) and `domain/variation.ts`; the generator and rounding are shared from `domain/noteTransforms.ts` (`random`, `roundAway`, `fit`). Matching numbers are pinned by the tests `groove_numbers_match_the_frontend_mock` and `variation_numbers_match_the_frontend_mock` (numbers computed by the TS copy). Mock: `notes.groove/grooveFromClip/vary/varyToNewClip` in `mock/handlers/notes.ts` (the clip copy uses the shared `mock/clipRules.ts: duplicateClip`). Actions — `groove`, `grooveFromClip`, `vary`, `varyToNewClip` in `actions/notes.ts`; the "Groove ▾" panels (template, amount, "From clip" — another note clip in the project) and "Variation ▾" (sliders, seed with 🎲, "In scale" — the scale from "To scale", "Apply" / "To new clip") — in `NoteTools.tsx`.
* **How to add another note edit:** a `NoteTransform` variant + a function in `note_transforms.rs` and a test, an RPC line, a copy in `domain/noteTransforms.ts` and a mock handler, an action method and a button in `NoteTools`.

## MIDI controllers: pitch bend, CC, aftertouch and MIDI learn

Performance expression (pitch wheel, modulation wheel, pedal, pressure) reaches instruments from clips, from a MIDI keyboard and from MIDI files; controller knobs can be assigned to any project parameter.

* **Model** (`daw-contracts/src/model.rs`). `NoteContent::controllers: Vec<ControllerLane>` (JSON `controllers`, not written when empty), at most one lane per kind. `ControllerLane { kind: ControllerKind, points: Vec<ControllerPoint { tick, value }> }`; `ControllerKind` — `{ "type": "cc", "number": 0..=119 }` | `{ "type": "pitchBend" }` | `{ "type": "aftertouch" }` (channel pressure); `range()` — `-1..=1` for pitch bend (0 is the center), `0..=1` for the rest; `CC_MODULATION` = 1, `CC_SUSTAIN` = 64, `MAX_CC_NUMBER` = 119 (120–127 are channel mode messages). Point times are from the start of the clip content, as for notes; lanes repeat with the content (`loop_ticks`). **Between points the value holds as a step** (no smooth transition): this is how MIDI messages themselves behave, and smoothness comes from dense points — simpler and identical for the engine, files and drawing.
* **Editing** — `NoteControl::set_controller_lane(clip, kind, points)` (`daw-contracts/src/notes.rs`; rule — `daw-project/src/note_rules.rs: set_controller_lane`): replace or create a lane, empty points — remove it; sorted by tick, among duplicates the last one wins; a CC number above 119 or a tick past the content (with auto length — past `MAX_CLIP_LOOP_TICKS`) — `OutOfRange`, a value outside `range` — `Invalid`, more than `MAX_CONTROLLER_POINTS` (4096) — `LimitReached`; one undo step. Auto length takes points into account (`fit_length`), a manual length drops points beyond it. RPC `notes.setControllerLane { clip, kind, points }`; tests — `daw-project/src/tests/controllers.rs`, wire — `daw-contracts` (`controller_lanes_use_the_exact_wire…`) and `daw-rpc/tests/controllers.rs`.
* **Instruments.** `Instrument::controller(kind, value)` is a required method (built-ins implement it explicitly): the sampler — pitch bend ±2 semitones (speed of all voices) and the CC64 pedal (voices released while the pedal is down fade out when the pedal is released); drums do nothing (a hit plays to its end on its own). `LiveNoteSink::controller(track, kind, value)` — the same live (the value is clamped to `range`); RPC `live.controller`.
* **Engine** (`daw-engine/src/controllers.rs`: `ControllerSchedule`, capacity 8192, no allocations). Lane points of note clips within the segment's tick window (repeats and phase as for notes); `play_events` in `engine.rs` plays instruments in chunks between note **and** controller events (a controller on the same tick goes before the note: bend and pedal already affect it). **Chase:** after start, seek and loop wrap (`Plan::release_all` while playing), the schedule adds at the start of the segment the value that holds at the new position (the last point strictly before it inside the clip — accounting for repeats and phase), so jumping into the middle of a bend sounds like playing from the start. **Reset:** on every `release_all` (stop, pause, seek) `InstrumentRack::reset_controllers` sets to 0 those of pitch bend, aftertouch, CC1 and CC64 that the instrument received since the previous reset (like "Reset All Controllers"; other CCs, e.g. volume CC7, are left alone; untouched ones are not sent — the plugin gets no extra messages). Tests — `daw-engine/src/tests/controllers.rs` (exact frame, order relative to notes, chase, reset, loop).
* **VST3** (`daw-vst3/src/midi_map.rs`: `MidiAssignments`; plugin calls — `instance/midi.rs`). In VST3, controllers are not events but parameters that the plugin names through `IMidiMapping::getMidiControllerAssignment(bus 0, channel 0, number)` (CC 0..119, `kAfterTouch` = 128, `kPitchBend` = 129). The table is built when the instrument is created; `Vst3Instrument::controller` puts the parameter change (pitch bend `-1..1` → `0..1`) into the same `PendingChanges` queue as parameters; offset 0 is exact because the engine plays the instrument in chunks between events. If the plugin does not listen to a controller, the change is dropped and counted in `BlockFaults` ("MIDI controllers the plugin does not listen to"). A real plugin is checked by `tests/synth.rs: pitch_bend_reaches_the_synth_through_its_midi_mapping` (note frequency from zero crossings: 440 → 493.9 Hz; the test is skipped if the synth is not built).
* **Built-in synth** (`daw-synth`): pitch bend ±2 semitones (`Engine::set_pitch_bend`), the CC1 modulation wheel opens the filter up to 4 octaves above the high cut (`set_modulation`); `prepare`/`reset` return the wheels to rest; other controllers are ignored.
* **Live input** (`daw-midi/src/input.rs`): `parse_message` parses notes, CC, pitch bend (14-bit) and channel pressure; `route` sends notes and controllers to the track's instrument, but a CC is first offered to `MidiMappingControl::control_change` — a consumed one (learning or an assignment) does not go to the instrument; CC 120–127 do not go to instruments. Value conversion — `values.rs` (14-bit: 0 → −1, 8192 → 0, 16383 → exactly 1; 7-bit: n/127) — shared with files.
* **Recording** (`daw-recorder/src/controllers.rs`: `ControllerTake`). The engine hands played controllers to the recorder (`RecordedEvent { track, message: LiveMessage::Note | Controller, tick }`); the track's first event binds the take clip the same way a note does (`ensure_bound`). Points are written into the take clip's lane with `set_controller_lane` (in the same "Record" group). **Thinning:** a point is kept only if the value changed by more than 1/127 or more than 10 ms have passed since the last kept one (seconds — per the tempo map); a small frequent change is deferred and kept at the end of the take — the last knob position is not lost; identical consecutive values are not written. The span recorded in a loop pass replaces the lane points that were in it before the take; the next pass replaces what was recorded in the previous ones (as for notes).
* **MIDI files** (`daw-midi/src/file/`): clip export — points as they are, project export — with repeats unrolled (a track with only controllers is written too); on one tick: note-offs, controllers, note-ons. Import into a clip takes the controllers from the same file track as the notes, drops consecutive repeated values and replaces the notes and **all** lanes of the clip in one undo step (`MidiFiles` holds `HistoryControl`: the "Import MIDI" group, failure — `cancel_group`).
* **MIDI learn** — `MidiMappingControl` (`daw-contracts/src/midi.rs`), implementation `ProjectMidiMappings` (`daw-project/src/midi_mappings.rs`), wiring — `daw-bootstrap/src/wiring/project.rs` (`MidiInputService` gets it too). Assignments live **in the project** — `Project::midi_mappings: [{ cc, channel?, target: ParamTarget, min?, max? }]` (JSON `midiMappings`): the target is nodes, tracks and parameters of this project; their ids mean something else in another project; assignments are saved and undone together with the project. Targets are the same as for automation and are checked by the same rule `ops::validate_target`. `learn(target)` arms learning (in memory, not in the project); the next CC creates an assignment (the channel is the one it came from; the parameter range comes from the catalog and is remembered in `min`/`max`, so knob movement does not go to the catalogs; a previous assignment of the target is replaced; undo step "Assign MIDI controller"). An incoming assigned CC sets the parameter **like a knob in the interface** — through the owners (`GraphControl::set_volume/set_pan/set_effect_param/connect`, `TrackControl::set_instrument_param`): an undo step merged with neighboring movements; **right before that it is reported to the automation writer** (`AutomationWriter::touch` with `TouchEnd::Idle`: a knob has no release), which writes it only in Touch/Latch mode while playing (see "Automation: editing and live writing"). The value is linear `min..max` (volume is the linear level `0..1.5`, not the fader curve). An assignment to a vanished target has no effect and is not shown; undoing the target's deletion brings it back; "Clear project" removes assignments. RPC: `midi.learn { target }`, `midi.cancelLearn`, `midi.mappings` → `{ mappings, learning }`, `midi.removeMapping { target }`. Tests — `daw-project/src/tests/midi_mappings.rs`, `daw-rpc/tests/controllers.rs`.
* **Frontend.** Types — `api/types/model.ts` (`ControllerKind`, `ControllerLane`, `MidiMapping`, `MidiMappings`), calls — `api.midi.learn/cancelLearn/mappings/removeMapping`, actions — `actions/midiLearn.ts` (`learn` with the hint "Turn a knob…"; `mappings()` is read from the project copy, without assignments to vanished targets — `domain/automation.ts: targetExists`, the backend's `validate_target`; `learning()` is read from the backend after `learn` and, while waiting, on every project change, because a turned knob ends learning with an edit). Right-click on a knob or fader — `ui/common/ParamMenu.tsx` (the parameter's context menu: "Add / Show automation" (creates the lane if needed, shows it under the timeline and switches to Tracks — `actions/automation.ts: showFor`; the shown lane is UI state `session.selection.automation()`), "Delete automation", then "Assign MIDI controller" / "Remove assignment (CC n)" / "Stop waiting for a knob"); the automation header lists the project's lanes as chips (click shows one) instead of a picker; it is used on `ParamControl` (effect and instrument parameters, except sample choice), `PanKnob`, the width knob of `ChannelUtility`, volume faders (`Inspector`, `NodeStrip`, `ChannelStrip`) and the volume knob in the track header. The list — "Settings" → "MIDI" → "Knobs on parameters" (the same `mappings()`). Mock (`mock/handlers/midi.ts`): there is no knob, so `midi.learn` immediately assigns the first free CC starting from 20.
* **Adding something similar** (e.g. polyphonic pressure): a `ControllerKind` variant and its `range`, parsing in `input.rs` and `read.rs`, writing in `write.rs`, the VST3 number in `midi_map.rs`, tests at every layer; frontend — the kind in `domain/controllers.ts`.

## Track MIDI effects: arpeggiator and chord

A chain of MIDI effects sits on an instrument track **before the instrument**: clip notes and live notes (keyboard, `live.*`) pass through it in order, and the instrument receives the output of the last effect.

* **Contract** — `daw-contracts/src/note_effect.rs`: the realtime side `NoteEffect` (`set_param`, `reset`, `process(segment input, BlockTiming, NoteBuffer)` — no allocations: `NoteBuffer` is allocated in advance, overflow is dropped), the catalog `NoteEffectCatalog` (kinds with `ParamInfo`, as for effects), chain editing `NoteEffectControl` (add/remove/reorder/parameter/bypass — one undo step each, a parameter merges while the knob moves). Model — `Track::note_effects: Vec<NoteEffectSpec { id, kind, params, bypass }>` (JSON `noteEffects`, not written when empty; ids come from the project's shared counter).
* **Implementations** — `daw-note-effects`: `arp` (step 1/4…1/32 with triplets, order Up/Down/Up-down/Random/As played, octaves 1–4, length 10–100 %, swing 0–75 % — every second step is shifted by a fraction of a step). Steps lie on the transport grid (step `k` is tick `k × step`), so they stay in time, in export too; while the transport is stopped, the grid is a free-running clock at the segment tempo, started by the first key press (the first step plays immediately). `chord` (major, minor, sus2, sus4, major 7, minor 7, dominant 7, fifth, octave, "In scale"/"In scale 7" — degrees of the `Scale` taken every other degree from the note's degree; inversion 0–3, "Wide" — the second note from the bottom raised an octave). The chord remembers what it played from each key and counts shared notes, so releasing does not depend on parameter changes. A new kind is a module with `KIND`/`LABEL`/`PARAMS` and a line in `KINDS` (`lib.rs`).
* **Engine** — `daw-engine/src/note_effects.rs`: the conductor gathers the segment's notes (`SegmentNotes`: live ones at frame 0, clip ones at their own frames), `NoteEffectRack` runs the notes of tracks with a chain through the effects (bypassed ones are skipped) and hands them to instruments by frame (`play_events`; a controller on the same frame goes before the note). No stuck notes: the rack remembers the held input keys and the notes the chain has pressed on the instrument; when the chain changes (`DspCommand::SetNoteEffects`, empty — remove) or bypass changes, it releases what is pressed, resets the effects and feeds the held keys again (remove the arpeggiator while holding a chord — the chord sounds); stop and seek — `reset` for all, whatever is sounding is silenced by `all_notes_off`.
* **Core** — `daw-project`: `ProjectNoteEffects` (`note_effects.rs`); reconciliation (`service/sync.rs: sync_note_effects`) recreates the whole chain when its composition or order (id and kind) changes; parameters and bypass travel as a snapshot (as for instruments: only the changed ones, `params::changed`). An effect that failed to create is left out of the chain (a `dsp` log entry and a warning); the rest work.
* **Export and bounce** — the offline engine (`daw-render`, `load_engine`) builds the same chains: export sounds like playback (`daw-bootstrap/tests/render_note_effects.rs`).
* **RPC** — `noteEffects.add {track, kind, params?}` → id, `noteEffects.remove/move/setParam/setBypass {track, effect, …}`; `catalog.get` → `noteEffects`. **Interface** — the "MIDI effects" section of the instrument window (`ui/tracks/NoteEffectsSection.tsx`: add, bypass, ↑/↓, remove, parameters via `ParamControl`), an "ARP"/"CH" badge in the track header (`domain/noteEffects.ts: chainBadge`); actions — `actions/noteEffects.ts`, mock — `mock/handlers/noteEffects.ts` (model only, no sound).
* **Limits.** What is recorded is what was played (the chain input), not its output; MIDI export is also the clip notes. MIDI effect parameters have no automation or MIDI learn (there is no `ParamTarget` for them). The arpeggiator has no latch. At most `MAX_NOTE_EFFECTS` (8) per track. Stop and seek cut off the arpeggio even from held live keys (as with the instrument's sound): the key has to be pressed again. Changing the chain's composition resets its state (the arpeggio pattern starts over).
* **How to add something similar** — a new MIDI effect kind: a module in `daw-note-effects` (implements `NoteEffect`, follows the output contract: by frame, a release before a press on the same frame, every press of its own is released by itself), a line in `KINDS`, a copy of the kind in `app/src/mock/catalog.ts`, the badge in `domain/noteEffects.ts`.

## Automation: editing and live writing

* **Lanes and clips.** `AutomationLane { id, target, clips }` — one lane per param; its `AutomationClip { id, start_tick, length_ticks, loop_ticks, points }` work like looped note clips: the points are a pattern in pattern ticks (`0..=loop_ticks`, from the clip start) repeated every `loop_ticks` over the clip length. Clips of a lane are kept sorted and never overlap; between clips the lane does not touch the param (its project value plays). Value at a tick — `daw_contracts::clip_value_at` / `lane_value_at` (`automation.rs`): local tick = `(tick - start) mod loop`; at the loop seam the last points hold (or lead to a point placed exactly at `loop_ticks`) up to the end of the repeat, and the next repeat restarts at its first point. Contract `AutomationControl` (one interface — "edit automation lanes and their clips"): `add_lane`/`remove_lane`, `add_clip(lane, start, length)` (loop = length capped at `MAX_CLIP_LOOP_TICKS`, starts as a flat line at the param's current value — `ops::target_value`), `edit_clip(AutomationClipEdit { start?, length?, loop? })` (a shorter loop drops points after it), `duplicate_clip` (at the clip end), `remove_clip`, `set_points`, `draw_shape` — every call one undo step (`set_points` of one clip coalesces). Implementation `daw-project/src/automation.rs`. Limits `MAX_LANES` 256, `MAX_AUTOMATION_CLIPS` 1024 per lane, `MAX_POINTS` 4096 per clip. Codes: `AT-011` clip not found, `AT-115` overlap, `AT-116` zero length/loop, `AT-117` end past `u32::MAX`, `AT-118` loop too long, `AT-119` point/shape after the loop end, `AT-212` too many clips. RPC `automation.addClip/editClip/duplicateClip/removeClip/setPoints/drawShape` (all take `lane` and `clip`). Engine: `AutomationPlayer` calls `lane_value_at` (binary search over the sorted clips, no allocation). Mix check `automationOutOfRange` reports out-of-range pattern points at their song tick in the first repeat.
* **Curves.** `AutoPoint { tick, value, curve }` — `curve` (`-1..=1`, JSON default 0) shapes the segment from this point to the next. One formula, documented on the contract: `daw_contracts::curve_shape` / `value_at` (`automation.rs`; `t^e` for `curve > 0`, `1 - (1-t)^e` for `curve < 0`, `e = 4^|curve|`). The engine plays with it (`daw-engine/src/automation.rs`), the interface draws with its mirror `app/src/domain/automationCurve.ts` (`curveShape`, `valueAt`, `curveThrough` — the inverse used when bending). A change of the formula is a change in both places.
* **Shapes.** `AutomationControl::draw_shape(lane, clip, ShapeRequest { from_tick, to_tick, shape, period_ticks, min, max })` replaces the pattern points in `from..=to` (pattern ticks, `to <= loop_ticks`; one undo step); shapes: sine (16 straight steps per period), triangle, saw, square (a jump is two points a tick apart), ramp up/down (period ignored). Point generation is pure: `daw-project/src/automation_shapes.rs`, mirrored by `shapePoints` for the mock. RPC `automation.drawShape { lane, clip, fromTick, toTick, shape, periodTicks, min, max }`. Codes `AT-112` (empty range), `AT-113` (period < `MIN_SHAPE_PERIOD`), `AT-114` (non-number curve).
* **Automation clips (frontend).** An automation lane is a timeline row: `domain/trackRows.ts` `trackRows(tracks, folders, ownedLanes(project))` puts each lane right under the track that owns it (`domain/automation.ts` `laneTrack`: instrument param → its track; a node's volume/pan/effect → the track whose strip — source or inserts — holds the node; a connection level → the owner of its `from`) and lanes of buses/master in a "Buses & master" block at the end; folder collapse and track order apply to them too. Values follow the backend formula in `domain/automationCurve.ts` (`clipValueAt`/`laneValueAt`). On the timeline `ui/tracks/lanePointer.ts` (select, move, resize, double-click adds a one-bar clip, right-click deletes) and `laneRender.ts` (curve and repeat lines inside the shared clip frame, `clipFrame.ts`) handle lane rows, `LaneHeader.tsx` is the left column. The selected lane/clip is `session.selection.automation()` (`{lane, clip|null}`, exclusive with the clip selection; actions set it via `ctx.selectAutomation`; ⌘D/Delete/Esc in `state/clipKeys.ts`), and the bottom `ClipPanel` opens `ui/automation/AutomationClipPanel.tsx` (clip and pattern length in bars, tools, shapes over the whole pattern) with `PatternEditor.tsx` editing one repeat. The write-mode selector is in `TimelineToolbar.tsx`. `editClip` and `setPoints` show the change in the project at once (`patchProject`), so a dropped clip or a moved point is not drawn at its old place for a frame before the refreshed project arrives. To add a clip operation: `api/api.ts` → `actions/automation.ts` → mock handler → gesture in `lanePointer.ts` or a control in `AutomationClipPanel.tsx`; a new parameter kind needs `targetLabel`/`targetRange`/`paramValue`/`laneTrack` cases in `domain/automation.ts`.
* **Pattern editor (frontend).** `ui/automation/patternPointer.ts`: select tool — click adds, drag moves the selection (snapped by the grabbed point), drag on empty space selects a box, Shift-click toggles, the middle handle or Alt-drag bends a segment (value tooltip while dragging); pencil tool — points on grid steps, replacing the stroke span (`domain/controllers.ts: startStroke/extendStroke/strokeOver`, shared with the piano roll controller lane). `PatternEditor.tsx` (keys by the table `PATTERN_KEYS`, which also feeds the shortcut help): Delete, ⌘C/⌘V (paste at the playhead; the clipboard is `actions/automation.ts: copyPoints/pastedPoints`, one for every pattern while the app is open), ⌘A, Esc on the focused lane (`data-owns-keys`), double-click types a value. Pure edits: `domain/automationEdit.ts`. The shape toolbar is in `AutomationClipPanel.tsx` (the whole pattern, the parameter's whole range).
* **Live writing.** Contract `AutomationWriter` (`daw-contracts/src/automation_write.rs`): global `AutomationWriteMode { Off, Touch, Latch }` (run state, not in the project; RPC `automation.writeMode` / `automation.setWriteMode`, shown in the `tick` as `automationWrite`), `touch(target, value, TouchEnd)` — called right *before* the param is set through its owner, `release(target)`, `release_all()`. Who reports: the frontend action layer (`actions/paramTouch.ts: createParamTouch`, used by `actions/graph.ts` — volume, pan, effect params, connection levels — and `actions/tracks.ts` — instrument params; only while playing with the mode on; a mouse/key up anywhere releases, `state/touchRelease.ts`) through RPC `automation.touch` / `automation.releaseAll`, and MIDI knobs (`ProjectMidiMappings`, `TouchEnd::Idle`: released after `TOUCH_IDLE_MS` without moves). Plugin windows do not report yet.
* **Writer** (`daw-automation-writer`). The play position comes from `TransportControl` (its own reference, not the core's). A touch opens the pass's edit group (`HistoryControl::begin_group`; the param moves themselves join it) and starts a stretch for the target (lane created with `add_lane` if missing) in one clip: the clip under the play position, written at its pattern position (in a looped clip the pattern of every repeat changes), or — outside clips — a new clip from the bar start of the touch (`TempoControl::tempo_map().bar_start`, not before the previous clip's end) that grows (length = loop, whole beats) with the writing up to the next clip or `MAX_CLIP_LOOP_TICKS`. The poll (20 ms) extends active stretches to the play position (Latch, or a held Touch), ends idle knobs, starts a new stretch when the position leaves the clip, crosses the loop seam or jumps back (in whatever clip is there then), and sends clips with `edit_clip` (growth) + `set_points` at most every 100 ms. A stretch replaces the old pattern points inside its span and adds joins a tick before and (except in a growing clip) after it with the old values (`stretch.rs`); close moves (< 30 ticks) merge into one point. While a target is written the engine does not play its lane: `AutomationHold::hold(lanes)` → `EngineLink` (`link/held.rs`, atomic slots, no locks) → `AutomationPlayer` skips it and the param's project value (moved by the performer) sounds. Stop/pause or mode `Off` ends the pass: holds are cleared, the group closes = one undo step. A lane or clip deleted while writing just stops its writing; other failures go to the log (`automation`, once per pass).
* **Mock.** `mock/handlers/automation.ts` mirrors the methods; live writing is simplified (a point per touch into the clip under the play position or a new clip from the bar start that grows during the pass; one undo step per pass).
* **Adding a parameter kind** to live writing: its `ParamTarget` must already be automatable; report its moves with `touch` from the action that sets it (and from MIDI if it can be mapped).

## Errors as codes

Every contract failure is a `daw_contracts::ContractError` (`daw-contracts/src/error.rs`): a registered code plus named parameters, never free text.

* **Code** — `AA-KNN`: `AA` the area prefix, `K` the kind (`ErrorKind`: `0` not found, `1` invalid value, `2` limit or range, `3` state/conflict — not possible right now, `4` system/IO — files, devices, plugins, `5` unsupported, `9` internal), `NN` the number within the area and kind. One code — one situation. Example: `TR-001` "Track {id} not found".
* **Registry** — `crates/daw-contracts/src/codes/`: one module per area (`tracks.rs`, `clips.rs`, `graph.rs`…), each a `codes! { NAME = "AA-KNN", "English template with {param}"; … }` list; the table of prefixes is at the top of `codes/mod.rs`. The English message is the template filled with the parameters (`ContractError::message`).
* **Building an error** — `codes::tracks::NOT_FOUND.with("id", id)` (more parameters — chained `.with(...)`), or `.err()` when there are none; check a specific failure with `error.is(codes::…)`, its kind with `error.kind()`.
* **Over the wire** — RPC and Tauri send `{ code, params, message }`. The interface (`app/src/i18n/errors/`) shows the text in the current language: English is the backend's `message`, Russian is the template from `errors/ru.ts` looked up by code and filled with `params`; the code is appended to the text, so a screenshot names the exact failure. MCP clients get `CODE: message` (for example `TR-001: Track 7 not found`). The error log records the code and message as well.
* **Test** — `codes/mod.rs` checks that codes are unique, well-formed (prefix and kind digit match their area module) and that every code has a Russian translation in `app/src/i18n/errors/ru.ts`.
* **How to add a failure:** add a line to the area module (next free number for the kind), build it with `codes::NAME.with("param", v)`, add the Russian text with the same `{param}` placeholders to `app/src/i18n/errors/ru.ts`. If the browser mock (`app/src/mock/`) must reproduce it, return the same code there. A new area: a new module, a prefix in the table and in `AREAS` in `codes/mod.rs`.

## Languages of backend labels (`daw_contracts::i18n`)

English is the default, Russian the second language. The choice is `Preferences::language` (JSON `"language": "en" | "ru"`, missing — `"en"`, anything else — the preferences are rejected). The current language is one process-wide value, `i18n::current()` / `i18n::set_current()` (an `AtomicU8`): it is a display setting read wherever a label is built, like a locale, so it is not threaded through every contract. Only the preferences store sets it — `PreferencesFile` on open (the saved value, before `daw-bootstrap` builds anything else) and after a successful `set`; the audio thread never reads it. After `preferences.set` the interface re-reads the catalog: nothing caches label text, every `kinds()`/`patterns()` call serializes in the current language. Texts already built (undo labels, names of created tracks and buses) stay in the language they were made in.

Texts live next to the code that uses them, as an English + Russian pair (no key catalogs):
* a fixed `&'static` label — `L10n { en: "Cutoff, Hz", ru: "Срез, Гц" }` (`L10n::same("Q")` when there is nothing to translate); `.get()` gives the current text, `Display` and `Serialize` write it. Catalog tables use it: `ParamInfo::label`, `ParamInfo::choices` (`&'static [L10n]`), `KindInfo::label`, `EffectFactory::label`/`InstrumentFactory::label`, pattern names and descriptions (`daw-patterns/src/data.rs`). VST3 labels come from the plugin in its own language: `daw-vst3/src/text.rs::leak_label` makes `L10n::same(...)`;
* a formatted text — `tr!("Bounce to audio «{name}»", "Свести в аудио «{name}»")` → `String` in the current language; both strings take the same arguments (inline `{name}` or trailing `, value`) and use all of them. Undo labels are written this way: `project.edit(&tr!("Add note", "Добавить ноту"), …)`; a reused label is a `const LABEL: L10n` passed as `LABEL.get()`.

Errors are not localized this way: they are registered codes translated by the interface (see "Errors as codes"); log texts stay in English. Tests: the default language is English, so ordinary tests expect English labels; a test that switches the language lives in its own test program (`tests/language.rs` in `daw-contracts`, `daw-persistence`, `daw-bootstrap`) — a separate process, so the global switch cannot race with other tests. Adding a label: write the pair at the place of use; a new catalog table entry takes `L10n`, never a bare `&str`.

## How to add a new operation (end-to-end order)

Example: "rename a mixer track". Every step is checked by the compiler and tests, so no step can be skipped.

1. **Contract** — a method in the area's trait (the area file in `crates/daw-contracts/src/`: `tracks.rs`, `clips.rs`, `notes.rs`, `graph_control.rs`, `automation.rs`, `history.rs`, `record.rs`, `project_io.rs`…, e.g. `TrackControl::rename_track`). Describe the errors and edge cases in the doc comment; failures are codes from `daw_contracts::codes` (add new ones to the area's module).
2. **Implementation** — in the crate that owns the area (`crates/daw-project/src/mixer.rs`), through the shared edit pipeline `edit(...)` (undo, DSP, snapshot); the test goes in the area file `crates/daw-project/src/tests/<area>.rs`.
3. **RPC** — a line in the method table (`crates/daw-rpc/src/mixer.rs`: `table.add("mixer.renameTrack", "What it does.", ...)`); a test in `crates/daw-rpc/tests/`.
4. **Frontend API** — a typed wrapper in `app/src/api/api.ts`.
5. **Browser mock** — a handler in `app/src/mock/handlers/<area>.ts` with the same checks as the real backend, returning the same error codes.
6. **Action** — a method in the area's interface `app/src/actions/<area>.ts` and in its implementation (this is also where we decide how to show an error and what to re-read). There are no frontend tests yet.
7. **Interface** — the component calls `session.actions.<area>.<method>()`; it sees neither `api` nor `rpc`.
8. If a new role or folder appeared, update this file.

Look-alike "pass-throughs" in the actions layer are a deliberate price for the layer boundary: every line is obvious, and a forgotten step is caught by `tsc`.
